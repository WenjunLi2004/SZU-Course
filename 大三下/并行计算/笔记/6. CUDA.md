# 1. 为什么需要 CUDA

## 1.1 直观理解

CPU 像少数几个很强的工程师，擅长复杂控制、分支判断和系统调度；
GPU 像一大片流水线工厂，单个工人不强，但**人数很多**，适合让大量线程对大量数据执行相同或相似操作

> [!important]+ 一句话  
> **GPU 的优势不是单线程强，而是吞吐量高**

典型适合 GPU 的任务：

- **向量加法**：`z[i] = x[i] + y[i]`
- **矩阵乘法**：每个线程负责一个 `z[row][col]`
- **图像处理**：每个线程处理一个像素
- **数值积分**：每个线程计算一部分梯形
- **深度学习**：大量矩阵/张量运算

不太适合 GPU 的任务：

- 大量复杂 `if-else`
- 不规则数据结构，如链表、树形指针追踪
- 强依赖串行流程
- 数据规模很小但传输开销很大的任务

## 1.2 严谨定义

| 术语        | 定义                                                                |
| --------- | ----------------------------------------------------------------- |
| GPU       | Graphics Processing Unit，图形处理单元，最初用于图形渲染                          |
| **GPGPU** | General-Purpose computing on GPU，用 GPU 解决通用计算问题                   |
| **CUDA**  | Compute Unified Device Architecture，**NVIDIA** 提供的 GPU 通用编程平台/API |
| OpenCL    | 更可移植的异构编程 API，可用于 GPU、FPGA、DSP 等                                  |
| 异构计算      | 同时使用不同架构处理器，例如 CPU + GPU                                          |

## 1.3 与 MPI / Pthreads / OpenMP 对比

| 模型       | 硬件/内存模型          | 并行单位    | 通信/协作方式                    | 典型用途      |
| -------- | ---------------- | ------- | -------------------------- | --------- |
| MPI      | 分布式内存            | 进程      | 显式消息传递                     | 多机集群      |
| Pthreads | 共享内存             | CPU 线程  | 共享变量 + 锁/条件变量              | 单机多核细粒度控制 |
| OpenMP   | 共享内存             | CPU 线程组 | 编译指示、reduction、barrier     | 循环并行、增量并行 |
| CUDA     | **CPU + GPU 异构** | GPU 线程  | host/device 内存、kernel、显存传输 | 大规模数据并行   |

> [!note]+ 考试句  
> CUDA 是用于 NVIDIA GPU 的并行编程模型
> 它由主机 CPU 启动设备 GPU 上的核函数，GPU 通过大量轻量级线程执行数据并行任务，并需要考虑主机内存与设备显存之间的数据传输

# 2. GPU 架构：SM、SP、SIMD、SIMT、warp

## 2.1 层级直观图

```text
GPU
├── SM 0
│   ├── CUDA Core / SP
│   ├── CUDA Core / SP
│   └── ...
├── SM 1
│   └── ...
└── ...
```

| 名称             | 直观类比 | 严谨含义                            |
| -------------- | ---- | ------------------------------- |
| GPU            | 整个工厂 | 图形/通用并行处理器                      |
| SM             | 一个车间 | Streaming Multiprocessor，流式多处理器 |
| SP / CUDA Core | 工人   | SM 内的数据通路/计算核心                  |
| **warp**       | 一组工人 | GPU 调度和执行的基本单位，通常 32 个线程        |

## 2.2 SIMD 与 SIMT

### SIMD

**SIMD = Single Instruction Multiple Data，单指令多数据**

一个控制单元发出同一条指令，多个数据通路对不同数据执行同一种操作

例如：

```c
b[i] = a[i] * 2;
```

不同数据 `a[i]` 执行同样的乘法

### SIMT

**SIMT = Single Instruction Multiple Threads，单指令多线程**

==**CUDA 程序员写的是很多线程，但 GPU 硬件会把线程按 warp 组织起来，以类似 SIMD 的方式执行**==

> [!warning]+ 重点区别  
> NVIDIA GPU 严格说是 **SIMT**，不是传统意义上的纯 SIMD
> 程序员看到的是 thread，硬件底层按 warp 成组执行

## 2.3 warp

`warp`中文为 **线程束**

| 问题                    | 答案                               |
| --------------------- | -------------------------------- |
| 一个 warp 通常多少线程？       | **32**                           |
| 这个值在哪？                | **系统变量** `warpSize`              |
| warp 是什么单位？           | ==**GPU 调度和执行的基本单位**==           |
| 一个 block 会被拆到多个 SM 吗？ | 不会，==**一个 block 分配给一个 SM**==     |
| 不同 warp 一定在不同 SM 吗？   | 不一定，==**一个 SM 可以驻留多个 warp**==    |
| 一个SP执行一个线程吗？          | **==一个 SP 在同一时刻只能执行一个线程的一条指令==** |

**线程并不是永久绑定某个 SP**

同一时刻：
```
SP5
↓
Thread5 的 add 指令
```

下一时刻：
```
SP5
↓
Warp7 中 Thread5 的 mul 指令
```


## 3.2 主机代码与设备代码

| 代码类型 | 运行位置 | 示例 |
|---|---|---|
| host code | CPU 主机端 | `main`、`malloc`、`cudaMemcpy` |

## 3.3 函数修饰符

| 修饰符                   | 谁调用            | 哪里执行       | 用途             |
| --------------------- | -------------- | ---------- | -------------- |

# 4. CUDA Hello World

## 4.1 代码

```c
#include <stdio.h>
#include <cuda.h>

__global__ void Hello(void) {
    printf("Hello from thread %d!\n", threadIdx.x);
}

int main(void) {
    int thread_count = 10;
    Hello<<<1, thread_count>>>();
    cudaDeviceSynchronize();
    return 0;
}
```

## 4.2 逐行理解

| 代码                             | 含义                                         |
| ------------------------------ | ------------------------------------------ |
| `__global__ void Hello(void)`  | 定义 GPU kernel，由 CPU 启动，在 GPU 上执行           |
| `Hello<<<1, thread_count>>>()` | 启动 1 个 block，每个 block 有 `thread_count` 个线程 |
| `threadIdx.x`                  | 当前线程在 block 内的 x 方向编号                      |
| `cudaDeviceSynchronize()`      | CPU 等待 GPU kernel 执行完成                     |

> [!warning]+ 常见误区  
> `__global__` 不是“全局变量”，而是 CUDA kernel 修饰符
> `Hello<<<...>>>()` 也不是普通函数调用，而是 ==**kernel launch**==

# 5. thread、block、grid

## 5.1 三层结构

```text
kernel launch
└── 一个 grid
    ├── block 0
    │   ├── thread 0
    │   ├── thread 1
    │   └── ...
    ├── block 1
    └── ...
```

| CUDA 变量     | 推荐理解               | 含义                         |
| ----------- | ------------------ | -------------------------- |
| `threadIdx` | thread id in block | **线程**在本 **block** 内的编号    |
| `blockIdx`  | block id in grid   | **block** 在 **grid** 中的编号  |
| `blockDim`  | threads per block  | 每个 block 的形状/**线程数**       |
| `gridDim`   | blocks per grid    | 一个 grid 中 **block 的形状/数量** |

> [!important]+ 关键纠正  
> 一次 kernel launch 只有 **一个 grid**
> `<<<A, B>>>` 中的 `A` 不是 grid 的数量，而是这个 grid 中 block 的数量配置

## 5.2 一维全局线程编号

```c
int tid = blockIdx.x * blockDim.x + threadIdx.x;
```

含义：

```text
当前 block 前面已经覆盖的线程数 + 当前线程在 block 内的编号
```

例如：

```c
Kernel<<<4, 256>>>();
```

| block | `threadIdx.x` | `tid` 范围 |
|---|---|---|
| block 0 | 0~255 | 0~255 |
| block 1 | 0~255 | 256~511 |
| block 2 | 0~255 | 512~767 |
| block 3 | 0~255 | 768~1023 |

## 5.3 二维矩阵编号

矩阵乘法常用二维 block 和二维 grid：

```c
dim3 block_dim(16, 16);
dim3 grid_dim((n + block_dim.x - 1) / block_dim.x,
              (n + block_dim.y - 1) / block_dim.y);
```

在 kernel 中：

```c
int row = blockIdx.y * blockDim.y + threadIdx.y;
int col = blockIdx.x * blockDim.x + threadIdx.x;
```

| 方向 | 计算式 | 含义 |
|---|---|---|
| x 方向 | `blockIdx.x * blockDim.x + threadIdx.x` | 列号 `col` |
| y 方向 | `blockIdx.y * blockDim.y + threadIdx.y` | 行号 `row` |

> [!tip]+ 命名建议  
> 一维问题建议用 `th_per_blk` 和 `blk_ct`；
> 二维问题建议用 `block_dim` 和 `grid_dim`
> 如果怕混淆，写成 `threads_per_block` 和 `blocks_per_grid` 最清楚

# 6. CUDA 内存模型

## 6.1 host 与 device

| 名称         | 含义       | 例子                            |
| ---------- | -------- | ----------------------------- |
| **host**   | CPU 及其内存 | `malloc` 得到的 `x, y, z`        |
| **device** | GPU 及其显存 | `cudaMalloc` 得到的 `dx, dy, dz` |

**CUDA 异构程序经常包含以下流程：**

```c
CPU 准备数据   |x = (float *)malloc(n * sizeof(float));|
→ GPU 准备空间  |cudaMalloc(&dx, n * sizeof(float));|
→ 拷贝到 GPU 显存  |cudaMemcpy(da, a, n * sizeof(float), cudaMemcpyHostToDevice);|
→ CPU 启动 GPU kernel | Vec_add<<<blk_ct, th_per_blk>>>(dx, dy, dz, n);| 
→ CPU 等待 GPU 完成  | cudaDeviceSynchronize();|
→ 拷贝结果回 CPU  |cudaMemcpy(z, dz, n * sizeof(float), cudaMemcpyDeviceToHost);|
```

## 6.2 统一内存：`cudaMallocManaged`

```c
float* x;
cudaMallocManaged(&x, n * sizeof(float));
```

| 优点                | 缺点                |
| ----------------- | ----------------- |
| CPU/GPU 都能访问，写法简单 | 可能有页面迁移开销，性能不一定最好 |

## 6.3 显式设备内存：`cudaMalloc` + `cudaMemcpy`

```c
float *x, *dx;
x = (float*)malloc(n * sizeof(float));
cudaMalloc(&dx, n * sizeof(float));
cudaMemcpy(dx, x, n * sizeof(float), cudaMemcpyHostToDevice);
```

| 函数                                                | 含义           |
| ------------------------------------------------- | ------------ |
| `cudaMalloc(&dx, size)`                           | 在 GPU 显存分配空间 |
| `cudaMemcpy(dx, x, size, cudaMemcpyHostToDevice)` | CPU → GPU    |
| `cudaMemcpy(x, dx, size, cudaMemcpyDeviceToHost)` | GPU → CPU    |
| `cudaFree(dx)`                                    | 释放 GPU 显存    |

> [!warning]+ 易错点  
> `cudaMalloc` 分配的是设备显存，CPU 不能像普通指针那样直接读写它；
> **需要用 `cudaMemcpy` 或统一内存**

# 7. 整体骨架例子：向量加法

## 7.1 kernel

```c
__global__ void Vec_add(const float x[], const float y[], float z[], const int n) {
    int my_elt = blockDim.x * blockIdx.x + threadIdx.x;
    if (my_elt < n)
        z[my_elt] = x[my_elt] + y[my_elt];
}
```

## 7.2 调用

```c
int th_per_blk = 1024;
int blk_ct = (n + th_per_blk - 1) / th_per_blk;
Vec_add<<<blk_ct, th_per_blk>>>(dx, dy, dz, n);
cudaDeviceSynchronize();
```

## 7.3 为什么要判断 `if (my_elt < n)`

==**因为 block 数量通常向上取整**==：

```c
blk_ct = (n + th_per_blk - 1) / th_per_blk;
```

**实际启动线程数一般都大于 `n`，多出来的线程必须排除，否则会越界访问**

# 8. 从 CUDA 核函数返回结果

## 8.1 为什么不能普通 return

kernel 在 GPU 上异步执行，且由大量线程并行执行，不适合像普通 C 函数一样：

```c
int ans = Kernel(...);
```

**CUDA kernel 通常通过==指针==写回结果**
1. **统一内存**：`cudaMallocManaged`，kernel 修改的数据对 CPU 和 GPU 共享
2. **显式设备返回**：`cudaMalloc()` + `cudaMemcpy(..., cudaMemcpyDeviceToHost)`，kernel 将结果写入 GPU 显存，需要显式复制回主机
## 8.2 错误思路

```c
__global__ int Add(int x, int y) {
    return x + y; // kernel 不这样返回结果
}
```

## 8.3 统一内存返回

```c
__global__ void Add(int x, int y, int* sum_p) {
    *sum_p = x + y;
}

int* sum_p;
cudaMallocManaged(&sum_p, sizeof(int));
Add<<<1, 1>>>(2, 3, sum_p);
cudaDeviceSynchronize();
printf("%d\n", *sum_p);
cudaFree(sum_p);
```

## 8.4 显式设备内存返回

```c
int* hsum_p;
int* dsum_p;

hsum_p = (int*)malloc(sizeof(int));

cudaMalloc(&dsum_p, sizeof(int));
Add<<<1, 1>>>(2, 3, dsum_p);
cudaDeviceSynchronize();

cudaMemcpy(hsum_p, dsum_p, sizeof(int), cudaMemcpyDeviceToHost);
```

## 8.5 `__managed__` 全局变量

```c
__managed__ int sum;

__global__ void Add(int x, int y) {
    sum = x + y;
}
```

# 9. CUDA 梯形法则与并行求和

## 9.1 串行梯形法则

目标是近似计算：

$$
\int_a^b f(x)\,dx
$$

梯形法则：

$$
h = \frac{b-a}{n}
$$

$$
T = h\left[\frac{f(a)+f(b)}{2}+\sum_{i=1}^{n-1}f(a+ih)\right]
$$

串行核心：

```c
trap = 0.5 * (f(a) + f(b));
for (int i = 1; i <= n - 1; i++) {
    x = a + i * h;
    trap += f(x);
}
trap = trap * h;
```

## 9.2 CUDA 朴素版本：atomicAdd

```c
__global__ void Dev_trap(const float a, const float b, const float h,
                         const int n, float* trap_p) {
    int my_i = blockDim.x * blockIdx.x + threadIdx.x;
    if (0 < my_i && my_i < n) {
        float my_x = a + my_i * h;
        float my_trap = f(my_x);
        atomicAdd(trap_p, my_trap);
    }
}
```

问题：
- 每个线程都 `atomicAdd`
- **原子操作次数太多**
- **全局求和竞争严重**

## 9.3 经典改进思路：局部计算以减少原子操作

```text
每个线程算局部值
→ warp 内归约
→ block 内归约
→ 全局归约
```

这和 OpenMP 的 `reduction(+:sum)` 思想一致，只是 **CUDA 要手动写**

# 10(a). warp shuffle 归约

## 10.1 `__shfl_down_sync` warp 洗牌函数

```c
temp += __shfl_down_sync(mask, temp, diff);
```

**temp：核函数内定义的局部变量，每个线程都有**

**lane「通道」**：线程束中线程的序列号 `lane = threadldx.x % warpSize`

**含义：**

> 当前 lane 从同一个 warp 内 `lane + diff` 的线程那里读取它的 `temp` 值，并加到自己的 `temp` 上

## 10.2 树形归约过程

假设 `warpSize = 32`：

```text
diff = 16: lane 0 += lane 16, lane 1 += lane 17, ...
diff = 8 : lane 0 += lane 8,  lane 1 += lane 9,  ...
diff = 4 : lane 0 += lane 4,  lane 1 += lane 5,  ...
diff = 2 : lane 0 += lane 2,  lane 1 += lane 3,  ...
diff = 1 : lane 0 += lane 1
```

最后：

> **每个 warp 的 lane 0 拿到完整 warp_sum**
> 总共进行 $\log_{2}{t} +1$ 次加法 

## 10.3 实现

```c
unsigned mask = 0xffffffff;
for (int diff = warpSize / 2; diff > 0; diff /= 2) {
    temp += __shfl_down_sync(mask, temp, diff);
}
if (threadIdx.x % warpSize == 0) {
    atomicAdd(sum_p, temp);
}
```

- **mask**：指示哪些线程正在参与调用
>   通常会使用线程束中的所有线程，即mask = 0xffffffff
- **向下洗牌**：diff 的类型是无符号，返回的值来自更高序列号的线程
>   如果超出warpSize，则**返回当前线程自己的 `temp`**，虽然混乱，但是不用

## 10.4 为什么只让 lane 0 atomicAdd

`__shfl_down_sync` 后，不是所有线程都有完整和完整结果，**只在每个 warp 的 lane 0 上**

```c
threadIdx.x % warpSize == 0
```

选出的就是：

```text
threadIdx.x = 0, 32, 64, 96, ...
```

也就是每个 warp 的第 0 个 lane

> [!danger]+ 如果所有线程都 atomicAdd  
> 会把同一批数据重复加很多次，结果错误

# 11. shared memory 与 block 级归约

## 11.1 为什么需要 shared memory

warp shuffle 只能在同一个 warp 内交换寄存器值，不能跨 warp，更不能跨 block

如果一个 block 有 256 个线程，就有 8 个 warp每个 warp 得到一个 `warp_sum` 后，可以：

- 简单版：每个 warp 的 lane 0 直接 `atomicAdd`
- 优化版：先把 8 个 `warp_sum` 写入 shared memory，再由第一个 warp 归约成 `block_sum`，每个 block 只 `atomicAdd` 一次


## 11.2 简单版结构

```text
thread → warp → global
```

优点：简单，符合实验要求  
缺点：每个 warp 都 atomicAdd，原子操作次数较多

## 11.3 完整 block 级归约结构

```text
thread → warp → block → global
```

优点：每个 block 只 atomicAdd 一次  
缺点：代码更复杂，需要 shared memory 和 `__syncthreads()`

==`warp_sum_arr` **必须至少有 32 个元素**==

# 12. 实验：CUDA 矩阵乘法 + 矩阵元素求和

## 12.1 实验目标

- 用 CUDA 计算两个 $n \times n$ 方阵 `x` 和 `y` 的乘积 `z`
- 用 CUDA 计算 `z` 中所有元素之和
- 测试不同规模 `n = 32, 64, 128, 256, 512, 1024`
- 每组运行 5 次取平均
- 与 CPU 串行版本比较，计算加速比

## 12.2 矩阵乘法 kernel

```c
__global__ void Matrix_mult(const float dx[], const float dy[], float dz[], const int n)
{
    int r = blockIdx.y * blockDim.y + threadIdx.y;
    int c = blockIdx.x * blockDim.x + threadIdx.x;

    if (r < n && c < n)
    {
        float temp = 0.0;
        for (int i = 0; i < n; i++)
        {
            temp += dx[r * n + i] * dy[i * n + c];
        }
        dz[r * n + c] = temp;
    }
}
```

核心解释：

| 代码 | 含义 |
|---|---|
| `r = blockIdx.y * blockDim.y + threadIdx.y` | 当前线程负责的行 |
| `c = blockIdx.x * blockDim.x + threadIdx.x` | 当前线程负责的列 |
| `temp += dx[r*n+i] * dy[i*n+c]` | 计算第 `r` 行与第 `c` 列点积 |
| `dz[r*n+c] = temp` | 写回结果矩阵元素 |
| `if (r < n && c < n)` | 防止越界 |

## 12.3 调用配置

```c
dim3 block_dim1(16, 16);
dim3 grid_dim1((n + block_dim1.x - 1) / block_dim1.x,
               (n + block_dim1.y - 1) / block_dim1.y);

Matrix_mult<<<grid_dim1, block_dim1>>>(dx, dy, dz, n);
```

注意：

- `block_dim1(16,16)`：每个 block 有 256 个线程
- 256 是 `warpSize=32` 的整数倍
- `grid_dim1` 实际表示 **一个 grid 中 block 的二维布局**
- 一次 kernel launch 只有一个 grid

## 12.4 Sum kernel

```c
__global__ void Sum(const float a[], int n, float *sum_p)
{
    int id = blockIdx.x * blockDim.x + threadIdx.x;
    float temp = 0.0;

    if (id < n)
    {
        temp = a[id];
    }

    unsigned mask = 0xffffffff;
    for (int diff = warpSize / 2; diff > 0; diff /= 2)
    {
        temp += __shfl_down_sync(mask, temp, diff);
    }

    if (threadIdx.x % warpSize == 0)
    {
        atomicAdd(sum_p, temp);
    }
}
```

这里的 `n` 表示元素总数，因此调用时应传：

```c
Sum<<<grid_dim2, block_dim2>>>(dz, n * n, sum_p);
```

## 12.5 Sum 的层级解释

```text
thread 层：每个线程读取一个 dz[id] 到 temp
warp 层：__shfl_down_sync 做 warp 内树形归约
global 层：每个 warp 的 lane 0 用 atomicAdd 累加到 sum_p
```

> [!note]+ 本实验版本  
> 当前 Sum 是 `thread → warp → global` 的简化归约block 在这里主要是 warp 的容器，没有额外做 shared memory 的 block 级归约

## 12.6 加速比公式

$$
S = \frac{T_{CPU}}{T_{GPU}}
$$

| 符号      | 含义                                               |
| ------- | ------------------------------------------------ |
| `T_CPU` | CPU 串行矩阵乘法 + 串行求和时间                              |
| `T_GPU` | CUDA 矩阵乘法 kernel + CUDA 求和 kernel 及统计范围内的同步/拷贝时间 |

> [!warning]+ 不要写反  
> 加速比是 **CPU time / GPU time**，不是 GPU time / CPU time

## 12.7 误差解释

GPU 与 CPU 结果不完全一致是正常的：

- 浮点加法不满足严格结合律
- GPU 矩阵乘法累加顺序可能和 CPU 不同
- warp shuffle 和 `atomicAdd` 的归约顺序不同
- `atomicAdd` 执行顺序不固定

只要误差相对结果规模较小，就属于正常浮点误差

# 13. CUDA 性能分析

## 13.1 GPU 不一定总是更快

GPU 总时间包含：

```text
数据传输时间 + kernel 启动开销 + GPU 计算时间 + 同步等待时间
```

小规模问题可能 GPU 不明显，因为并行开销占比较大

## 13.2 `-O3` 的作用

`nvcc -O3` 会进行：

- 循环优化
- 地址计算优化
- 寄存器分配优化
- 指令调度
- 内联优化
- 减少不必要访存

矩阵乘法中每个线程都有内部 `for` 循环，`-O3` 对性能影响很大

## 13.3 block size 怎么选

| 选择         | 特点                             |
| ---------- | ------------------------------ |
| **32 的倍数** | **充分利用 warp**                  |
| 128 / 256  | 常见、稳定                          |
| 512 / 1024 | 线程更多，但资源压力更大                   |
| 16×16      | 矩阵乘法常用，256 threads/block       |
| 32×32      | 1024 threads/block，可能更快也可能占用过高 |

## 13.4 分支发散

同一个 warp 内线程走不同分支：

```c
if (a[i] > 0)
    b[i] = a[i] * 2;
else
    b[i] = a[i] - 1;
```

如果一个 warp 内部分线程走 `if`，部分走 `else`，GPU 可能分批执行，导致部分线程空闲

> [!tip]+ 判断标准  
> 不是“有 if 就不能用 GPU”，而是看同一 warp 内分支是否严重分化，以及分支内部计算是否复杂

## 13.5 合并访存

GPU 喜欢同一个 warp 的相邻线程访问相邻地址：

```text
lane 0 → a[0]
lane 1 → a[1]
lane 2 → a[2]
...
lane 31 → a[31]
```

这叫 global memory coalescing，合并访存

## 13.6 global memory 与 shared memory

| 内存 | 位置 | 速度 | 可见范围 | 用途 |
|---|---|---|---|---|
| global memory | GPU 显存 | 慢 | 所有线程 | 大数组、输入输出 |
| shared memory | SM 上片上内存 | 快 | 同一个 block | block 内协作、缓存 tile |
| register | 每个线程私有 | 最快 | 单线程 | 局部变量 |
| managed memory | 统一内存 | 方便但可能迁移 | CPU/GPU | 简化编程 |

# 16. 常见误区

| 误区 | 正确理解 |
|---|---|
| `grid_size` 是 grid 的数量 | 一次 kernel launch 只有一个 grid，`gridDim` 是 block 布局 |
| `threadIdx.x` 是全局线程号 | 它只是 block 内编号，全局号要结合 `blockIdx` 和 `blockDim` |
| `__global__` 是全局变量 | 它是 kernel 函数修饰符 |
| kernel 可以普通 return | kernel 通常通过指针写回结果 |
| GPU 一定比 CPU 快 | 小规模或传输开销大时不一定 |
| 一个 CUDA core 等于 CPU core | CUDA core 更轻量，靠数量和吞吐取胜 |
| 有 if 就不能用 GPU | 关键看同一 warp 内是否严重分支发散 |
| warp shuffle 可以跨 block | 不行，只能在同一个 warp 内交换 |
| `atomicAdd` 不需要 | 多线程更新同一变量时需要防止竞争 |
| CPU/GPU 浮点结果必须完全一样 | 并行归约顺序不同，小误差正常 |

# 18. 典型题答题模板

## 18.1 简述 CUDA 编程模型

> CUDA 是 NVIDIA 提供的 GPU 通用并行编程模型CUDA 程序采用 CPU + GPU 异构计算结构，CPU 作为 host 负责程序控制、数据准备、内存传输和 kernel 启动，GPU 作为 device 负责执行大量并行线程程序员通过 `<<<grid, block>>>` 指定线程块和线程组织方式，通过 `threadIdx`、`blockIdx`、`blockDim` 和 `gridDim` 计算每个线程负责的数据位置

## 18.2 `<<<blk_ct, th_per_blk>>>` 的含义

> 该语法表示启动一个 CUDA 核函数第一个参数 `blk_ct` 表示一个 grid 中线程块 block 的数量或布局；第二个参数 `th_per_blk` 表示每个 block 中线程 thread 的数量或布局一次 kernel launch 只有一个 grid，grid 由多个 block 组成，block 由多个 thread 组成

## 18.3 为什么需要 `cudaDeviceSynchronize`

> CUDA kernel 启动通常是异步的，CPU 发起 kernel 后可能继续执行后续代码`cudaDeviceSynchronize()` 使主机端等待设备端所有已启动的工作完成，常用于保证结果已经计算完、保证 printf 输出完成以及进行正确计时

## 18.4 为什么 GPU 适合数据并行

> GPU 拥有大量相对简单的计算核心，采用 SIMT 模型组织大量线程对于大量数据执行相同或相似操作的问题，例如向量加法、矩阵乘法和数值积分，不同数据之间相互独立，能够被映射到大量 GPU 线程上并行执行，因此 GPU 能获得较高吞吐量

## 18.5 为什么复杂分支会降低 GPU 性能

> GPU 中线程通常按 warp 成组执行同一个 warp 内线程执行相同指令流时效率较高如果同一 warp 内不同线程走不同分支，硬件需要分别执行不同路径，未走当前路径的线程会空闲，产生分支发散，降低并行效率

## 18.6 CUDA 中如何做并行求和

> CUDA 并行求和通常先让每个线程计算局部和，然后在 warp 内使用 `__shfl_down_sync` 做树形归约，使每个 warp 的 lane 0 得到 warp 局部和由于 warp shuffle 只能在同一 warp 内进行，多个 warp 或多个 block 的结果还需要通过 shared memory 进一步归约，或使用 `atomicAdd` 合并到全局结果中

## 18.7 矩阵乘法 kernel 怎么设计

> 对于 $n \times n$ 矩阵乘法，可使用二维 grid 和二维 block每个 CUDA 线程负责计算结果矩阵中的一个元素，行号由 `blockIdx.y * blockDim.y + threadIdx.y` 得到，列号由 `blockIdx.x * blockDim.x + threadIdx.x` 得到线程内部通过一个循环计算对应行与列的点积，并通过边界判断防止越界

# 20. 常见误区汇总

- 把 `gridDim` 当作 grid 数量
- 忘记 kernel 是异步启动
- 忘记 `cudaDeviceSynchronize`
- 把 `cudaMalloc` 指针当 CPU 普通指针直接访问
- 把 `threadIdx.x` 当全局 id
- 求和时所有线程直接 `*sum_p += temp`
- warp shuffle 后让所有线程都 `atomicAdd`
- 忘记 `Sum` 中传的是 `n*n` 而不是矩阵阶数 `n`
- 浮点误差非零就认为程序错
- 做性能实验时忘记 `nvcc -O3`
