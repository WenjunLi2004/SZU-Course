Pthreads = ==**共享内存**==里的==**多线程**==编程

| 对比点  |            MPI            |         Pthreads          |
| ---- | :-----------------------: | :-----------------------: |
| 并行单位 |           多个进程            |      一个进程里的**多个线程**       |
| 内存关系 |       通常各进程有自己的地址空间       |      所有线程共享同一个进程地址空间      |
| 通信方式 | MPI_Send / MPI_Recv 显式传消息 |       **直接读写**共享变量        |
| 启动方式 | 通常由 mpiexec/mpirun 启动多个进程 | 程序自己用 pthread_create 创建线程 |
| 常见风险 |       通信、死锁、消息匹配错误        |      竞争条件、临界区、数据不一致       |
|      |                           |                           |
正因为是多线程，所以**Pthreads可以单机器执行，不再需要machinefile文件**

## 1. Introduction
### 1.1 进程和线程

**经典定义：进程是程序运行的一个实例，一个进程可以拥有多个线程**

	进程：Chrome 浏览器
	线程1：负责界面
	线程2：负责网络请求
	线程3：负责渲染网页
	线程4：负责播放视频

### 1.2 Pthreads
Pthreads是一个**多线程**API，是一个可以和 C/C++ 程序链接的库
- 这一点和MPI是一样的
```

MPI：
#include <mpi.h>
mpicc xxx.c

Pthreads：
#include <pthread.h>
gcc xxx.c -lpthread

```
### 1.3 Pthreads的 Hello World 程序

```cpp
#include <stdio.h>
#include <stdlib.h>
#include <pthread.h>

int thread_count;  // 全局变量，所有线程都能访问

void* Hello(void* rank) {
    long my_rank = (long) rank;
    printf("Hello from thread %ld of %d\n", my_rank, thread_count);
    return NULL;
}

int main(int argc, char* argv[]) {
    long thread;
    pthread_t* thread_handles;

    thread_count = atoi(argv[1]);

    thread_handles = (pthread_t*)malloc(thread_count * sizeof(pthread_t));

    for (thread = 0; thread < thread_count; thread++)
        pthread_create(&thread_handles[thread], NULL, Hello, (void*) thread);

    printf("Hello from the main thread\n");

    for (thread = 0; thread < thread_count; thread++)
        pthread_join(thread_handles[thread], NULL);

    free(thread_handles);
    return 0;
}
```

#### **骨架分析**
##### 1. main
**main 本身也是一个线程**，通常叫主线程

##### 2. pthread_t
**pthread_t**：线程的身份证 / **线程句柄**，类似MPI里的rank
- 创建线程后，系统会把这个线程的信息记录到对应的 `pthread_t` 对象里
- pthread_t thread_handles[4]：准备4个线程身份槽位
##### 3. pthread_create
**pthread_create**(
    &thread_handles[thread],  // 1. 存放新线程身份
    NULL,                     // 2. 线程属性，暂时不用
    Hello,                    // 3. 线程要执行的函数
    (void*) thread             // 4. 传给线程函数的参数
);
- 创建一个新的线程
- ==**线程身份信息存到 thread_handles[thread] 里**==
- 执行Hello函数
- thread 这个**编号**传给它

> MPI 进程通常由脚本启动，一开始就存在，通过 MPI_Comm_rank 得到自己的 rank
> Pthreads 线程由可执行程序本身启动，手动传入 rank


##### 4. 线程函数
==**Pthread要求线程函数的固定形式：**==
`void* thread_function(void* args_p);` 
- 参数类型：void*
- 返回类型：void*

**void * “万能指针”**，**可以被强制转换为任意指针类型**
—— 既可以是整数编号，也可以传一个结构体指针
- 传编号：
	1. `pthread_create(..., Hello, (void*) thread);`
	2. 线程内部再转回来 `long my_rank = (long) rank;`

```c
void* Thread_work(void* rank) {
    long my_rank = (long) rank;

    // 每个线程要执行的任务

    return NULL;
}
```
##### 5. pthread_join：停止线程
`pthread_join(thread_handles[thread], NULL);`：**主线程等待这个子线程执行完**

如果没有 `pthread_join`，主线程可能提前结束，整个进程退出，**子线程还没来得及运行完就被杀掉**

##### 6. 全局变量
**这是和MPI最重要的区别：**
- MPI：每个进程有自己的 thread_count 副本
- Pthreads：全局变量所有线程都能访问，看到的是同一个 thread_count
> 如果多个线程同时修改同一个变量，就可能出问题
##### 7. 经典骨架
**所以Pthreads的main函数经典骨架：**

1. 从命令行参数读取线程数 **thread_count**
2. 分配线程句柄数组 thread_handles
3. **单独编写线程函数** `void* function(void * rank)`
4. 循环`pthread_create`创建线程并执行函数
5. 主线程自己的工作，可有可无
6. 循环`pthread_join`等待所有线程结束
7. 释放资源

```cpp
int main(int argc, char *argv[])
{
    long thread;
    double start, finish, elapsed;
    thread_count = atoi(argv[1]);
    pthread_t *thread_handles = (pthread_t *)malloc(thread_count * sizeof(pthread_t));
    start = clock();
    for (thread = 0; thread < thread_count; thread++)
        pthread_create(&thread_handles[thread], NULL, Pth_mat_vect, (void *)thread);
    for (thread = 0; thread < thread_count; thread++)
        pthread_join(thread_handles[thread], NULL);
    finish = clock();
    elapsed = (finish - start) / CLOCKS_PER_SEC;
    printf("Elapsed time = %f seconds\n", elapsed);
    free(thread_handles);
    return 0;
}
```

## 2. 经典例子1：矩阵乘法

MPI的分布式内存思路：不同进程都有独立的数据，广播B数组，各自计算后gather

### 2.1 Pthreads是如何划分的呢？
分块思想一致，不同在**直接定义全局变量**，所有线程都能直接访问，不再需要通信

这就是 Pthreads 中最理想的情况：
- **共享读可以并行，不同位置的写也可以并行；真正危险的是多个线程同时写同一个共享变量**
```c
int local_m = m / thread_count;
int my_first_row = my_rank * local_m;
int my_last_row = (my_rank + 1) * local_m - 1;
```

## 3. 经典例子2:估算π

串行算法 -- 级数估算：π / 4 = 1 - 1/3 + 1/5 - 1/7 + 1/9 - ...

![[Pasted image 20260426210707.png]]

线程函数：多个线程各自负责一段i，然后**一起把结果加到全局变量 sum 里面**

‼️ ==**涉及到共享变量的写「临界区」必然可能导致混乱**==

同理，sum操作并非原语，会导致==**竞争条件**==

	第 1 步：从内存读取 sum
	第 2 步：计算 sum + 当前项
	第 3 步：把新值写回 sum

在 `-O3` 下，**编译器可能把它优化成类似**：

	double temp = sum;  
	  
	for (...) {  
	    temp += factor / (2 * i + 1);  
	}  
	  
	sum = temp;

于是每个线程像是在自己寄存器里算一段，最后再把自己的结果写回 `sum`，越往后的线程结果越接近0

```
$ ./pi 4 1000000000
Estimate of pi     = 0.000000000333333
Elapsed time = 7.749645 seconds
Math library of pi = 3.141592653589793
```

### 3.1 第一种解决方案：忙等待

忙等待：一个线程反复检查某个条件「忙」，条件满足前一直「等待」
- 典型代码：`while (flag != my_rank);`
```cpp
while (flag != my_rank);

sum += factor / (2 * i + 1);

flag = (flag + 1) % thread_count;
```

- 缺点：每个线程依次执行，多数线程只是在空转抢 CPU，性能退化到串行，甚至比串行更慢

### 3.2 缓解：**先局部求和，再全局合并**
每个线程算出自己的 `my_sum`，互不影响
只有最后sum += my_sum;才需要保护


## 4. 互斥锁

和操作系统一样，引入互斥锁 Mutex 来解决忙等待的资源浪费
- 等待锁的进程进入阻塞队列，等待CPU

>[!note]+ 为什么忙等待，线程增加时占用时间增加，而互斥锁不会？
>
> 答：忙等待线程一直处于 **READY/RUNNING** 状态，调度器会反复给它 CPU 时间片；而真正要修改 `flag` 的线程也要靠调度器获得 CPU 才能执行
>
>	如果线程数远大于 CPU 核心数有没有可能一直不调度？
> - 不会，时间片到了以后，调度器会把 T0 切到最后，让 T1 运行 -> **OS！！！**



**Pthreads 使用互斥锁通常有四步：**

1. **声明**一把锁「全局变量」：`pthread_mutex_t mutex;`
2. **初始化**锁「主进程执行」：`pthread_mutex_init(&mutex, NULL);`
3. **上锁**进入临界区「线程函数」：`pthread_mutex_lock(&mutex);`
4. **释放锁**离开临界区：`pthread_mutex_unlock(&mutex);`
5. **销毁锁**「主进程执行」：`pthread_mutex_destroy(&mutex);`

**Mutex锁的是操作，而非变量**
- 临界区越短越好，尽量降低上锁对并行的影响

## 5. 生产者-消费者问题：**互斥 + 同步**

有些问题不只是“互斥”，还需要控制：

1. 谁先执行？-- 有些场景中，我们需要控制**线程访问临界区的顺序**
2. 有没有资源？  
3. 缓冲区满了吗？  
4. 缓冲区空了吗？

这就引出 **==信号量 semaphore==**

### 5.1 mutex 和 semaphore 的核心区别
非常重要的类比：
- mutex：一把钥匙  
	厕所只有一间，一次只能进一个人
- semaphore：一**堆**许可证
	停车场有10个车位，最多停10台车

所以
- mutex：关注谁进入临界区，解决的是一次只能有一个进程改变共享变量
- semaphore：关注资源多少、谁该等谁，解决的是缓冲区空/满，顺序同步

**重点：mutex可以看作一种特殊的信号量** **「初值为1」**

	sem_init(&count_sem, 0, 1);
	///////////////////////////
	sem_wait(&count_sem);
	/* 修改 counter */
	sem_post(&count_sem);

等价于：

	pthread_mutex_lock(&mutex);
	/* 修改 counter */
	pthread_mutex_unlock(&mutex);
### 5.2 信号量操作

本质整数计数器 + 两个原子操作

	sem_wait(&sem); 申请一个资源  
	sem_post(&sem); 释放一个资源

### 5.3 信号量的 API

对应头文件：`#include <semaphore.h>`
> 信号量不属于 Pthreads 线程库的一部分，需要额外包含 `semaphore.h`

常用API：
1. 声明：`sem_t sem;`
2. 初始化：`sem_init(&sem, 0, 初始值);`
3. 等待 / 申请：`sem_wait(&sem);`
4. 释放 / 发信号：`sem_post(&sem);`
5. 销毁：`sem_destroy(&sem);`

### 5.4 例子：实现线程间通信
每个线程给下一个线程发送消息
通信方式：修改和读取共享数组 Message
1. 先给别人发消息 `message[dest] = my_msg`
   >写的位置不同，不需要互斥
2. 读取别人的消息 `message[my_rank]`

```cpp
long dest = (my_rank + 1) % thread_count;
long source = (my_rank + thread_count - 1) % thread_count;

char* my_msg = malloc(MSG_MAX * sizeof(char));
sprintf(my_msg, "Hello to %ld from %ld", dest, my_rank);

messages[dest] = my_msg;

if (messages[my_rank] != NULL)
    printf("Thread %ld > %s\n", my_rank, messages[my_rank]);
else
    printf("Thread %ld > No message from %ld\n", my_rank, source);
```

```plain
$ ./message  10
Thread 0 > No message from 9
Thread 2 > No message from 1
Thread 1 > Hello to 1 from 0
Thread 3 > Hello to 3 from 2
Thread 4 > Hello to 4 from 3
Thread 5 > Hello to 5 from 4
Thread 6 > Hello to 6 from 5
Thread 7 > Hello to 7 from 6
Thread 8 > Hello to 8 from 7
Thread 9 > Hello to 9 from 8
```

无信号量：是否能读到取决于对应进程是否在我读取之前完成写入
- **执行顺序出错**
- 无法直接表达：线程 1 必须等线程 0 写完 messages[1] 后，才能读 messages[1]

#### **如何增加信号量？**

定义一个信号量表示 **线程 i 的消息是否已经准备好**
- `sem_t * semaphores`

初始化时全为零：所有进程都还没准备好
- 逐个`sem_init`
```
semaphores = malloc(thread_count * sizeof(sem_t));
for (long i = 0; i < thread_count; i++) {
    sem_init(&semaphores[i], 0, 0);
}
```

当线程 `source` 给线程 `dest` 写完消息后：
- `sem_post(&semaphores[dest]);`

线程 `my_rank` 在读自己的消息前:
- `sem_wait(&semaphores[my_rank]);`

### 生产者消费者模型

什么是生产者消费者模型？
- 生产者生产数据，写入缓冲区
- 消费者取出数据，释放缓冲区

**生产者：**

```c
void* Producer(void* rank) {  
    while (还有数据要生产) {  
        item = produce();  
  
        sem_wait(&empty_slots);  
  
        pthread_mutex_lock(&mutex);  
        buffer[in] = item;  
        in = (in + 1) % N;  
        pthread_mutex_unlock(&mutex);  
  
        sem_post(&full_slots);  
    }  
  
    return NULL;  
}
```

**消费者：**

```c
void* Consumer(void* rank) {  
    while (还要继续消费) {  
        sem_wait(&full_slots);  
  
        pthread_mutex_lock(&mutex);  
        item = buffer[out];  
        out = (out + 1) % N;  
        pthread_mutex_unlock(&mutex);  
  
        sem_post(&empty_slots);  
  
        consume(item);  
    }  
  
    return NULL;  
}
```

>[!warning]+ **危险的点：必须先wait再mutex**
> 因为假设生产者拿到了 mutex，然后发现缓冲区满了，而消费者等锁，形成死锁

## 6.  栅栏 barrier
栅栏 barrier 是一个“**集合点**”：**所有线程都必须到齐，才能一起继续往后走**
**🔆 barrier有固定MPI，但更聚焦在手动实现**
> 效果等同于 MPI_Barrier 线程版

假设有 4 个线程：

	线程0：阶段1 ─── 到达栅栏 ─── 等待 ─── 阶段2  
	线程1：阶段1 ───────── 到达栅栏 ─ 等待 ─ 阶段2  
	线程2：阶段1 ─ 到达栅栏 ───────── 等待 ─ 阶段2  
	线程3：阶段1 ─────── 到达栅栏 ─── 等待 ─ 阶段2

线程 2 最早到，但它不能继续

它必须等：

	线程0 到  
	线程1 到  
	线程3 到

**全部到齐后：所有线程一起进入阶段2**

Barrier保护的是 **程序执行阶段的先后关系**

### 1. 区分MPI_Barrier
**MPI:**

	每个进程算完局部结果
	MPI_Barrier
	然后开始下一轮通信

**Pthreads：依然聚焦在共享内存部分**

	每个线程写完自己的共享数组部分
	barrier
	然后所有线程开始读取完整数组

==**Barrier底层是怎么实现？**== 
### **2. 最简单的 barrier：计数器 + 忙等待**

每个线程到达 "barrier" 时：counter + 1 ，直到 `counter = thread_count`

```c
// mutex保护counter
pthread_mutex_lock(&barrier_mutex);
counter++;
pthread_mutex_unlock(&barrier_mutex);

while (counter < thread_count);
```

不可避免忙等待造成的资源浪费，且只能用一次

**⬇️ 怎么用信号量来改善？**

1. mutex / sem_counter：保护counter
2. sem_barrier：表示阻塞进程的数量，所以设置初始值为0

```cpp
sem_wait(&count_sem);

if (counter == thread_count - 1) {
    counter = 0;
    sem_post(&count_sem);

    for (int i = 0; i < thread_count - 1; i++)
        sem_post(&barrier_sem);
}
else {
    counter++;
    sem_post(&count_sem);
    sem_wait(&barrier_sem);
}
```

- 不是最后一个到的：打卡 -> 睡觉
- 最后一个到：重置打卡，叫醒所有人

>[!danger]+ **为什么这个barrier还是一次性的？**
> 最后一个到达上一轮 barrier 的进程不会执行 `sem_wait(&barrier_sem)`，`sem_post`完就结束了，操作系统不保证马上切换到那 3 个线程，所以他会比其他进程更早进入下一轮
> - **此时如果复用barrier_sem，就会和上一轮的barrier冲突**

### 3. **条件变量**实现barrier

允许线程暂停执行，直到**某个特定事件**或条件发生的机制

> 和信号量有什么差别？

**条件变量常见变量：**

1. pthread_mutex_t mutex：互斥锁
2. **==pthread_cond_t cond_var：**==
3. int counter = 0;

**基本 barrier 思路：**

<font color="#4f6128">pthread_mutex_lock(&mutex);  </font>
  
**counter++;**  
  
if (counter == thread_count) {  
    counter = 0;  
    **pthread_cond_broadcast**(&cond_var);  
}  
else {  
    **pthread_cond_wait**(&cond_var, &mutex);  
}  
  
<font color="#4f6128">pthread_mutex_unlock(&mutex);</font>

#### **特殊之处：pthread_cond_wait**
它并不是简单地阻塞线程，而是会**三个原子操作**
1. **==释放mutex==**
   >为什么要释放?
   >- 因为`pthread_cond_wait`要求调用它的时候，**==线程必须已经持有 mutex==**，必须释放以避免死锁
2. 阻塞当前线程，等待被`signal/broadcast`唤醒
---
3. **==满足条件被唤醒==**
---
4. **重新==竞争==mutex**，从`pthread_cond_wait`返回

>[!fail]+ 为什么条件变量必须搭配mutex使用？
>条件来自于共享变量，而这些变量必须被保护！

#### **条件变量两种唤醒方式：signal 和 broadcase**

`pthread_cond_signal(&cond_var)`：唤醒一个等待进程
`pthread_cond_broadcast(&cond_var)`：唤醒所有等待进程

#### **更严谨的条件barrier**

标准写法不是 `if(!condition) {pthread_cond_wait}`，而是：
```c
while(!condition)
	pthread_cond_wait(&cond,&mutex);
```

`while` 里的==**条件不是“退出 wait 的条件”，而是“继续等待的条件”**==

>[!bug]+ 为什么不能写 `while(count < p)`?
>原因在于count = 0 
>1. 如果count是一次性的，不需要count = 0，那么`while(count < p)`完全没问题
>2. 问题就是加上 count = 0 想让barrier可复用，count<p会导致线程死锁，所以必须去掉，那这样就会导致 -- 如果虚假唤醒，这个程序无法保证正确
>3. 要想复用就得使用 phase 变量
> 


`pthread_cond_wait` 返回有三种情况：
1. 真正被signal / broadcast 唤醒：条件可能发生了变化，**不保证当前线程拿到锁时条件仍然成立**
2. ==**虚假唤醒 spurious wakeup**==：**奇异现象**
    >线程可能在没有人真正满足条件、甚至没有对应 signal/broadcast 的情况下，从 `pthread_cond_wait` 返回
3. 被唤醒时条件满足，拿到锁后条件又被改变了
##### 例子：多个线程被唤醒后会竞争

前提：如果只要有数据，生产者就broadcast所有进程

假设多个消费者都在等待：

```
while (count == 0)  
    pthread_cond_wait(&not_empty, &mutex);
```

**结果**：拿到数据的线程正常执行，没有数据的线程拿到锁后 「如果没有循环检查条件」，拿到空数据报错
- **条件被其他进程修改了**

#### **可复用Barrier**
增加
1. 一个共享变量 phase ： 当前的第几轮 barrier
2. 条件变量判断：`while(my_phase == phase)`检查当前在第几轮 barrier，最后一个进程执行完再去到下一轮 `phase++`
## 7. 读写锁
### **7.1 读写锁经典例子：共享链表 list**

**三个操作：**

```
Member(value)：查找 value 是否在链表中
Insert(value)：插入 value
Delete(value)：删除 value
```

**要求：**
1. 多个线程都能读
2. 读写互斥：只要有一个线程要写，其他线程都不能读
3. 写写互斥：同一时间只能有一个线程执行写

<u>普通mutex</u>也能解决，两种方案：
1. 对整个list上锁
2. 对每个node上锁

```c
pthread_mutex_lock(&mutex);  
  
Member(value);  
// 或 Insert(value)  
// 或 Delete(value)  
  
pthread_mutex_unlock(&mutex);
```

虽然能解决读写互斥和写写互斥
——但是同时多个链表**读并行**降为串行执行，效率低下
- **复杂度较低，简单稳定，适合写操作较多，逻辑简单**
### **7.2 读写锁**

**读锁：read lock，允许多个线程同时持有读锁**
**写锁：write lock，只允许一个线程持有写锁**
- **复杂度较高，需要额外管理成本，适合读操作远多于写操作**

![[Pasted image 20260506163458.png]]

### **7.3 Pthreads 中的读写锁 API**

Pthreads 里读写锁类型是：

```
pthread_rwlock_t rwlock;
```

**初始化**：

```
pthread_rwlock_init(&rwlock, NULL);
```

**加读锁**：

```
pthread_rwlock_rdlock(&rwlock);
```

**加写锁**：

```
pthread_rwlock_wrlock(&rwlock);
```

**解锁**：

```
pthread_rwlock_unlock(&rwlock);
```

**销毁**：

```
pthread_rwlock_destroy(&rwlock);
```

**所以结构是**：

```
pthread_rwlock_t rwlock;

int main() {
    pthread_rwlock_init(&rwlock, NULL);

    // 创建线程
    // join 线程

    pthread_rwlock_destroy(&rwlock);
}
```

### **7.4 读写锁的算法缺陷**
writer starvation，写者饥饿：**如果读者源源不断到来，写者可能一直拿不到写锁**

> 提高了读读并行性，但也带来了公平性和调度策略问题
## 8. Cache & 共享内存

### 8.1 多线程🉐缓存不一致问题

回顾分布式内存里每个CPU都有其独立的Cache，所以会涉及缓存不一致的问题

- 共享内存也有有这个问题吗？

>**区别：**
>- **共享内存**：多个线程之间访问对象在同一个物理地址
>- **Cache**：一个CPU多个核心多个Cache，缓存**同一个RAM**的数据
	Core0 ---- L1/L2 Cache0
	Core1 ---- L1/L2 Cache1
	Core2 ---- L1/L2 Cache2
	Core3 ---- L1/L2 Cache3
	            ↓
	         Shared L3
	            ↓
	           RAM

所以不同CPU核心都有自己的Cache，当多个核心同时读写共享数据时，就会出现缓存一致性问题

- **缓存一致性协议**
	- 多核间通过缓存一致性协议保证缓存一致
	- 当一个核心修改缓存行中的任意一个变量，会将**该行标记为Modified（脏）**，并向所有其他核心发送无效化（Invalidate）消息，强制它们的副本失效

### 8.2 缓存 - 性能 例子：矩阵-向量乘法
**矩阵-向量乘法中，不同数据布局（矩阵形状）对并行性能和缓存行为的影响**

三个矩阵维度：**总计算量差不多**

| **维度**        | **含义**         |
| ------------- | -------------- |
| 8,000,000 × 8 | 极高瘦矩阵（很多行，很少列） |
| 8,000 × 8,000 | 方阵             |
| 8 × 8,000,000 | 极宽矩阵（很少行，很多列）  |

**但性能完全不同，为什么？**
- 为什么M=8时间不会减少，反而会增加？
![[Pasted image 20260508122653.png]]
矩阵乘法循环计算 `y[i] += A[i][j] * x[j];`，==**反复读取 x[j]**==
真正关键的是 x 向量能不能留在 cache 中

#### 1. 第一种：8,000,000 × 8
x 极小完全驻留在 cache -> 每次计算一行  都重复使用 cache 中的 x
#### 2. 第二种：8000 × 8000
x 长度 = 8000，8000 × 8B(double) ≈ 64KB，开始逼近甚至超过：L1 cache
但仍可能部分留在：L2/L3 cache
**因此：缓存局部性还不错**
#### 3. 第三种：8 × 8,000,000
x 长度 = 800万，8000000 × 8B ≈ 64MB，远远超过 L3 Cache，所以每次做乘法，都要从RAM不断取 x[j]

同时线程越多效率暴跌
- 多个线程同时疯狂读取巨大 x 向量，共享内存带宽被迅速打满，**CPU核心忙于等待内存**
### 8.3 真共享 True Sharing vs 伪共享 False Sharing

**真共享**：两个Cache缓存的是==**同一个**==共享变量
- 解决方式：**mutex**

⬇️

**==伪==共享：多个线程修改的是不同变量「==程序逻辑不共享==」，但是因为这些变量刚好在一个Cache line里面「==硬件逻辑共享==」，导致硬件把它们当作用一个数据反复同步**

比如：

```
double x[8];
```

假设 `x[0]` 到 `x[7]` 正好在同一个 64 字节缓存行里。

线程 0 修改：

```
x[0]
```

线程 1 修改：

```
x[1]
```

从程序逻辑看：

```
x[0] 和 x[1] 是不同变量没有数据竞争
```

但从硬件缓存角度看：

```
x[0] 和 x[1] 在同一个 cache line
```

于是 Core 0 修改 `x[0]` 后，整个缓存行被标记为 modified，Core 1 缓存中的同一行失效

Core 1 修改 `x[1]` 后，Core 0 的缓存行又失效

**于是缓存行在多个核心之间来回“乒乓”**

### 8.4 伪共享例子：全局求和
全局求和的思路是每个线程计算自己的my_sum，然后再上锁加到共享的sum里面

n = 1000000000，Cache = 64字节，对应8个double
- 问题在于Cache line的大小可能大于每个线程分配的数据量，导致伪共享

强制隔开 **my_rank * 10** 时间会减少很多

## 9. 线程安全 Thread Safety

### 9.1 什么是线程安全

如果一段代码能够被多个线程同时执行，并且不会破坏程序正确性，那么这段代码就是线程安全的

线程安全关注的是：

> 多个线程同时调用同一段代码时，程序状态是否仍然正确

需要注意：

- 线程安全不等于性能高；
- 线程安全不等于没有锁；
- **线程安全只表示并发执行时不会破坏正确性**

---

### 9.2 线程安全问题的本质

线程安全问题的本质是：

> 多个线程访问共享可变状态

其中：

- 共享：多个线程都能访问
- 可变：该状态可能被修改

常见的共享可变状态包括：

- 全局变量；
- ==**`static` 局部变量**==；
- 堆上共享对象；
- 共享缓冲区；
- **随机数生成器内部的 seed**；
- 某些库函数内部保存的状态。

如果多个线程同时访问这些状态，并且至少有一个线程会修改它，就可能产生竞态条件或线程安全问题

>线程安全问题 ⊃ 竞态条件
---

### 9.3 为什么 static 变量容易导致线程不安全

`static` 局部变量虽然写在函数内部，但它不是普通局部变量

普通局部变量：

```c
void f() {
    int x = 0;
}
```

每个线程调用函数时，都会在自己的栈上拥有一份 `x`

而 `static` 局部变量：

```c
void f() {  tatic int x = 0;}
```

整个程序只有一份 `x`，所有线程调用这个函数时共享同一个 `x`

因此，如果多个线程同时读写这个 `static` 变量，就可能发生数据覆盖或竞态条件

---

### 9.4 static buffer 的典型问题

考虑下面这个函数：

```c
char* Get_msg(int rank) {
    static char buf[100];
    sprintf(buf, "Hello from thread %d", rank);
    return buf;
}
```

**这个函数返回的是 `static buf` 的地址**

在单线程中，这通常没问题。

但在多线程中，多个线程会共享同一个 `buf`

可能的执行顺序如下：

```
线程0 调用 Get_msg(0)
    buf = "Hello from thread 0"
    返回 buf 地址

线程0 暂时还没打印，被操作系统切走

线程1 调用 Get_msg(1)
    buf = "Hello from thread 1"
    返回同一个 buf 地址

线程0 恢复执行并打印 msg
    但 msg 指向的 buf 已经被线程1覆盖
```

因此，线程0可能输出：

```
Thread 0 got message: Hello from thread 1
```

这说明：

> 返回内部 static buffer 的函数通常不是线程安全的

原因不是指针本身错误，而是多个线程拿到的指针都指向同一个共享缓冲区

---

### 9.5 strtok 为什么不是线程安全的

`strtok` 用于字符串分词

典型用法：

```c
char s[] = "a,b,c";

char* token = strtok(s, ",");
token = strtok(NULL, ",");
token = strtok(NULL, ",");
```

问题在于：

> `strtok` 内部会保存上一次分词的位置

它通常通过内部静态状态记录“下一次应该从哪里继续切分”

在单线程中，这样可以正常工作

但在多线程中：

```
线程0 正在对字符串 A 分词
线程1 同时对字符串 B 分词
```

线程1 的调用可能覆盖线程0 内部保存的分词位置，导致线程0 后续分词结果错误。

因此，`strtok` 不是线程安全的

线程安全替代方案通常是：

```
strtok_r
```

它要求调用者自己传入保存状态的指针，从而避免多个线程共享同一个内部状态。

---

### 9.6 rand 和随机数生成器的线程安全问题

很多随机数函数内部会维护一个全局或静态 seed。

例如可以简化理解为：

```c
static unsigned long seed;

int rand() {
    seed = seed * A + B;
    return seed;
}
```

如果多个线程同时调用 `rand()`，它们会同时修改同一个 `seed`，从而产生数据竞争

解决方法包括：

- 每个线程维护自己的 seed；
- 使用线程安全版本的随机数函数；
- 使用 mutex 保护随机数生成器；
- 使用线程局部存储 TLS 
- ...

---

### 9.7 线程安全与可重入 Reentrant

线程安全和可重入相关，但不完全相同

线程安全：

> 多个线程同时调用同一段代码不会出错。

可重入：

> 一个函数执行到一半时，即使被再次进入，也不会破坏正确性。

**通常来说，可重入函数更严格**

可重入函数一般要求：

- 不使用全局变量；
- 不使用 static 可变变量；
- 不返回内部共享缓冲区；
- 只依赖参数和局部变量；
- 不修改共享状态，或者共享状态由调用者显式管理。

例如：

```c
int square(int x) {
    return x * x;
}
```

**自定义函数**只使用参数和局部计算结果，因此天然线程安全，也天然可重入。

---

### 9.8 判断函数是否可能线程不安全

看到以下特征时，需要警惕线程安全问题：

#### 1. 使用 static 局部变量

```c
static int counter;
```

多个线程共享同一个 `counter`，如果同时修改，就可能发生竞态条件

#### 2. 使用全局变量

```c
int global_sum;
```

多个线程同时读写全局变量时，需要同步保护

#### 3. 返回内部缓冲区指针

```c
char* get_buffer() {
    static char buf[100];
    return buf;
}
```

多个线程拿到的都是同一个 `buf`，内容可能互相覆盖

#### 4. 函数内部维护状态

例如：

- `strtok` 内部保存分词位置；
- 随机数函数内部维护 seed；
- 某些时间转换函数返回内部静态结构；
- 某些库函数使用内部缓存

这些函数在多线程环境中可能不是线程安全的

---

### 9.9 如何让代码线程安全

常见方法有以下几种。

#### 方法 1：避免共享状态

最好的方式是让函数只使用参数和局部变量。

```c
int Add(int a, int b) {
    return a + b;
}
```

这种函数天然线程安全。

#### 方法 2：使用 mutex 保护共享状态

如果必须访问共享变量，可以使用互斥锁保护临界区。

```c
pthread_mutex_lock(&mutex);

/* 访问或修改共享状态 */

pthread_mutex_unlock(&mutex);
```

这种方式可以保证正确性，但可能降低并行性能
