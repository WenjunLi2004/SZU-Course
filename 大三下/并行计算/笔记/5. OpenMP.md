# 1. OpenMP如何并行化规则循环
## 1. OpenMP有什么不同？
**Pthreads** : 
>你亲自招聘工人、分配编号、告诉每个人干什么、最后一个个等他们下班，即就是要自己写：

```c
pthread_create(...)
pthread_join(...)
pthread_mutex_lock(...)
pthread_mutex_unlock(...)
```

OpenMP更像是：
>你在代码旁边贴一张"施工提示牌"，告诉编译器：下面这段代码请帮我并行执行

比如：
```cpp
#pragma omp parallel
{
    printf("hello\n");
}
```

你**没有显式创建线程**，**也没有写 join**，但 OpenMP 运行时会帮你完成"==**创建线程组、执行并行块、结束后合并回主线程**=="的过程
- ==**增量式并行**==
- 仿佛AI时代的到来😁

和Pthreads一样，OpenMP 是一个**用于共享内存并行编程的 API**

> OpenMP是比 Pthreads 更高级的的编程方式，主要体现在对于**线程管理细节的封装**

## 2. 第一个 OpenMP 程序：Hello World

```c
#include <stdio.h>
#include <stdlib.h>
#include <omp.h>

void Hello(void);

int main(int argc, char* argv[]) {
    int thread_count = atoi(argv[1]);

    #pragma omp parallel num_threads(thread_count)
    Hello();

    return 0;
}

void Hello(void) {
    int my_rank = omp_get_thread_num();
    int thread_count = omp_get_num_threads();

    printf("Hello from thread %d of %d\n", my_rank, thread_count);
}
```

`#pragma` 称为一种**特殊的预处理器指令**
`#pragma omp parallel num_threads(thread_count)` 表示创建一个 **==OpenMP 并行区域==**，并指定希望使用 `thread_count` 个线程

- NOTE：如果编译器不支持对应 pragma，可能会忽略它

#### 例子

#pragma omp parallel num_threads(4) 「==**后面不加分号**==」
- OpenMP 组织出一个 **4 个线程的线程组**，这 4 个线程都会执行 ==**结构化代码块**==
- 初始线程叫主线程，额外创建的线程叫从线程
- **4 个线程 = 1 个主线程 + 3 个新建线程**
- 并行区域结束后，新建线程会结束或回到 OpenMP 运行时线程池中；**主线程继续执行并行区域后面的代码**

```c
#pragma omp parallel num_threads(8)
{
    Hello();
}

printf("after\n");
```
### 和 Pthreads Hello World 对比

```cpp
for (thread = 0; thread < thread_count; thread++)
    pthread_create(&thread_handles[thread], NULL, Hello, (void*)thread);

for (thread = 0; thread < thread_count; thread++)
    pthread_join(thread_handles[thread], NULL);
```

OpenMP只需要在串行程序的基础上加上一句**预处理语句**

**所以它把这几件事隐藏起来了：**
1. **创建线程**
2. **给线程分配编号**
3. **所有线程执行同一段代码**
4. **并行区域结束时自动等待所有线程结束**

> **但是线程函数内部的划分还是要自己做**
> 但注意：OpenMP 后面还有更高级的写法 `parallel for`，这时候**循环迭代的划分可以交给 OpenMP 自动做**，你就不一定要手动算每个线程的起点和终点了

`omp_get_thread_num()` 类似于 Pthreads 里手动传进去的 `rank`

`omp_get_num_threads()` 类似于全局的 `thread_count`


**这就是 OpenMP 的第一个核心模型**：

> **fork-join 模型**：主线程执行到并行区域时分叉出一组线程；并行区域结束时，这组线程汇合回主线程。

`#pragma omp parallel` 是最基本的并行指令，运行后续结构化代码块的线程数量由**运行时系统决定**；
- **这点和Pthreads一样，需要Shell里输入参数**

加上 `num_threads(thread_count)` ：指定**希望使用**的线程数量

### **例子：梯形求和**

```cpp

#pragma omp parallel num_threads(thread_count)
Trap(a, b, n, &global_result);

Trap(...)
{
	int my_rank = omp_get_thread_num();
	int thread_count = omp_get_num_threads();
	
	h = (b - a) / n;
	local_n = n / thread_count;
	
	local_a = a + my_rank * local_n * h;
	local_b = local_a + local_n * h;
}
```

## 3. 变量作用域：shared 和 private

补：pthreads问题解决方法区别，共享内存，互斥，信号量...

**变量的作用域**：在一个并行块中，可以访问该变量的==**线程集合**==
1. **共享作用域 Shared**：能被线程组中所有线程访问的变量
   在并行块之前声明的变量，其默认作用域为共享
2. **私有作用域 Private**：只能被单个线程访问

### 共享变量 & 竞态条件

#### 解决方法1：critical 临界区
```c
#pragma omp critical
global_result += my_result;
```

> critical : 下面这个**结构化代码块**一次只能有一个线程执行
> 等同于 Pthreads里的 互斥锁
> **可以写在线程函数，也可以主函数**

**同理，互斥的部分越少越好**，所以**善用局部结果**

```c
my_result += Local_trap(a, b, n);  
  
#pragma omp critical  
global_result += my_result;
```

#### **比 critical 更简洁的方法——reduction**

对于"全局求和"这种模式，OpenMP 有专门工具：**归约 reduction**

>从数学结果上看，reduction 和"**每个线程算局部和，再进入 critical 加到全局和**"是等价的；
>但==**从执行机制上看，它不是 critical，通常性能更好，也更高级**==

```c
#pragma omp parallel num_threads(thread_count) reduction(+: global_result)
{
    global_result += Local_trap(a, b, n);
}
```

OpenMP 会==**自动**==给每个线程创建一个 `global_result` 的 **==私有副本==**
	
- **规约变量的初始值会根据符号而变化，加是0，乘是1**
	
每个线程只更新自己的副本；并行区域结束时，再把所有副本加起来，写回原来的 `global_result`


**critical**：本质是让线程排队进入某段代码
**reduction**：
	1. **不需要每个线程争同一把锁**：最后会自动合并再赋值
	2. **树形合并**：线程数量越多，reduction 的结构优势越明显
	3. parallel for 里 reduction 更自然

## 4. parallel for —— OpenMP 最常用的并行方式
### 4.1 形象理解
`parallel for` 
1. **分叉一组线程**来执行下面的结构化块
2. **这个结构化块必须是一个 `for` ==循环==**
3. 系统会在线程之间==**分配**==循环迭代，从而实现 `for` 循环并行化



```
#pragma omp parallel for num_threads(4)
for (int i = 0; i < 100; i++) {
    work(i);
}
```

OpenMP 大概会自动分成：**==默认均匀分块==**
```
线程 0：i = 0 ~ 24
线程 1：i = 25 ~ 49
线程 2：i = 50 ~ 74
线程 3：i = 75 ~ 99
```

**不需要自己写**：
```c
int my_rank = omp_get_thread_num();
int locan_n = n / thread_count;
int first = local_n * my_rank;
...
```

### 4.2 简化梯形代码

**串行程序：**
```c
h = (b - a) / n;  
approx = (f(a) + f(b)) / 2.0;  
  
for (i = 1; i <= n - 1; i++) {  
	approx += f(a + i * h);  
}  
  
approx = h * approx;
```

**OpenMP程序：**

```c
#pragma omp parallel for num_threads(thread_count) reduction(+:approx)
for (i = 1; i <= n - 1; i++) {  
	approx += f(a + i * h);  
}
```

> **现在连线程函数都不用写了 😂**

### **4.3 parallel for 的 致命前提！**

每次迭代之间==**必须没有 按顺序执行的数据依赖**==

例子：斐波那契数列：后面的结果依赖前面的结果
```c
fibo[0] = fibo[1] = 1;

#pragma omp parallel for
for (int i = 2; i < n; i++) {
    fibo[i] = fibo[i - 1] + fibo[i - 2];
}
```

### **4.4 经典陷阱**：估算 π 的 `factor = -factor`

**串行代码：**
```c
double factor = 1.0;
double sum = 0.0;

for (int k = 0; k < n; k++) {
    sum += factor / (2 * k + 1);
    factor = -factor;
}
```

如果直接加 ： `#pragma omp parallel for reduction(+:sum)`
OK，自动划分k，然后每个线程也有sum的私有副本

**问题就出在共享变量 factor**
1. 第 `k` 次迭代的 `factor` ==**依赖**==前一次迭代
2. ==**共享**==变量的竞态条件

#### **正确改法：每次迭代自己算出符号**

1. 不要让 `factor` 依赖前一次迭代，而是直接由 `k` 决定
   这样第 `k` 次迭代只依赖自己的 `k`，不依赖前一次迭代
2. 循环体内声明 factor 或者 使用 private(factor)
   `#pragma omp parallel for private(factor)`

>**`private(x)` 只是给每个线程创建一个私有副本，不保证这个副本继承原来 `x` 的值**


```c
double sum = 0.0;

#pragma omp parallel for num_threads(thread_count) reduction(+:sum)
for (int k = 0; k < n; k++) {
    double factor;

    if (k % 2 == 0)
        factor = 1.0;
    else
        factor = -1.0;

    sum += factor / (2 * k + 1);
}
```



### 4.5 parallel for 的合法循环形式

本质：OpenMP 要能在进入循环前，把**循环迭代次数**算清楚，然后**安全切成**几段分给线程

1. 循环变量 `index` 必须是整型或指针类型： `double` 就不行，因为`double`有精度误差
	>
	>循环变量必须是**离散、可数、可预测**的类型
	
2. `start`、`end`、`incr` 在循环执行过程中不能改变：已经划分好了
	
3. **循环变量**只能被 `for` 语句里的增量表达式修改：函数内部不要改

### 4.6 `default(none)`：强迫你把变量作用域说清楚

OpenMP 默认规则是：

```
并行块外声明的变量：默认 shared
并行块内声明的变量：通常 private
```

但这个默认规则有时会害人，**因为你可能忘了某个变量其实被多个线程共享写了**

所以课件引入了：

```
default(none)
```

它的作用是：

> 要求你==**明确写出**==并行区域里用到的**外部变量**到底是 shared、private，还是 reduction

### 4.7 parallel for 和 omp for 的区别

`parallel for`可以理解成两个动作：
1. parallel：==**创建线程组**==  
2. **for：把循环迭代分配给线程组**

**等价于：**
```c
#pragma omg parallel
{
	#pragma omp for
	for()
} 
```

但这两个写法在多层循环或多阶段算法中差别很大！

**具体应用差别在哪？** -> **奇偶移项排序把排序过程分成很多个 phase**
#### 1.  parallel for ：每次都新开一个线程组
```c
for (phase = 0; phase < n; phase++) {
    #pragma omp parallel for num_threads(thread_count)
    for (i = 0; i < n; i++) {
        work(phase, i);
    }
}
```

**缺点**：反复==**创建/唤醒/同步/销毁**==线程组，开销更大

#### 2. omp for：在已有并行区里分配循环

```c
#pragma omp parallel num_threads(thread_count)
{
    for (phase = 0; phase < n; phase++) {
        #pragma omp for
        for (i = 0; i < n; i++) {
            work(phase, i);
        }
    }
}
```

- **只创建一次线程组**，开销更小
##### 既然是**同一批线程**，执行过的内容是否影响后续 phase？

**要看变量类型：**
- **共享变量 shared：会影响「这就是我们想要的！」**
- 私有变量 private：一般不会影响其他线程，但同一线程自己的值可能保留循环结果写入数组：当然会影响，因为排序本来就依赖上一轮结果

**排序问题就是要：**
- **同一个 phase 内：可以 parallel for**  
- **不同 phase 之间：必须==同步==**
  ⬇️ 同步必须保证同一时间进入下一阶段
### 4.8 关键细节：`omp for` 结束默认有隐式 barrier

每个 `#pragma omp for` 结束时，默认会有一个同步点，意思是：

> 所有线程都做完当前 phase 的比较交换后，才能进入下一个 phase

## 5. 循环调度 `schedule`
### 5.0 OpenMP 调度的“开销”

总时间 = 有效计算时间 + ==**调度分配开销**== + 等待/同步开销「==**负载均衡**==」 + 缓存/局部性损失

schedule 解决的问题：**循环迭代如何分配**
- **默认连续块分配**

> 不是所有问题都适合均匀连续分配，比如计算完数这种，**越往后越慢的问题** 
> ==**负载均衡问题**==

`schedule (type, chunksize)` 的不同形式
### 5.1 `schedule(static, chunksize)`

`static` 表示：
> 循环开始前，就把所有迭代分配好

优点：
1. 分配开销小
2. 连续块访问时缓存局部性好

`chunksize` 表示：**连续块分布**

`schedule(static, 4)` ：默认情况 = `chunksize = n / thread_count`

```shell
线程0：0,1,2,3
线程1：4,5,6,7
线程2：8,9,10,11
```

**轮流分配** :  `chunksize = 1`
```shell
线程0：0,3,6,9  
线程1：1,4,7,10  
线程2：2,5,8,11
```

### 5.2 `schedule(dynamic, chunksize)`

`dynamic` 表示：
>不一开始全部分完，而是先发一块；线程做完一块后，再向运行时系统要下一块
>迭代被拆成**若干连续块**
>有点像python的**迭代器**

`schedule(dynamic, 10)`：

```shell
线程0：先拿 10 个迭代
线程1：先拿 10 个迭代
线程2：先拿 10 个迭代
线程3：先拿 10 个迭代

谁先做完，谁再去领下一批
```

### 5.3 `schedule(guided, chunksize)`

`guided` 可以理解成：

> 一开始大块分，**后面逐渐变小块**

这样做的动机是：
1. 前期大块：减少调度开销 
2. 后期小块：改善负载均衡

如果没指定 `chunksize`，块大小会逐步减小到 1
如果指定了 `chunksize`，则递减到该指定值
### 总结

1. **`static`**
提前分好，固定不变**分配方式**  一开始就把迭代块固定分给各线程

**优点**：调度开销最低

**适合场景** ：每次迭代耗时差不多，例如：`csum += a[i];·

**缺点**：负载均衡较差，取决于任务是否均匀，只适用于有规律的不均衡

2. `dynamic`
谁空了谁继续拿去任务池领取下一块

**优点**：负载均衡最好，本质在于它按==**实际完成速度**==继续领取任务

**适合场景** ：**每次迭代耗时不可预测**，例如图算法、不规则搜索、复杂条件分支

**缺点** ：调度开销较高；`chunk` 太小开销大，太大又可能不均衡。

3. `guided`

开始分大块，后面块逐渐变小

**优点** ：兼顾负载均衡和调度开销，通常比 `dynamic,1` 开销低

**适合场景** ：任务不均衡，但不想像 `dynamic` 那样频繁调度

**缺点**  ：策略更复杂；如果前期大块刚好很不均衡，也可能不理想。

# 2. OpenMP 如何处理更复杂的线程协作？
## 6. 显式线程同步

`parallel for` 解决的是“**规则**循环并行”，但**不是所有程序都是简单 for 循环**
- 规则并行 -> **更一般的线程协作**
- 这时候就需要**显式同步**

### **6.1 例子：消费者 - 生产者** 

假设每个线程都有一个“收件箱”

```
线程0：queue[0]
线程1：queue[1]
线程2：queue[2]
线程3：queue[3]
```

如果线程 0 想给线程 2 发消息，它不是直接调用线程 2，而是把消息放进：

```
queue[2]
```

线程 2 想收消息，就从自己的队列`queue[2]`里取出队首消息

这种程序的重点不是“把 for 的 i 分给线程”，而是==**线程之间会通过共享数据结构协作**==
- 共享数组、共享队列、共享计数器...

**它必须解决三个问题**
1. 共享数据结构读写的竞态条件：**互斥**
   >队列操作的一致性：同时读写共享数组 queue
2. 不同阶段之间的依赖关系：**同步**
	>队列初始化 -> 发送消息：有的线程初始化过快会导致发送消息给未初始化队列
3. 什么时候结束：**终止检测**
	>增加一个计数器：检测其他进程发送的信息是否都接收完毕

**具体框架：每个线程既可能是生产者，也可能是消费者**
```c
#pragma omp parallel num_threads(thread_count)
{
    int my_rank = omp_get_thread_num();

    // 1. 每个线程创建自己的消息队列
    queues[my_rank] = Allocate_queue();

    // 2. 等所有线程的队列都创建完
    // 后面才可以互相发消息

    // 3. 每个线程不断发送消息
    // Send_msg(...)

    // 4. 每个线程也尝试接收自己的消息
    // Try_receive(...)

    // 5. 每个线程完成自己的发送任务后，更新完成计数器

    // 6. 只要还有线程没完成，就继续尝试接收剩余消息
}
```

### 6.2 同步：`#pragma omp barrier`

```
#pragma omp parallel num_threads(thread_count)
{
    int my_rank = omp_get_thread_num();

    queues[my_rank] = Allocate_queue();

    #pragma omp barrier

    Send_msg(...);
}
```


### 6.3 互斥：`critical / lock`

`critical`：保护 { } 内的代码块，同一时间只允许一个线程执行，其他线程排队

#### automic ：特殊的critical
`automic`：只能保护由单个C赋值语句构成的临界区
- 编译器针对 一条特殊的 ==**加载‑修改‑存储**== 指令 进行优化
#### Critical
```c
#pragma omp critical
{
    Enqueue(queues[dest], msg);
}	
```

- **性能差**：同一时间只能有一个线程发消息，不允许多个线程并行发消息
##### 实现细节

**Send_msg**

```c
mesg = random();
dest = random() % thread_count;

# pragma omp critical
Enqueue(queue, dest, my_rank, mesg);
```

**Try_receive**

```c
queue_size = enqueued - dequeued;

if (queue_size == 0) return;
else if (queue_size == 1)
# pragma omp critical
    Dequeue(queue, &src, &mesg);
else
    Dequeue(queue, &src, &mesg);

Print_message(src, mesg);
```

**为什么queue size 不使用 结构体的变量？**
- queue size 不是维护一个共享变量，而是通过末指针-头指针计算结果：这样可以少一个临界区，比如入队列不会影响出队列
**为什么线程自身出队列不需要保护 queue size ≧ 2 ？**
- 队头和队尾不是同一个节点，所以两者可以并发执行，==**不一定**==需要保护
  > 前提：Dequeue 每次只处理队头一个元素

**为什么不直接`queue_size = 0`作为结束信号**
- 因为你不知道之后还有没有线程会继续写入？
##### 细节：命名 和 未命名 区别

未命名 `critical` ：本身就只有一个全局入口
命名 `critical` ：每个名字一把锁，不同名字之间可以并行
- critical 也还可以并行加锁的，最主要的缺点名字写死，没有lock这么灵活

#### **更好**的写法：每个队列一把`lock`

```c
omp_set_lock(&locks[dest]);
Enqueue(queues[dest], msg);
omp_unset_lock(&locks[dest]);
```

- 每个线程各自初始化一个锁，所以它允许线程之间并行持有不同锁
	>线程0 操作 queue[2]  
	>线程1 操作 queue[3]
- **只有当两个线程都想持有同一把锁时，才需要互斥**

OpenMP 简单锁的常用 API：

**锁类型**：`omp_lock_t`

**初始化 -> 销毁锁**：
```c
for (int i = 0; i < thread_count; i++) {
    omp_init_lock(&locks[i]);
}

...

for (int i = 0; i < thread_count; i++) {
    omp_destroy_lock(&locks[i]);
}
```

**加锁**： `omp_set_lock(&locks[dest])`
**解锁**：`omp_unset_lock(&locks[dest])`


### 6.4 终止检测：done_count
**表示：已经完成发送任务的线程数量**
- 每个进程发完之后执行 `done_count++`


终止 == `done_count == thread_count` & 我的消息队列空了

这时候就适合用 `atomic` 来互斥自增 done_count
```c
#pragma omp atomic  
done_count++;
```

#### 为什么不用`reduction`

并行运行过程中，其他线程要能==**观察**== done_count 的变化「身份不是作为一个私有副本」，因此更适合用 `atomic` 更新，而不是 reduction

## 9. 任务并行 task
有些任务不是一开始就全部列好的，而是**在运行过程中不断生成**
- **递归**：快速排序，树遍历，Fibonacci
- **==动态==生成**子任务
- **循环次数未知的问题**

**task**：
- 当前线程发现一个新任务，就把它丢进任务池 
- 哪个线程空闲了，就去任务池里拿任务做
### 1. 最小例子
```c
#pragma omp parallel num_threads(4)
{
    #pragma omp single
    {
        #pragma omp task
        {
            printf("任务1由线程 %d 执行\n", omp_get_thread_num());
        }

        #pragma omp task
        {
            printf("任务2由线程 %d 执行\n", omp_get_thread_num());
        }
    }
}
```

**parallel**：  
>创建线程组，也就是线程池
  
**single**：  
>只让一个线程创建任务，避免 4 个线程重复创建同样的任务
- 只让一个线程生成==**最初的任务树**==，避免所有线程重复调用
  
**task**：  
>把下面这段代码封装成一个可调度任务
- 把递归产生的子问题交给线程池调度

### 2. taskwait
如果一个任务创建了两个子任务 e.g. `fib(n-1)` and `fib(n-2)`
	单个任务不能马上返回结果，需要等待

**taskwait**：**==等==** 直接创建的子任务都完成后，再继续往下执行

**重点**：==**任务依赖树**==，通过`taskwait`保证父任务等子任务完成

```c
int fib(int n) {
    int i = 0;
    int j = 0;

    if (n < 2)
        return n;

    #pragma omp task shared(i) if (n > 20)
    i = fib(n - 1);

    #pragma omp task shared(j) if (n > 20)
    j = fib(n - 2);

    #pragma omp taskwait

    return i + j;
}
```

### 3. 为什么 task 能表达递归？

`task` 不是把“每次函数调用”自动变成任务，而是程序员在递归函数里用 `#pragma omp task` 明确告诉 OpenMP：

**下面这段代码可以作为一个任务，放到任务池里，交给线程池执行**

比如 Fibo 的逻辑是：

**fib(n)**
├── **task 1**: 计算 fib(n-1)，结果写到 i
└── **task 2**: 计算 fib(n-2)，结果写到 j

**taskwait**：等 i 和 j 都算完
**return i + j**

**本质：递归天然会产生“子问题”；`task` 把这些子问题包装成可调度任务**

### 4. if(n > 20)
非常重要的性能优化！

当递归到最深处时，如果每一次调用都创建task -> 指数级爆炸

```c
#pragma omp task shared(i) if (n > 20)
i = fib(n - 1);
```

如果 n > 20，就创建新 task
如果 n <= 20，就不要创建 task，直接在当前线程里普通递归计算
-  Balance **创建开销** and **计算开销**

### 5. 是否只有4个线程去执行递归？
==**物理执行者仍然只有 4 个线程，但是 task 数量多得多**==

问题在于 OpenMP `task` 把“线程”和“任务”分开了
- 线程：真正干活的人
- 任务：要做的工作单元，数量可以很多很多
- 调度：OpenMP runtime 把这些 task 分配给这 4 个线程执行

**关键问题：到底是怎么调度的？**

#### **在我愚蠢的大脑里**：
```
线程0 执行 fib(30)
    创建 fib(29), fib(28)
    然后 taskwait 等

线程1 执行 fib(29)
    创建 fib(28), fib(27)
    然后 taskwait 等

线程2 执行 fib(28)
    创建 fib(27), fib(26)
    然后 taskwait 等

线程3 执行 fib(27)
    创建 fib(26), fib(25)
    然后 taskwait 等

所有线程都在等，那谁来继续算 fib(26), fib(25)...？
```

#### 实际模型

OpenMP task 的关键规则：

> **`taskwait` 是等待点，也是任务调度点
> 线程在这里可以==暂时放下==当前父 task，转去执行别的 ready task**

**真实模型更像**：**父 task 在等，但线程不一定闲着**
```shell
线程执行父 task
遇到 taskwait
发现自己要等子 task
于是：先去任务池里拿别的 task 做
做完一些子 task 后
再回来继续父 task
```

##### 小规模 fib(4) 梳理一遍

递归🌲：
fib(4)  
├── fib(3)  
│ ├── fib(2)  
│ │ ├── fib(1)  
│ │ └── fib(0)  
│ └── fib(1)  
└── fib(2)  
├── fib(1)  
└── fib(0)

1. parallel 创建 2个线程
	- 线程池T0，T1 -> `#pragma omp single`
	- 然后假如 T0 抢到了 `single`，于是 T0 开始执行 `fib(4)`
	- T1：空闲，等任务
	
2. T0 在 fib(4) 里面**创建两个 task**，任务池变成 {A,B}
	- task A : `i = fib(3)`
	- task B : `j = fib(2)`
	- 然后 T0 遇到`taskwait`，要等A和B做完，既然现在没做完「**T0变空闲**」，那我自己也去任务池里拿一个任务做
	- 可能发生：
		1. **T0 去执行 B = fib(2)**
		2. **T1 去执行 A = fib(3)**

3. 关键：T1 执行 fib(3) 时又创建新 task
	- task A1 : `i = fib(2)`
	- task A2 : `j = fib(1)`
	- T1 遇到`taskwait`，又得等，**T1变空闲**

==**关键理解**：**线程 在 taskwait 处不是完全卡死，它可以进入调度，继续帮忙做任务**==

##### 线程去执行子任务了，那“谁”在等待子任务
**父 task 的状态挂起**
**OpenMP runtime** 负责记录Task的状态
- 不需要一个线程专门站在那里等

## 10. 归并

*归并也能并行？*

**串行归并算法：双指针遍历 + 比较->复制**
- **特点**：`c[k]` 本身不一定依赖 `c[k-1]` 的值，但要知道 `c[k]` 应该放谁，必须知道前面已经从 `a` 取走了多少个、从 `b` 取走了多少个

### 1. 并行归并思路：先切边界，再各自归并

假设有两个有序数组：
```v
a: 1 3 5 7 9 10 13 15 17 19 20 23 25 27 29
b: 2 4 6 8 11 12 14 16 18 21 22 24 26 28 30
```

假设 `p = 3` 个线程

并行思路：
```v
先把 a 均匀切成 3 段：

a[0..4]   = 1 3 5 7 9
a[5..9]   = 10 13 15 17 19
a[10..14] = 20 23 25 27 29
```

**也就是：**

```c
u[0] = 0;
u[1] = 5;
u[2] = 10;
u[3] = 15;
```

现在问题是：如果 `a` 的第一段到 `9` 结束，那么 `b` 里面哪些元素应该和它一起归并？

因为 `b` 里小于等于 `9` 的元素是：`2 4 6 8`，所以`v[1] = 4;`

表示：a[0..4] 应该和 b[0..3] 归并

对应`c` 的起点是：`c + u[0] + v[0]`


### 2. 关键变量 u 和 v 怎么理解？

`u[i]` ：a 数组的切分点
`v[i]`： b 数组中有多少个元素 <= a[u[i]-1]
- 通过`rank`找到插入位置
```c
u[0] = v[0] = 0;
u[p] = m;
v[p] = n;

for (i = 1; i < p; i++) {
    u[i] = i * m / p;
    v[i] = rank(b, b+n, a[u[i]-1]);
}
```

### 3. 每个线程做什么？

**确定了u和v之后，每个线程只需要做一个局部普通串行归并 == 全局结果**

> 但我感觉前面这一系列操作搞完说不定串行算法都结束了

前面又算 `u[i]` 又算 `v[i]`，这套准备工作会不会比串行归并O(N)还慢？

#### 时间分析

1. 计算 `u[i]` 和 `v[i]`：rank 二分查找 O(log n) ，总工作量 O(p log n) ，二分查找本身也能并行，并行时间大约是 **O(log n)**

2. 每个线程归并自己的小段：如果切分比较均匀 O(N / p)

	串行 merge 是 O(N)，已经很优
	  
	并行 merge 额外增加 O(p log n) 的切分开销，  
	**但如果 N 很大、p 较小，这个开销远小于 O(N)**  
	  
	理想情况下，并行时间从 O(N) 降到 O(N/p + log n)
	  
	所以它不是渐进意义上把 O(N) 变成比 O(N) 更低的总工作量，而是在多线程机器上减少挂钟时间

## 11. PSRS 排序

PSRS = **Parallel Sorting by ==Regular Sampling==**，即**基于正则采样的并行排序算法**

### 1. 均匀划分

```v
原数组：
[ 15 46 48 93 39 6 72 91 14 | 36 69 40 89 61 97 12 21 54 | 53 97 84 58 32 27 33 72 20 ]

p = 3

P0 拿前 9 个
P1 拿中间 9 个
P2 拿后 9 个
```

→ 先保证 **每个线程的数据量均衡，但数值范围不一定均衡**

### 2. 局部排序

每个线程对自己的局部段执行串行排序，**局部排序复杂度 ≈ O((n/p) log(n/p))**


>[!quote]+ 问题：局部排序在整个流程中发挥了什么作用？
> **→ 让每个线程自己的数据有序，方便采样和二分查找**

> 划分出每个线程对应的left、right、local_n，这点和pthreads相同
> 对共享数组调用 sort(a+left,a+right)

### 3. 正则采样

**正则采样**：每个处理器从自己的局部有序段中==**等间隔选取 p 个样本**==

如果每段长度是 `n/p`，那么**采样间隔**大约是：$(n/p) / p = n / p^2$

`sample[i] = array[i*n/p/p]`

```v
P0 排好后：6 14 15 39 46 48 72 91 93
抽样：6 39 72

P1 排好后：12 21 36 40 54 61 69 89 97
抽样：12 40 69

P2 排好后：20 27 32 33 53 58 72 84 97
抽样：20 33 72
```

→ 从每个局部有序段里拿代表元素，**估计全局分布**

>sample数组，大小为 p×p，间隔 step 为 local_n / p
>每个线程填入p个样本，通过rank隔离填入位置
>for (int j = 0; j < p; j++)
	samples[id * p + j] = a[left + j * sample_step];

### 4. 样本排序
**把所有样本收集到一起排序**

计算量 = p 个线程 × 每个线程 p 个样本 = p² 个样本

时间复杂度：O(p² log(p²))

```v
排序后：  
6 12 20 33 39 40 69 72 72
```

>这一步的意义是什么？

**→ 把代表元素放到全局顺序里，方便选择主元**

### 5. 选择主元 & 主元划分

**从排好序的 `p²` 个样本中选择 `p - 1` 个主元**

> 相当于继续均分？差不多，选择第`p`,`2p` 个数据作为主元

找到2个分界点：`33 和 69`，于是全局数据被分为：
```
桶0：≤ 33
桶1：33 ~ 69
桶2：≥ 69
```

以P1为例：
```v
P1:
12 21 36 40 54 61 69 89 97

≤33：12 21
33~69：36 40 54 61 69
≥69：89 97
```

> 主元划分就是用一个二维数组记录每个线程中的边界
> p-1个主元 -> p个桶 -> p+1个边界
> 使用upper_bound函数（返回大于某个主元的位置）得到右边界

### 6. 按桶重组 + p 路归并
每个线程都切出了 3 个桶：
```
P0: 小桶0 | 中桶0 | 大桶0
P1: 小桶1 | 中桶1 | 大桶1
P2: 小桶2 | 中桶2 | 大桶2
```

**问题变成：多线程版桶排序**
⬇️
**多路归并**：反正都是共享数组，不用像MPI那样反复通信

> 感觉已经被MPI的Sendrecv深深影响了

### 7. 总结

**PSRS的精髓**：用**少量样本估计全局分界线**，使得并行排序可以变成多个独立的局部归并任务

并行算法设计的几个核心思想：
1. 先局部处理：每个线程先排序自己的数据
2. 用采样估计全局分布：避免全局扫描
3. 用主元划分值域：让每个线程负责一个区间
4. 用归并合并有序段：利用局部有序性质
5. 尽量负载均衡：让每个线程最终处理的数据量接近

#### 时间复杂度

```
1. 局部排序：
每个线程排序 n/p 个元素
约 O((n/p) log(n/p))

2. 正则采样 + 样本排序：
样本数量 p²
约 O(p² log p)

3. 主元划分：
每个线程用 p-1 个主元切自己的有序段
可用二分查找
约 O(p log(n/p))

4. 最后归并：
每个线程归并若干有序段
理想情况下处理约 n/p 个元素
```

#### 空间复杂度

感觉这个算法也太复杂了，是否需要很高的空间复杂度？

除了原始共享数组 `A[N]`，还需要的额外空间

1. 样本空间：存储取样点 p²
2. 主元数组：p - 1
3. 切分点数组：得到主元后对原始数据记录切分点，大约 p × (p + 1)，即 O(p²)
   >归并需要的 u[i]
4. Else
