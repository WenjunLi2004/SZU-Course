**MPI（Message Passing Interface，消息传递接口）** 
- 定义了被C语言程序调用的 ==**函数库**==
- 用来实现这种==**跨核心消息传递**==

## 1. MPI 核心骨架与基本概念
### 1. 环境初始化和释放

`MPI_Init(NULL,NULL);`：初始化准备必要的设置

`MPI_Finalize();`：程序结束回收资源

### 2. 通信域
**通信域 Communicator**：一组能够相互发送消息的**进程集合**，理解为一个 **“微信群”**
- `MPI_COMM_WORLD` 是 `MPI_Init` 自动建好的 **“所有人都在的总群”**，大部分基础通信都在这个群里进行
- `MPI_Comm_size(MPI_COMM_WORLD, &comm_sz)` : 通过调用这个函数，程序能知道当前到底有多少个核心在协同工作
	- 用命令行启动了 4 个进程（`mpiexec -n 4`），那么 `comm_sz` 的值就是 4
- `MPI_Comm_rank(MPI_COMM_WORLD, &my_rank);` ：区分不同进程的函数
	- 约定俗成地把 **0 号核心（Rank 0）** 当作 **“主核心（Manager）”**
#### MPI_Comm_split：拉讨论组
```c
MPI_Comm rowComm;

MPI_Comm_split(MPI_COMM_WORLD, rank / n, rank % n, &rowComm);
```
- 颜色 (`color = rank / n`)：颜色决定了你进哪个群；颜色相同的核心，会被分到同一个新群里
- 排序号 (`key = rank % n`)：进入新群后，大家重新排座次（生成新的 rowRank）。谁的 key 小，谁的新 rank 就靠前
### 3. SPMD编程
**Single program**, multiple data ：一种编程习惯，只写一份代码，通过Rank区分主核心和其他核心

```c
if (my_rank == 0) {
    // 0号核心去发试卷（分配数据）
} else {
    // 1、2、3号核心去接收试卷，开始干活
}
```

## 2. 通信 -- 点对点

### 1. 发送消息：`MPI_Send`
假设核心 0 要给核心 1 发送一个整数：
```C
MPI_Send(
    &number,      // 1. 寄什么包裹？（数据的内存地址）
    1,            // 2. 寄多少个？（数据个数）
    MPI_INT,      // 3. 包裹里是什么材质？（数据类型，如 MPI_INT 代表整数）
    1,            // 4. 寄给谁？（收件人的编号 Rank，这里是给核心 1）
    0,            // 5. 快递单号/标签（Tag，用于区分不同类别的消息，0最常用）
    MPI_COMM_WORLD// 6. 走哪个快递公司？（通信子，必须在同一个群里）
);
```
### 2. 接收消息 ：`MPI_Recv`
核心 1 必须配合接收，少一个环节都会出问题：
```C
MPI_Recv(
    &number,      // 1. 收到包裹放哪里？（接收缓冲区的地址）
    1,            // 2. 最多能收多少个？（容量限制）
    MPI_INT,      // 3. 期望收什么材质？（数据类型必须对应）
    0,            // 4. 等谁的包裹？（发件人的编号 Rank，这里等核心 0 的）
    0,            // 5. 期待的快递单号/标签（必须匹配）
    MPI_COMM_WORLD, // 6. 走哪个快递公司？（必须是同一个群）
    MPI_STATUS_IGNORE // 7. 快递回执单（暂时不用，填忽略即可）
);
```

**前三个参数描述信息的内容：内存地址、数据个数、数据类型**
![[Pasted image 20260314163150.png]]

#### 思考：为什么能保证正常执行？
如果**核心 1 执行得非常慢**，姗姗来迟，跑到 `MPI_Recv` 的时候，核心 0 的 `MPI_Send` 早就执行完了，快递已经被扔在了“驿站”（系统缓冲区）；
那么反过来，如果**核心 1 先跑到了 `MPI_Recv`，而核心 0 还在磨洋工还没执行 `MPI_Send`，你觉得核心 1 会怎么做？它会直接跳过报错，还是停在原地死等？**

### **阻塞通信**
标准的 `MPI_Recv` 是一个**阻塞型（==Blocking==）** 函数 
- `MPI_Send`==**没执行完**==，`MPI_Recv`会**始终处于阻塞状态**，**不会跳过，也不会报错**，直到那个带有特定发件人（0 号）和特定单号（标签 0）的数据包真正通过网络传输过来
![[Pasted image 20260314221109.png]]
#### **对于MPI_Send的阻塞通信**
**缺陷——缓冲区 & 效率** ：
1. **Eager Protocol**：当发送**小**数据（==**用户缓冲区**==） <= ==**接收缓冲区**==时，`MPI_Send` **瞬间把数据放到==系统发送缓冲区==并返回**，后续再放入接收方的 **系统缓冲区**
	- `MPI_Send`在 ① 执行完返回，不会阻塞
2. **Rendezvous Protocol**：当缓冲区不够时，绕过本地缓存，直接两个用户缓冲区之间握手直连
	- `MPI_Send`在 ③ 执行完返回，阻塞

**致命缺陷**：如果 `MPI_Send` 中途失效 or 阻塞死了，`MPI_Recv` 会永远卡住 —— ==**死锁**==
- **失效**：发送 or 接收 没有匹配的进程
- **阻塞**：两个进程之间交换信息（同时Send），当数据量很大时，==**同样会导致死锁**==
	- 两个`MPI_Send`都被阻塞了，所以**禁止同时相互Send**

#### 解决方案：非阻塞通信
1. Immediate send or recv：**瞬间返回**，拿了一张回执单（`MPI_Request`）
	`MPI_Isend(a, n, MPI_INT, 1, 0, MPI_COMM_WORLD, &request);`
	`MPI_Irecv(a, n, MPI_INT, 0, 0, MPI_COMM_WORLD, &request);`
	**关键的坑**：调用返回并不保证==**资源的可再用性**==
2. **通信完成检测** (`MPI_Wait` / `MPI_Test`)
	- **`MPI_Wait`**：拿着刚才的回执单，在这里死等，直到数据确实送到了
	- **`MPI_Test`**：拿着回执单问一下“数据发完了没？”，系统秒回 True 或 False
	  没发完我就再去干点别的事，一会儿再来问

***Note** : `MPI_Isend` + `MPI_Wait` = `MPI_Send`*

### 灵活接收

>[!note]+ 细节：接收方==可以==在不知道以下信息的情况下接收消息
> 1. **消息中的数据量**：只要求缓冲区足够大 send_buf_sz ≤ recv_buf_sz
> 2. **消息的发送方**：通配符 `MPI_ANY_SOURCE`，谁第一个把消息发过来，它就接收谁的
> 3. **消息的标签**：通配符 `MPI_ANY_TAG`，所有标签照单全收

#### 进一步：使用ANY通配符，**怎么知道消息到底是谁发送的？** 
—— 在“标准骨架”里忽略掉的最后一个参数了：**`MPI_Status`（消息状态回执）**
- 之前我们填的都是 `MPI_STATUS_IGNORE`（==**忽略**==回执）

在用了通配符后必须准备一个**回执单结构体**：==**只有三个成员**==
```C
MPI_Status status; 
// 接收时把 &status 传给最后一个参数
MPI_Recv(..., MPI_ANY_SOURCE, MPI_ANY_TAG, MPI_COMM_WORLD, &status);
```
接收完成后，可以从这个 `status` 里把那些“不知道”的信息全查出来：

- **是谁发给我的？** 查看 `status.MPI_SOURCE`
- **消息标签是多少？** 查看 `status.MPI_TAG`
- **有没有出错？** 查看 `status.MPI_ERROR`

**其他信息需要通过函数实现：**
- **==到底发了几个数据==？** 调用专门的函数 `MPI_Get_count(&status, MPI_INT, &count)`
```C
int count;
MPI_Get_count(&status, MPI_INT, &count);

cout << "source = " << status.MPI_SOURCE << endl;

cout << "tag = " << status.MPI_TAG << endl;

cout << "count = " << count << endl;
```
##### **为什么不能直接读取count?**
MPI 在网络底层传输的其实是==**“纯粹的字节（Bytes）”**==，而在代码里操作的是“数据类型（Datatype）”

**点对点通信问题在于收发效率低下，要挨个接收 1、2、3 号发来的数据**

## 3. 集合通信
针对 **所有进程都参与** 的行动，三大铁律：
1. **全员参与**：通信域（比如 `MPI_COMM_WORLD`）里的所有核心**必须**调用==**同一个**==集合通信函数，同时==**汇总对象要一致**==
2. **不用贴标签**：集合通信不需要像 Send/Recv 那样写 Tag，系统底层会自动匹配
	- 点对点通信：标签+通信域
	- 集合通信：==**被调用顺序**== + 通信域
3. **极速算法**：底层通常采用我们在第 1 章学过的“树形算法”（核心配对），把通信时间从 $O(n)$ 骤降到 $O(\log_2 n)$

### 1. **万剑归宗** —— `MPI_Reduce`（归约）
把所有人手里的数据，通过**某种数学运算**（如求和、求最大值），汇总到一个人的手里

**之前一大段的 if-else 现在只需要一句话**：
```cpp
// 所有人同时执行这一句：
MPI_Reduce(&local_int, &total_int, 1, MPI_DOUBLE, MPI_SUM, 0, MPI_COMM_WORLD);
```
**参数拆解：**
- `&local_int`：要交出去的数据（单份局部积分）
    
- `&total_int`：汇总后的结果存哪？（注意：**==只有主核心的这个变量最后会有意义==**，但是所有进程仍然需要传入这个参数，即使没有意义）
    
- `1, MPI_DOUBLE`：交出去 1 个双精度浮点数
    
- **`MPI_SUM`**：==**核心算法**==！告诉系统我要做什么数学运算。这里是**求和**，也可以换成 `MPI_MAX`（求全场最大值）、`MPI_PROD`（求全场乘积）等。
![[Pasted image 20260315214519.png]]
- **`0`**：结果汇总给谁？（Root 节点，这里是给 0 号核心）
    
- `MPI_COMM_WORLD`：在哪个群里进行
#### 如何理解调用顺序 —— MPI_Reduce的多次调用
**调用顺序 = 代码执行的先后顺序 强行配对**
##### 例子：多次调用
```c
    a = 1;
    c = 2;
    MPI_Init(NULL, NULL);
    MPI_Comm_rank(MPI_COMM_WORLD, &my_rank);
    if (my_rank == 0 || my_rank == 2) {
        MPI_Reduce(&a, &b, 1, MPI_INT, MPI_SUM, 0, MPI_COMM_WORLD);
        MPI_Reduce(&c, &d, 1, MPI_INT, MPI_SUM, 0, MPI_COMM_WORLD);
    }
    else {
        MPI_Reduce(&c, &d, 1, MPI_INT, MPI_SUM, 0, MPI_COMM_WORLD);
        MPI_Reduce(&a, &b, 1, MPI_INT, MPI_SUM, 0, MPI_COMM_WORLD);
    }
    if (my_rank == 0)
        printf("b = %d, d = %d\n", b,d);
```
![[Pasted image 20260315220656.png]]

==**致命易错点：只有目标核心的Total_int是有意义的**==，两层含义：
1. 只有目标核心的接收变量有意义
2. **其他核心调用MPI_Reduce只是提供数据**

**结果：**
1. **第一回合**：主核心调用 MPI_Reduce 接收 b，无脑相加：$1 (\text{来自 0 号}) + 2 (\text{来自 1 号}) + 1 (\text{来自 2 号}) = 4$
2. **第二回合**：主核心调用 MPI_Reduce 接收 d，无脑相加：$2 (\text{来自 0 号}) + 1 (\text{来自 1 号}) + 2 (\text{来自 2 号}) = 5$。
3. `b=4,d=5`

#### **结论：本质就是所有进程都必须调用 且 参数兼容**
```cpp
// 所有人同时执行这一句：
MPI_Reduce(&local_int, &total_int, 1, MPI_DOUBLE, MPI_SUM, 0, MPI_COMM_WORLD);
```
**等效于：**
```cpp
// 所有人同时执行这一句：
if (rank == 0)
	MPI_Reduce(&local_int, &total_int, 1, MPI_DOUBLE, MPI_SUM, 0, MPI_COMM_WORLD);
else
	 MPI_Reduce(&local_int, NULL, 1, MPI_DOUBLE, MPI_SUM, 0, MPI_COMM_WORLD);
```

### 2. 大喇叭广播 —— `MPI_Bcast`（Broadcast）
在梯形法则的例子中，积分区间 $a = 0.0$ 和 $b = 3.0$ 是写死在代码里的
但在实际应用中，这些参数通常是程序启动时，**由 0 号核心通过键盘读取的（`scanf`）**
- **问题**：0 号核心读到了数据，其他核心怎么知道是多少？用 `for` 循环挨个 `MPI_Send` 吗？太慢了！

这时候就需要用**广播：将属于单个进程的数据发送到通信域中所有进程**
![[Pasted image 20260315215124.png]]
```cpp
// 假设 0 号核心刚才通过键盘读取了 a, b, n
// 现在，全员同时执行以下这几行代码：

MPI_Bcast(&a, 1, MPI_DOUBLE, 0, MPI_COMM_WORLD);
MPI_Bcast(&b, 1, MPI_DOUBLE, 0, MPI_COMM_WORLD);
MPI_Bcast(&n, 1, MPI_INT, 0, MPI_COMM_WORLD);
```

### 3. **精准发牌官** —— `MPI_Scatter`（散播）
专门用来处理**数组/向量**的“切分发牌”与“原样回收”

以做一个**庞大的向量加法**为例子：两个长度为 1000 的数组 `x` 和 `y`
- 核心 0 把数组读取到了自己的内存里，现在要把它们平分给 **4 个核心**（每个核心分 250 个元素）

![[Pasted image 20260316085915.png]]

```cpp
// 假设全场有 4 个核心，Root 是 0 号
// 0 号核心的 x_global 装着 1000 个元素，其他核心的 x_global 是空的/无效的
// 每个人准备了一个容量为 250 的小数组 x_local

MPI_Scatter(
    x_global,      // 1. 发件箱：Root 核心手里的大数组（非 Root 核心填 NULL 即可）
    250,           // 2. 发送数量：【极其容易踩坑！】这是发给**每个**核心的数量，不是总数！
    MPI_DOUBLE,    // 3. 发送数据类型
    x_local,       // 4. 收件箱：每个人准备用来接牌的小数组
    250,           // 5. 接收数量：通常等于发送数量
    MPI_DOUBLE,    // 6. 接收数据类型
    0,             // 7. 发牌官是谁？（Root 核心的 Rank）
    MPI_COMM_WORLD // 8. 在哪个群里发？
);
```
**不同核心执行完这行代码后：**
- 核心 0 的 `x_local` 拿到了 `x_global` 的第 0~249 个元素
- 核心 1 的 `x_local` 拿到了 `x_global` 的第 250~499 个元素
- 核心 2 拿到 500~749
- 核心 3 拿到 750~999
#### 和MPI_Bcast区别
**`MPI_Bcast` vs `MPI_Scatter`**：
- ==**Bcast 是复印机**==，Root 核心手里有一份 100 页的文件，它复印了 N 份，给每个人发**完整的一本**
- ==**Scatter 是发牌官**==，Root 核心手里有一副 54 张的扑克牌，它把它**平均切分**，依次给每个人发几张不同的牌

### 4. **完美拼图工** —— `MPI_Gather`（聚集）
大家都算完了自己那 250 个结果，存放在各自的 `z_local` 里面。现在，核心 0要求看到**完整的 1000 个元素的最终结果数组 `z_global`**

此时可以通过 MPI_Gather把分散的结果拼起来，**它的参数结构和 Scatter 是对称的镜像**
![[Pasted image 20260316090834.png|525]]
```cpp
// 每个人手里有 250 个算好的结果在 z_local 里
// 0 号核心准备了一个容量为 1000 的大数组 z_global

MPI_Gather(
    z_local,       // 1. 发件箱：每个人交出的局部小数组
    250,           // 2. 发送数量：每个人交出多少个元素
    MPI_DOUBLE,    // 3. 发送数据类型
    z_global,      // 4. 收件箱：Root 核心用来装拼图的大数组
    250,           // 5. 接收数量：【再次划重点】是指从**每个**核心接收的数量！不是 1000！
    MPI_DOUBLE,    // 6. 接收数据类型
    0,             // 7. 谁负责把碎纸拼成整书？（Root 核心的 Rank）
    MPI_COMM_WORLD // 8. 在哪个群里拼？
);
```
#### 和 MPI_Reduce 区别
**`MPI_Reduce` vs `MPI_Gather`**：
- Reduce 是会计，把大家手里的钱收上来，**==加在一起==** 变成一个总数
- Gather 是装订工，把大家写好的零散报告收上来，**不做什么加减乘除，==只按顺序拼接==**成一本完整的大书

### **隐式同步**
MPI 集合通信最核心的底层机制之一：由于存在绝对的**数据依赖**，跑得快的“接收方”必定会停在原地，乖乖等待跑得慢的“发送方”把数据准备好并交接出来

### 5. 进阶用法：All
1. Scatter：老板发牌
2. Gather：老板收作业
3. Reduce: 老板算总账

**共同点**：只有老板（0 号核心）能看到最终结果

**实际问题**：机器学习的梯度下降要求每一个核心在算完自己的一部分后，都必须立刻拿到“全局的最新结果”，才能继续往下进行下一轮的迭代计算
1. **归约场景**：先用 `MPI_Reduce`到 Core 0 ，再用 `MPI_Bcast`广播到其他核心
2. **聚和场景**：先 `Gather` 给 0 号再由 0 号 `Bcast`

![[Pasted image 20260316183916.png]]

**针对这两种场景设计出更高效的函数**
#### 1. `MPI_Allreduce` (全局归约)
语法和普通的 `MPI_Reduce` 几乎一模一样，**唯一的区别是：砍掉了 `root`（目标核心）参数！** 因为现在没有老板了，大家都是平等的，每个人都要拿到结果

```c
// 普通的 Reduce (需要指定谁是老板，比如 0)
MPI_Reduce(&local_max, &global_max, 1, MPI_DOUBLE, MPI_MAX, 0, MPI_COMM_WORLD);

// 🌟 高阶的 Allreduce (没有老板！全员接收！)
MPI_Allreduce(&local_max, &global_max, 1, MPI_DOUBLE, MPI_MAX, MPI_COMM_WORLD);
```
#### 2. `MPI_Allgather` (全局聚集)
```c
// 普通的 Gather (需要 0 号核心收拢，填入大数组 c)
MPI_Gather(local_c, local_n, MPI_DOUBLE, c, local_n, MPI_DOUBLE, 0, MPI_COMM_WORLD);

// 🌟 高阶的 Allgather (砍掉 root，全员的大数组 c 都会被填满！)
MPI_Allgather(local_c, local_n, MPI_DOUBLE, c, local_n, MPI_DOUBLE, MPI_COMM_WORLD);
```
#### 为什么它们这么快？
实际上它根本不用 0 号核心当苦力，而是采用了一种叫 **“蝶形网络（Butterfly Network）”** 或 **“环形交换（Ring Algorithm）”** 的拓扑结构
![[Pasted image 20260316183901.png]]
### **6. 全局同步：MPI_Barrier**
`MPI_Barrier(MPI_Comm comm)` 属于**全局同步（Synchronization) 型集合通信原语**
当一个通信域内的某个进程调用此函数时，该进程会被挂起（阻塞），**直到该通信域内的所有其他进程都调用了此函数，路障才会集体放行**

#### **使用场景：**
1. **精确的性能测速**：由于各个进程的启动时间不同，或者之前的代码执行快慢不一，如果直接调用 `MPI_Wtime()` 开始计时，会导致大家起跑时间不一致，测出的并行总时间极不准确
```c
MPI_Barrier(MPI_COMM_WORLD); // 强行让所有人在这里等齐
double start_time = MPI_Wtime(); // 枪响，同时起跑开始计时
```

2. **阶段性任务隔离**：从独立作业到集体作业，**保证空间与时间上的绝对安全隔离**
   例如：阶段一是大家各自生成数据集，阶段二是调用`MPI_Allgather()`聚集数据

## 4. 派生数据类型
到目前为止，我们发送的数据都是同一种数据类型 且 内存连续，但实际数据形式：
1. 异构数据 —— 结构体：涉及内存对齐，大小端架构
2. 非连续数据：无法使用普通的`MPI_Send`发送

**解决方法：派生数据类型**
- 定义由**数据类型不同**且**地址空间不连续**的数据项组成的消息
- 充当架构师，向 MPI 注册一种全新且详细的结构体
![[Pasted image 20260318104117.png]]
### 1. 核心生命周期
任何自定义类型都必须经历这四步：
1. **构造（Create）**：用特定函数描述你的数据长什么样
    
2. **提交（Commit）**：调用 `MPI_Type_commit` 告诉系统：“我设计好了，请在底层帮我注册这个新类型！”（==**很多新手会忘写这一句导致报错**==）
    
3. **使用（Use）**：在 Send/Recv/Bcast 里把它当普通的 `MPI_DOUBLE` 一样用
    ==**最重要：派生前置工作做完可以当正常的Datatype来用**==
4. **释放（Free）**：用完后调用 `MPI_Type_free` 把新类型销毁，归还内存

### 2. 两种常用构造函数

1. 步长跳跃：`MPI_Type_vector`
	- **应用场景**：当需要每==**隔固定距离**==抓取几个数据时（比如矩阵的列），只需要告诉它“抓几块”、“每块多大”、“两块之间隔多远”

2. 异构结构体：`MPI_Type_create_struct`
	- **应用场景**：向 MPI 描述你的 `struct Particle`，需要告诉它里面有几个基本类型、每个类型对应在内存里的真实偏移量（用 `MPI_Get_address` 探查系统内存对齐的间隙）

#### 例子1：发送一个数组的所有偶序数元素

```c
double A[100];

MPI_Datatype EvenElements;

···

MPI_Type_vector(50, 1, 2, MPI_DOUBLE, &EvenElements);

MPI_Type_commit(&EvenElements);

MPI_Send(A, 1, EvenElements, destination, ···);
```

**又：取矩阵的列**
`MPI_Type_vector(count,blocklength,stride,type,&name)`
- **`count` (抓几次？)**：我们要取一列，矩阵有 3 行，所以我们要抓 3 次
- **`blocklength` (每次抓几个？)**：我们只取一列，所以每次只抓 1 个元素。
- **`stride` (每次跳多远？)**：从上一行的元素，跳到下一行的对应元素，中间隔了一整行的长度，所以跨度就是矩阵的列数（$n=3$）
#### 例子2：发送结构体
```c
#include "mpi.h"
#include <iostream>

using namespace std;

// 1. 定义我们要发送的异构结构体
struct Particle {
    int id;
    double mass;
    double velocity[3];
};

int main(int argc, char** argv) {
    int rank, size;
    MPI_Init(&argc, &argv);
    MPI_Comm_rank(MPI_COMM_WORLD, &rank);
    MPI_Comm_size(MPI_COMM_WORLD, &size);

    // ==========================================
    // 🌟 第一步：准备“造箱子”的三张图纸
    // ==========================================
    // 这个结构体有 3 个成员变量
    int count = 3; 
    
    // 图纸 1：每个成员包含几个元素？
    // id有1个，mass有1个，velocity有3个
    int blocklengths[3] = {1, 1, 3}; 
    
    // 图纸 2：每个成员的数据类型是什么？
    MPI_Datatype types[3] = {MPI_INT, MPI_DOUBLE, MPI_DOUBLE};
    
    // 图纸 3：每个成员在内存里的“真实偏移量”是多少？
    MPI_Aint displacements[3]; 

    // 🌟 核心技术点：用一个实体变量来“实地测量”偏移量
    Particle dummy_particle;
    MPI_Aint base_address, id_addr, mass_addr, vel_addr;
    
    // 获取每个成员的绝对内存地址
    MPI_Get_address(&dummy_particle, &base_address);
    MPI_Get_address(&dummy_particle.id, &id_addr);
    MPI_Get_address(&dummy_particle.mass, &mass_addr);
    MPI_Get_address(&dummy_particle.velocity, &vel_addr);
    
    // 计算相对偏移量（这彻底避开了内存对齐的陷阱！）
    displacements[0] = id_addr - base_address;   // 通常是 0
    displacements[1] = mass_addr - base_address; // 可能是 4，也可能是 8
    displacements[2] = vel_addr - base_address;  // 紧接着 mass 后面

    // ==========================================
    // 🌟 第二步：根据图纸，创建全新的数据类型！
    // ==========================================
    MPI_Datatype MPI_PARTICLE; // 我们专属的新类型名
    MPI_Type_create_struct(count, blocklengths, displacements, types, &MPI_PARTICLE);

    // ==========================================
    // 🌟 第三步：向 MPI 系统提交注册！(极易忘的一步)
    // ==========================================
    MPI_Type_commit(&MPI_PARTICLE);

    // ==========================================
    // 🚀 开始愉快地通信吧！(把它当成普通类型用)
    // ==========================================
    if (rank == 0) {
        // 0 号核心制造 2 个粒子
        Particle p_array[2];
        p_array[0].id = 101; p_array[0].mass = 1.5;
        p_array[0].velocity[0] = 0.1; p_array[0].velocity[1] = 0.2; p_array[0].velocity[2] = 0.3;
        
        p_array[1].id = 102; p_array[1].mass = 2.5;
        p_array[1].velocity[0] = 0.4; p_array[1].velocity[1] = 0.5; p_array[1].velocity[2] = 0.6;

        // 发送！注意这里的类型填的是我们刚造好的 MPI_PARTICLE
        MPI_Send(p_array, 2, MPI_PARTICLE, 1, 0, MPI_COMM_WORLD);
        cout << "Rank 0 发送了两个物理粒子数据。" << endl;
    } 
    else if (rank == 1) {
        Particle recv_p[2];
        
        // 接收！MPI 会自动在底层帮我们做解包和类型匹配
        MPI_Recv(recv_p, 2, MPI_PARTICLE, 0, 0, MPI_COMM_WORLD, MPI_STATUS_IGNORE);
        
        cout << "Rank 1 成功接收！" << endl;
        cout << "粒子1 ID: " << recv_p[0].id << ", 质量: " << recv_p[0].mass << endl;
        cout << "粒子2 速度X: " << recv_p[1].velocity[0] << endl;
    }

    // ==========================================
    // 🌟 第四步：打扫战场，注销类型
    // ==========================================
    MPI_Type_free(&MPI_PARTICLE);

    MPI_Finalize();
    return 0;
}
```

## 5. 性能评估
### **并行程序计时函数** `double MPI_WTime(void);`
`WTime`搭配 `MPI_Barrier()`一起使用 （Barrier -> Wtime）
1. Start：确保每个进程起始时间相同
2. End：确保 `End - Start`对应最慢进程时间，然后再用 `if(rank==0)`输出结果

### 1. 加速比 S
加了 $p$ 个核心，到底给**快了多少倍**

**公式**：$S = \frac{T_{serial}}{T_{parallel}}$
- $T_{serial}$：最好、最优的**单核串行程序**跑完所需的时间
    
- $T_{parallel}$：**并行程序**在使用 $p$ 个核心时跑完所需的时间

**理想与现实**：
- **线性加速比（Ideal）**：$S = p$
	用了 16 个核，就刚好快 16 倍
	这是我们梦寐以求的，但现实中几乎不可能达到
    
- **次线性加速比（Sub-linear）**：$S < p$
  用了 16 个核，但只快了 10 倍
  这是最常见的现实，因为多核心之间有**通信开销**（比如之前矩阵乘法里的 `MPI_Send/Recv`）和**同步等待**（`MPI_Barrier`）
    
- **超线性加速比（Super-linear）**：$S > p$
  极罕见！用了 16 个核，竟然快了 20 倍！
  这通常是因为把大任务切小后，每个核心分到的数据足够小，刚好能全部塞进 CPU 超快的高速缓存（Cache）里，产生了“Cache 红利”

### 2. 并行效率 (Efficiency, $E$)
加速比只说明了“快了多少”，而并行效率说明了“硬件有多努力”
- **公式**：$E = \frac{S}{p} = \frac{T_{serial}}{p \times T_{parallel}}$
    
- **意义**：它的值通常在 0 到 1（即 0% 到 100%）之间
	e.g. : 如果 $E = 0.8$，说明在计算过程中，每个核心平均有 80% 的时间在工作，20% 的时间在发呆（等待收发网络数据或负载不均）
    
- **规律**：随着核心数 $p$ 的增加，虽然整体时间 $T_{parallel}$ 可能会减少，但**效率 $E$ 几乎总是下降的**。因为人越多，沟通成本（通信开销）就成倍增长

### 3. 天花板：阿姆达尔定律 (Amdahl's Law)
只要代码里有一丁点部分是**只能单核串行执行**的，你的程序速度就有一个永远无法突破的天花板
- **推导逻辑**：假设一个程序，有比例为 $f$ 的代码只能串行执行（比如从硬盘读数据、主核心负责分配任务等），剩下 $(1-f)$ 的代码可以完美并行。
    
- **极限公式**：无论你加多少个核心（当 $p \to \infty$ 时），你的最大加速比 $S_{max} \le \frac{1}{f}$

### 4. 破局之道：可扩展性 (Scalability)
==**从效率不降低理解**==的另一种评估维度：
- **强可扩展性 (Strong Scaling)**：**问题规模不变**，不断增加核心数，效率不会降低，则具有强扩展性
	- 这就刚好撞在阿姆达尔定律的枪口上，效率通常会崩塌
- **弱可扩展性 (Weak Scaling / 古斯塔夫森定律)**：既然人多了，那我们就**把任务搞大**！
	- 如果把核心数增加 10 倍，同时把我们要算的矩阵规模也增大 10 倍，只要执行时间能保持不变，就说明程序的“弱可扩展性”极好
	- 这才是超算真正发挥威力的地方——不是为了把一个小题算得无限快，而是为了**在可接受的时间内，算出一个以前根本算不动的天文级大题**
### 5. 安全通信和死锁
“死锁”和“安全通信”通常是围绕着 **==阻塞==式发送/接收**（`MPI_Send` 和 `MPI_Recv`）产生的

—— 安全通信是指**无论数据多大、无论系统缓冲区多小，都绝对不会发生死锁的通信方式**

### 进程内交换数据常用做法：交换指针
首先必须明确：
- **跨进程（比如 进程 0 给 进程 1）：** 绝对**不能**传指针！因为进程 0 和进程 1 的内存是物理隔离的，你把 0 号进程里的地址 `0x1234` 传给 1 号进程，1 号进程去读那个地址，要么读出垃圾数据，要么直接段错误（Segmentation Fault）。跨进程**必须**通过 MPI 老老实实地拷贝发送**真实的数据**

## 例子：**并行奇偶移项排序**

### 1. 基本原理
并行奇偶排序是基数排序在并行计算环境下的变形。它将 $N$ 个数据分布在 $P$ 个进程上，通过交替进行的两个阶段完成全局排序：
* **偶数阶段 (Even)：** 偶数号进程 (0, 2, ...) 与其右侧邻居 (1, 3, ...) 进行比较与交换
* **奇数阶段 (Odd)：** 奇数号进程 (1, 3, ...) 与其右侧邻居 (2, 4, ...) 进行比较与交换

### 2. 核心操作：Compare-Split
每个进程内部先对本地数据进行预排序。在交换阶段，两个相邻进程：
1.  交换各自拥有的全部数据。
2.  **左侧进程：** 保留合并后较小的 $N/P$ 个元素。
3.  **右侧进程：** 保留合并后较大的 $N/P$ 个元素。

### 3. 算法特点
* **复杂度：** 
	* **时间复杂度：** 在 $P$ 个进程下，需要进行 $P$ 个阶段的交换，总复杂度为 $O(\frac{N}{P} \log \frac{N}{P} + P \times \frac{N}{P})$
    * **空间复杂度：** 每个进程需要额外的缓冲区来接收邻居的数据
* **通信模式：** 仅涉及最近邻通信，不涉及全局归约，扩展性较好
* **同步要求：** 每个阶段结束后需要==**隐式或显式的同步**==（通过阻塞式 `MPI_Sendrecv` 或 `MPI_Barrier`）
	**依然是阻塞通信**

### 4. 局限性
当 $P$ 非常大时，虽然单个阶段计算变快，但总阶段数 $P$ 也会增加，通信延迟可能成为主要瓶颈
