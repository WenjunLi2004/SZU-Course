# 10(b)：共享内存归约
## 10.1 为什么shuffle不通用？
 **==shuffle 不是一种算法，而是一种硬件指令==**

`__shfl_down_sync` 的本质是通过==**硬件实现**== 让**同一个 warp 内的线程直接读取其他 lane 的寄存器值**

**它很快，但适用范围受到硬件边界限制：**

| 限制               | 说明                             |
| ---------------- | ------------------------------ |
| 只能在同一个 warp 内通信  | 不能读取另一个 warp 的寄存器              |
| 不能跨 block        | **不同 block 甚至可能在不同 SM 上执行**    |
| warp 通常只有 32 个线程 | 一个 256 线程的 block 会被拆成 8 个 warp |
| 依赖有效线程掩码         | 参与 shuffle 的线程必须正确包含在 `mask` 中 |
| 只负责传值            | "怎么加、加几轮、谁保留结果"仍由算法决定          |

因此，下面的代码只能得到**一个 warp 内部**的局部和：

```c
for (int offset = warpSize / 2; offset > 0; offset /= 2)
    value += __shfl_down_sync(mask, value, offset);
```

执行结束后，通常只有 `lane 0` 保存完整的 `warp_sum`
如果一个 block 中有多个 warp，还必须继续合并这些 `warp_sum`

> [!important]+ shuffle 与归约的关系
> - **shuffle：线程之间交换寄存器数据的硬件指令**
> - **归约 reduction**：把多个值按照加法、最大值等运算合并成一个值的算法
> - shuffle 可以用来实现归约，但 shuffle 本身不等于归约算法

## 10.2 GPU 内存层次结构

GPU 的内存并不是"只有显存"
不同内存具有不同的**位置、作用域、容量和速度**

```text
线程 thread
├── 寄存器 register
└── 局部内存 local memory（逻辑私有，物理上通常位于显存）

线程块 block
└── 共享内存 shared memory / L1

整个 GPU device
├── L2 cache
├── 全局内存 global memory
├── 常量内存 constant memory
└── 纹理内存 texture memory

CPU host
└── 主机内存 host memory
```

### 10.2.1 主要内存对比

| 内存                             | 作用域           | 生命周期       | 典型速度       | 容量   | 程序员是否直接管理 |
| ------------------------------ | ------------- | ---------- | ---------- | ---- | --------- |
| **寄存器 register**               | **单个线程**      | 线程执行期间     | 最快         | 很小   | 编译器分配     |
| 局部内存<br>local memory           | 逻辑上单线程        | 线程执行期间     | 通常接近全局内存   | 来自显存 | 编译器决定     |
| ==**共享内存 <br>shared memory**== | 同一个 block     | block 执行期间 | 很快         | 较小   | 是         |
| L1 cache                       | 单个 SM         | 硬件管理       | 快          | 较小   | 否         |
| L2 cache                       | 整个 GPU        | 硬件管理       | 较快         | 中等   | 否         |
| ==**全局内存 <br>global memory**== | 整个 GPU        | 显式释放前      | 较慢、高延迟     | 最大   | 是         |
| 常量内存 <br>constant memory       | 整个 GPU，只读     | 程序期间       | 命中缓存时快     | 很小   | 是         |
| **统一内存 <br>managed memory**    | **CPU 与 GPU** | 显式释放前      | 取决于页面位置与迁移 | 较大   | 运行时迁移     |

> [!warning]+ "local memory"并不一定快
> CUDA 的 local memory 虽然名字叫"局部内存"，但它通常位于**设备显存**中
> **寄存器不足发生 register spilling，或局部数组无法放入寄存器时，数据可能被放到 local memory，因此访问延迟远高于寄存器**

### 10.2.2 作用域是最重要的判断标准

- **寄存器**：每个线程都有寄存器，只有当前线程能直接访问
- **shared memory**：同一个 block 的所有线程都能访问
- **global memory**：所有 block 都能访问，但需要同步与竞争保护
- **==不同 block 之间不能通过 shared memory 通信==**，因为每个 block 都有自己独立的 shared memory 副本

### 10.2.3 为什么共享内存适合归约

归约需要线程反复交换和合并中间结果，若每一步都访问 global memory，会产生高延迟和大量流量；shared memory 位于 SM 片上，适合保存：

- 一个 block 中每个线程的局部值
- 每个 warp 的局部和
- 矩阵乘法中的 tile
- block 内需要重复使用的数据

> [!summary]+ 内存优化原则
> **尽量让频繁使用的数据留在寄存器或共享内存，只把最终结果写回全局内存**

## 10.3 `__shared__` 与 block 内通信

静态共享内存：

```c
__shared__ float shared_vals[256];
```

动态共享内存：

```c
extern __shared__ float shared_vals[];
```

调用时指定字节数：

```c
Kernel<<<blk_ct, th_per_blk, th_per_blk * sizeof(float)>>>(...);
```

共享内存具有以下特点：

1. **每个 block 都拥有一份独立副本**；
2. block 内所有线程可以读写；
3. block 结束后内容失效；
4. 多线程交换数据时通常需要同步；
5. 容量有限，用得过多会降低一个 SM 同时驻留的 block 数量

## 10.4 `__syncthreads()`：共享内存归约的关键

```c
__syncthreads();
```

它同时具有两个作用：

- **执行屏障**：同一个 block 的所有线程都到达后，才能继续；
- **内存可见性**：屏障前对 shared memory 的写入，在屏障后对 block 内线程可见

典型流程：

```c
shared_vals[threadIdx.x] = local_sum;
__syncthreads();                 // 所有线程写完后才能开始读取
```

> [!danger]+ 不能随意放进分支
> `__syncthreads()` 必须由一个 block 中所有仍在执行的线程共同到达
> 若部分线程进入分支执行同步、其他线程没有进入，可能导致死锁或未定义行为

`__syncthreads()` 只能同步**同一个 block**，不能同步整个 grid

跨 block 合并通常使用：

- `atomicAdd`；
- 第二次 kernel launch；
- Cooperative Groups 等更高级机制

## 10.5 示例：共享内存传播求和

示例的核心代码为：

```c
__device__ float Shared_mem_sum(float shared_vals[]) {
    int my_lane = threadIdx.x % warpSize;

    for (int diff = warpSize / 2; diff > 0; diff /= 2) {
        int source = (my_lane + diff) % warpSize;
        shared_vals[my_lane] += shared_vals[source];
    }

    return shared_vals[my_lane];
}

__global__ void Sum(float* sum_p) {
    __shared__ float shared_vals[32];

    shared_vals[threadIdx.x] = threadIdx.x;
    float result = Shared_mem_sum(shared_vals);

    if (threadIdx.x == 0)
        *sum_p = result;
}
```

这个例子只启动：

```c
Sum<<<1, 32>>>(sum_p);
```

即：

- 1 个 block；
- 32 个线程；
- 恰好 1 个 warp；
- `shared_vals[0...31]` 保存 32 个线程的初始值

### 10.5.1 为什么叫"传播求和"

普通 `shfl_down` 归约通常只保证 `lane 0` 获得完整和；课件中的传播求和使用：

```c
source = (my_lane + diff) % warpSize;
```

每轮让每个 lane 从环形位置读取另一个线程的值每执行一轮，每个线程手里的结果包含的原始元素数量翻倍：

```text
初始：每个线程包含 1 个值
diff=16：每个线程包含 2 个值
diff=8 ：每个线程包含 4 个值
diff=4 ：每个线程包含 8 个值
diff=2 ：每个线程包含 16 个值
diff=1 ：每个线程包含 32 个值
```

最终不是只有 `lane 0`，而是理论上**每个 lane 都传播得到完整总和**，因此更接近一种 warp 内的 **all-reduce**

### 10.5.2 用 8 个线程演示

假设初始值为：

```text
[0, 1, 2, 3, 4, 5, 6, 7]
```

传播过程：

| 阶段 | 每个线程保存的代表性结果 |
|---|---|
| 初始 | `[0,1,2,3,4,5,6,7]` |
| `diff=4` | `[4,6,8,10,4,6,8,10]` |
| `diff=2` | `[12,16,12,16,12,16,12,16]` |
| `diff=1` | `[28,28,28,28,28,28,28,28]` |

因此最终每个线程都得到：

$$
0+1+2+3+4+5+6+7=28
$$

> [!note]+ 与普通树形归约的区别
> - **传播求和 / all-reduce**：所有 lane 最终都获得总和
> - **普通 reduction**：只需要一个代表线程获得总和，通常是 lane 0
> - 如果最终只有一个线程需要结果，普通 reduction 更省工作

## 10.6 代码的不足

示例体现的是共享内存传播求和的核心思想，但它隐含依赖**同一 warp 的同步执行**

现代 CUDA 中，为了让 shared memory 的跨线程读写更稳健，应显式考虑同步

对于同一个 warp，可以使用：

```c
__syncwarp(mask);
```

对于整个 block，则使用：

```c
__syncthreads();
```

更稳健的设计原则是：

```text
所有线程写入 shared memory
→ 同步
→ 所有线程读取上一阶段数据
→ 同步
→ 进入下一阶段
```

若只在单个 warp 内做归约，通常直接使用 `__shfl_down_sync` 更简单、更高效；**shared memory 的真正优势主要体现在==多个 warp 之间的 block 级通信==**

## 10.7 从 warp 归约扩展到 block 归约

假设一个 block 有 256 个线程：

```text
256 / 32 = 8 个 warp
```

第一次 warp 归约后，得到：

```text
warp 0 → W0
warp 1 → W1
...
warp 7 → W7
```

shuffle 不能跨 warp，因此需要把这些结果写入 shared memory：

**关键计算：**
1. warp = threadIdx.x / warpSize
2. lane = threadIdx.x % warpSize
3. id = threadIdx.x
```c
__shared__ float warp_sum[32];

int tid = threadIdx.x;
int lane = tid % warpSize;
int warp_id = tid / warpSize;

if (lane == 0)
    warp_sum[warp_id] = local_sum;
```

此时：

```text
warp_sum[0] = W0
warp_sum[1] = W1
...
warp_sum[7] = W7
```

然后必须同步：

```c
__syncthreads();
```

**再让第一个 warp 读取这些值**：

- 为什么用第一个warp而不是随便选一个？
	- 第一个warp的threadid刚好对应了0~31，每个thread拿一个值去shuffle求和
	- **一个 block 内最多1024个线程，所以最多 32 个 warp**

```c
int num_warps = (blockDim.x + warpSize - 1) / warpSize;

local_sum = (tid < num_warps) ? warp_sum[tid] : 0.0f;

if (tid < warpSize)
    local_sum = warpReduceSum(local_sum);
```

**最后：**

```c
if (tid == 0)
    atomicAdd(sum_p, local_sum);
```

## 10.8 完整的 thread → warp → block → global 归约

```c
__device__ float warpReduceSum(float value) {
    unsigned mask = 0xffffffff;

    for (int offset = warpSize / 2; offset > 0; offset /= 2)
        value += __shfl_down_sync(mask, value, offset);

    return value;
}

__global__ void Sum(const float a[], int n, float* sum_p) {
    int tid = threadIdx.x;
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    int stride = blockDim.x * gridDim.x;
    int total = n * n;

    float local_sum = 0.0f;

    // 每个线程先对自己负责的元素做局部累加
    for (int i = idx; i < total; i += stride)
        local_sum += a[i];

    // 第一级：warp 内归约
    local_sum = warpReduceSum(local_sum);

    // 每个 warp 的 lane 0 把 warp_sum 写入共享内存
    __shared__ float warp_sum[32];

    int lane = tid % warpSize;
    int warp_id = tid / warpSize;

    if (lane == 0)
        warp_sum[warp_id] = local_sum;

    __syncthreads();

    // 第二级：第一个 warp 读取所有 warp_sum
    int num_warps = (blockDim.x + warpSize - 1) / warpSize;

    if (tid < warpSize)
        local_sum = (tid < num_warps) ? warp_sum[tid] : 0.0f;

    // 第一个 warp 把多个 warp_sum 合并成 block_sum
    if (tid < warpSize)
        local_sum = warpReduceSum(local_sum);

    // 第三级：每个 block 只执行一次全局原子加
    if (tid == 0)
        atomicAdd(sum_p, local_sum);
}
```

执行层级：

```text
每个线程：计算 local_sum
        ↓
每个 warp：得到 warp_sum
        ↓
shared memory：保存同一 block 的所有 warp_sum
        ↓
第一个 warp：得到 block_sum
        ↓
每个 block 的 thread 0：atomicAdd 到 global sum
```

## 10.9 为什么不做 block 归约也能正确

简化版可以在每个 warp 得到 `warp_sum` 后，直接让每个 warp 的 lane 0 执行：

```c
atomicAdd(sum_p, warp_sum);
```

数学上：

```text
sum_p += W0
sum_p += W1
...
```

仍然能够得到正确总和，==**block 归约不是正确性的必要条件，而是性能优化**==：

| 方案 | 每个 256 线程 block 的 `atomicAdd` 次数 |
|---|---:|
| thread → warp → global | 8 次 |
| thread → warp → block → global | 1 次 |

当 block 有 256 个线程时，block 归约可以把全局原子操作次数减少到原来的 `1/8`

> [!summary]+ 本质区别
> - 不做 block 归约：每个 warp 直接把自己的和加到全局
> - 做 block 归约：先在 shared memory 中把同一 block 的多个 warp 和合并，再一次性加到全局
> - 两者都正确，后者通常具有更好的性能潜力

## 10.10 共享内存的 bank 与 bank conflict

shared memory 通常被划分为多个 bank一个 warp 中的线程若访问不同 bank，可以并行完成；若多个线程访问同一个 bank 的不同地址，访问可能被串行化，形成 **bank conflict**

适合的访问：

```text
lane 0 → shared[0]
lane 1 → shared[1]
...
lane 31 → shared[31]
```

这些连续访问通常能很好地分布到不同 bank

block 归约中：

```c
warp_sum[warp_id]
```

只由每个 warp 的 lane 0 写入；随后第一个 warp 连续读取 `warp_sum[0...num_warps-1]`，通常不会形成严重 bank conflict

> [!tip]+ 记忆
> global memory 关注 **合并访存 coalescing**；shared memory 关注 **bank conflict**

## 10.11 传播求和、warp 归约、block 归约对比

| 方法 | 通信介质 | 范围 | 最终谁有结果 | 是否需要同步 |
|---|---|---|---|---|
| shared memory 传播求和 | shared memory | 一个 warp | 通常所有 lane | 需要考虑 `__syncwarp` |
| `__shfl_down_sync` 归约 | 寄存器 shuffle | 一个 warp | 通常 lane 0 | 指令本身带同步掩码语义 |
| shared memory block 归约 | shared memory + shuffle | 一个 block | block 的 thread 0 | 需要 `__syncthreads` |
| `atomicAdd` 全局合并 | global memory 原子操作 | 所有 block | 全局变量 | 原子操作保证更新正确 |

## 10.12 常见误区

> [!warning]+ 易错点
> 1. `__shared__` 不是所有 block 共享，而是**每个 block 各有一份**
> 2. `__syncthreads()` 不能跨 block，只能同步一个 block
> 3. shuffle 不能跨 warp，更不能跨 block
> 4. local memory 名字虽然是 local，但通常位于显存，不等于寄存器
> 5. 不做 block 归约仍可正确，但会产生更多 `atomicAdd`
> 6. 共享内存归约必须确保"写入完成后再读取"，否则会出现数据竞争
> 7. 传播求和让多个 lane 都获得总和；普通 reduction 通常只保留一个结果
> 8. block 线程数不一定恰好是 32 的倍数，因此常用：
>
> ```c
> int num_warps = (blockDim.x + warpSize - 1) / warpSize;
> ```

## 10.13 期末考试答题模板

### 为什么 warp shuffle 后还需要 shared memory？

> `__shfl_down_sync` 只能在同一个 warp 内交换寄存器数据当一个 block 包含多个 warp 时，每个 warp 只能得到自己的局部和，无法直接读取其他 warp 的寄存器因此可由每个 warp 的 lane 0 把局部和写入 block 共享的 shared memory，经 `__syncthreads()` 同步后，再由第一个 warp完成第二次归约，从而得到整个 block 的局部和

### 为什么 block 归约可以减少原子操作？

> 若每个 warp 的 lane 0 都直接执行一次 `atomicAdd`，一个含 256 个线程的 block 有 8 个 warp，因此需要 8 次原子加若先用 shared memory 将 8 个 warp 的局部和归约成一个 block_sum，则每个 block 只需由 thread 0 执行一次 `atomicAdd`，从而减少全局原子竞争

### 简述 GPU 内存层次

> GPU 内存按照距离计算核心由近到远主要包括寄存器、共享内存/L1、L2 和全局内存寄存器为线程私有，速度最快；共享内存由同一个 block 的线程共享，位于 SM 片上，适合 block 内通信和数据复用；全局内存容量大、所有线程可访问，但延迟较高CUDA 优化通常应尽量提高寄存器与共享内存的利用率，减少对全局内存的频繁访问

## 10.14 最终总结

> [!abstract]+ 一句话串联
> shuffle 只能完成一个 warp 内的寄存器通信；shared memory 使同一个 block 内的多个 warp 能够交换局部结果；`__syncthreads()` 保证这些共享数据已经写完；第一个 warp 再把多个 `warp_sum` 合成 `block_sum`；最后由每个 block 的 thread 0 用 `atomicAdd` 汇入全局结果

```text
register：线程私有，最快
    ↓ warp shuffle
shared memory：block 共享，负责跨 warp 合并
    ↓ block reduction
global memory：整个 GPU 共享，负责跨 block 合并
```
