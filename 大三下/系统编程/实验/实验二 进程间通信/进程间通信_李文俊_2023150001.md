#### 1.4 使用 GDB 定位其他出错代码

除路径错误外，原程序还有几处运行时问题，也可以用 GDB 定位到具体代码行。

（1）定位 `SIGKILL` 处理无效。

原服务器代码在 `main()` 中注册了：

```c
signal(SIGKILL, handler);
```

在 GDB 中停在该行，并直接调用同样的系统函数：

```bash
gdb ./raw_calcserver_debug
(gdb) break raw/calcserver.c:44
(gdb) run
(gdb) list 42,46
(gdb) print (void (*)(int)) signal(SIGKILL, handler)
(gdb) print errno
```

观察到返回值为 `0xffffffffffffffff`，即 `SIG_ERR`；`errno` 为 22，表示参数无效。这说明 `SIGKILL` 不能被捕获、阻塞或忽略，给它注册处理函数没有效果。因此应删除 `signal(SIGKILL, handler)`，保留 `SIGINT`、`SIGTERM` 等可捕获信号即可。

图：`screenshots/09-gdb-sigkill-invalid.png`。

（2）定位客户端错误分支打印未初始化 `buffer`。

原客户端在创建私有 FIFO 失败时执行：

```c
printf("FIFO %s was not created\n", buffer);
```

但此时 `buffer` 尚未被赋值。为了稳定进入失败分支，GDB 停在 `mkfifo(mypipename, 0777)` 前，先手动调用一次 `mkfifo()` 创建同名 FIFO，再执行原代码中的 `mkfifo()`：

```bash
gdb ./raw_client_debug
(gdb) break raw/client.c:56
(gdb) run 12 + 30
(gdb) print mypipename
(gdb) call (int)mkfifo(mypipename, 0777)
(gdb) next
(gdb) print res
(gdb) print errno
(gdb) list 55,59
(gdb) print buffer
```

GDB 中可见第二次 `mkfifo()` 后 `res = -1`，`errno = 17`，表示 FIFO 已存在；同时 `list 55,59` 显示失败分支打印的是 `buffer`，而 `print buffer` 的结果是未初始化的乱码内容。因此这里应改为打印 `mypipename`，更稳妥的写法是 `perror(mypipename)`。

图：`screenshots/10-gdb-client-buffer-uninitialized.png`。

（3）定位服务器除零缺少保护。

原服务器 `calc()` 中除法分支为：

```c
case '/':
    return info->leftarg / info->rightarg;
```

在 GDB 中构造 `rightarg = 0` 的请求并调用 `calc()`：

```bash
gdb ./raw_calcserver_debug
(gdb) break raw/calcserver.c:31
(gdb) start
(gdb) set var info.leftarg = 81
(gdb) set var info.rightarg = 0
(gdb) set var info.op = '/'
(gdb) print info
(gdb) call calc(&info)
(gdb) list 29,32
```

GDB 停在 `return info->leftarg / info->rightarg;`，并且变量显示 `rightarg = 0`。这说明原程序在除数为 0 时仍直接执行除法，没有错误处理。修正时应在除法前判断 `info->rightarg == 0`，并返回 `Error: division by zero`。

图：`screenshots/11-gdb-division-by-zero-no-guard.png`。

（4）定位服务器只读打开 FIFO 后读到 EOF。

原服务器代码使用：

```c
fifo_fd = open(FIFO_NAME, O_RDONLY);
```

客户端发送请求并关闭写端后，服务器下一次 `read()` 可能返回 0。GDB 中在服务器 `read()` 行设置断点，另一个进程运行客户端：

```bash
gdb ./raw_calcserver_debug
(gdb) break raw/calcserver.c:72
(gdb) run
```

客户端执行一次 `./raw_client_debug 12 + 30` 后，服务器第一次 `read()` 返回完整结构体大小，第二次回到同一行再执行 `next`：

```bash
(gdb) next
(gdb) print res
(gdb) continue
(gdb) next
(gdb) print res
(gdb) list 59,74
```

GDB 中可见第一次 `res = 64`，说明读到了一个完整请求；客户端关闭后，第二次 `res = 0`，说明读到了 EOF。原代码只判断 `if (res != 0)`，没有专门处理 EOF，会导致服务器在循环中无意义空转。修正时将服务器公共 FIFO 改为 `O_RDWR` 打开，可以避免无写端时反复读到 EOF。

图：`screenshots/12-gdb-server-read-eof.png`。

#### 1.5 编译警告定位头文件问题

原程序使用 `mkfifo()`，但没有包含 `sys/stat.h`。使用如下命令编译原程序：

```bash
gcc -g -Wall -Wextra -o raw_calcserver raw/calcserver.c
gcc -g -Wall -Wextra -o raw_client raw/client.c
```

编译器会提示 `mkfifo` 隐式声明。这类问题属于编译阶段定位的问题，不需要通过运行时断点定位。修正方法是在 `calcserver.c` 和 `client.c` 中加入：

```c
#include <sys/stat.h>
```

#### 1.6 出错代码与修正方向总结

结合 GDB 输出、源代码行和编译警告，可定位出原程序存在以下问题：

- `calcserver.c` 中 `#define FIFO_NAME "/tmp/server_fifo"` 将公共 FIFO 放在 `/tmp`，不符合题目指定路径，应改为实验目录下的 `data/server_fifo/chat_server_fifo`。
- `client.c` 中 `sprintf(mypipename, "/tmp/client%d_fifo", getpid())` 将客户端私有 FIFO 放在 `/tmp`，不符合题目指定路径，应改为 `data/client_fifo/chat_client<PID>_fifo`。
- `calcserver.c` 和 `client.c` 缺少 `#include <sys/stat.h>`，导致 `mkfifo()` 在严格编译环境下可能出现隐式声明警告或错误。
- `client.c` 中 `printf("FIFO %s was not created\n", buffer)` 打印了未初始化的 `buffer`，应改为打印 `mypipename` 或使用 `perror(mypipename)`。
- `calcserver.c` 和 `client.c` 注册了 `signal(SIGKILL, handler)`，但 `SIGKILL` 不能被捕获、阻塞或忽略，应删除该无效处理。
- `calcserver.c` 中除法没有判断除数为 0，应在执行除法前返回错误信息。
- `calcserver.c` 中服务器只读打开公共 FIFO，不利于长期持续服务，应改为读写方式打开，避免无写端时读到 EOF。

#### 1.7 GDB 调试命令小结

本次调试中主要使用了以下 GDB 命令：

- `gcc -g3 -Wall -Wextra -o 程序名 源文件.c`：生成带调试信息的可执行文件。这里使用 `-g3`，是因为 `FIFO_NAME` 是宏定义，`-g3` 能保留宏调试信息，便于在 GDB 中使用 `info macro` 查看。
- `gdb ./程序名`：进入 GDB 调试环境。
- `break main`：在 `main()` 函数入口设置断点，使程序一开始就暂停，方便观察初始化代码。
- `break 文件名:行号`：在指定源文件的指定行设置断点。本实验在 `gdb_client.c:57` 设置断点，使程序停在 `mkfifo(mypipename, 0777)` 前，此时 `mypipename` 已经由上一行 `sprintf()` 生成。
- `run 参数1 参数2 ...`：带命令行参数运行程序。例如 `run 12 + 30` 用于模拟客户端执行 `./client 12 + 30`。
- `next`：单步执行下一行源代码，但不进入函数内部，适合按行观察主流程。
- `print 变量名`：打印普通变量的值。例如 `print mypipename` 可查看客户端私有 FIFO 路径。
- `info macro 宏名`：查看宏定义内容。例如 `info macro FIFO_NAME` 可观察原程序中公共 FIFO 被定义为 `/tmp/server_fifo`。
- `list 起始行,结束行`：显示指定范围源代码，用于把 GDB 停住的位置和具体出错代码行对应起来。
- `set var 变量 = 值`：临时修改被调试程序中的变量值。本实验用它构造 `rightarg = 0` 的除法请求。
- `call 函数(参数)`：在 GDB 中主动调用被调试程序可见的函数。本实验用 `call calc(&info)` 进入服务器计算函数，也用 `call (int)mkfifo(mypipename, 0777)` 人为制造 FIFO 已存在的错误场景。
- `quit`：退出 GDB。若程序仍在调试运行，GDB 会提示是否结束被调试进程，输入 `y` 确认。

### 2. FIFO 计算客户端-服务器代码修正

#### 2.1 程序设计

修正后的程序仍采用“公共 FIFO + 私有 FIFO”的结构。服务器创建一个公共 FIFO 接收所有客户端请求，客户端创建自己的私有 FIFO 接收服务器返回结果。

公共 FIFO 路径为：

```text
/home/szu/liwenjun2023150001/chatapplication/data/server_fifo/chat_server_fifo
```

客户端私有 FIFO 路径格式为：

```text
/home/szu/liwenjun2023150001/chatapplication/data/client_fifo/chat_client<PID>_fifo
```

客户端向服务器发送的数据结构如下：

```c
typedef struct
{
    char myfifo[CLIENT_FIFO_NAME_LEN];
    int leftarg;
    int rightarg;
    char op;
} CLIENTINFO, *CLIENTINFOPTR;
```

其中 `myfifo` 保存客户端私有 FIFO 路径，`leftarg` 和 `rightarg` 保存操作数，`op` 保存运算符。

#### 2.2 逐项修改说明

根据 GDB 定位到的问题，对原始 FIFO 计算程序做了以下修改。

修改一：补充头文件。

- 修改位置：`calcserver.c`、`client.c`。
- 修改原因：原程序使用 `mkfifo()`，该函数声明位于 `sys/stat.h`。缺少该头文件时，在严格编译环境下会出现 `mkfifo` 隐式声明警告或错误。
- 修改内容：加入：

```c
#include <sys/stat.h>
```

修改二：集中定义实验目录和 FIFO 路径。

- 修改位置：`clientinfo.h`。
- 修改原因：原程序把公共 FIFO 和客户端私有 FIFO 放在 `/tmp` 下，不符合实验要求，也不方便统一维护。
- 修改内容：将公共 FIFO、客户端 FIFO 模板和目录路径统一定义为：

```c
#define CALC_USER_HOME "/home/szu/liwenjun2023150001"
#define CALC_APP_DIR CALC_USER_HOME "/chatapplication"
#define CALC_DATA_DIR CALC_APP_DIR "/data"
#define CALC_SERVER_FIFO_DIR CALC_DATA_DIR "/server_fifo"
#define CALC_CLIENT_FIFO_DIR CALC_DATA_DIR "/client_fifo"

#define FIFO_NAME CALC_SERVER_FIFO_DIR "/chat_server_fifo"
#define CLIENT_FIFO_TEMPLATE CALC_CLIENT_FIFO_DIR "/chat_client%d_fifo"
```

修改三：扩大 `CLIENTINFO.myfifo` 的长度。

- 修改位置：`clientinfo.h`。
- 修改原因：原程序中 `myfifo[50]` 对 `/tmp/client<PID>_fifo` 足够，但对实验要求的绝对路径可能不够，存在字符串截断风险。
- 修改内容：增加 `CLIENT_FIFO_NAME_LEN`，并将结构体字段改为：

```c
#define CLIENT_FIFO_NAME_LEN 256

typedef struct
{
    char myfifo[CLIENT_FIFO_NAME_LEN];
    int leftarg;
    int rightarg;
    char op;
} CLIENTINFO, *CLIENTINFOPTR;
```

修改四：自动创建实验目录。

- 修改位置：`calcserver.c`、`client.c`。
- 修改原因：若 `data/server_fifo` 或 `data/client_fifo` 不存在，`mkfifo()` 会失败。自动创建目录可以减少手工准备步骤。
- 修改内容：增加 `ensure_dir()`、`prepare_fifo()` 或 `prepare_dirs()`，启动时依次创建用户目录、应用目录、数据目录、服务器 FIFO 目录和客户端 FIFO 目录。

修改五：去掉无效的 `SIGKILL` 处理。

- 修改位置：`calcserver.c`、`client.c`。
- 修改原因：`SIGKILL` 不能被捕获、阻塞或忽略，给它注册处理函数没有效果。
- 修改内容：保留 `SIGINT`、`SIGTERM`、`SIGHUP` 的清理处理，删除 `signal(SIGKILL, handler)`。

修改六：增加资源清理函数。

- 修改位置：`calcserver.c`、`client.c`。
- 修改原因：程序异常退出或按 `Ctrl+C` 结束时，应关闭文件描述符并删除 FIFO，避免遗留无用管道文件。
- 修改内容：服务器使用 `cleanup()` 关闭公共 FIFO 并删除服务器 FIFO；客户端使用 `cleanup()` 关闭私有 FIFO 并删除自己的 FIFO。

修改七：服务器以读写方式打开公共 FIFO。

- 修改位置：`calcserver.c`。
- 修改原因：原程序用 `O_RDONLY` 打开公共 FIFO，当没有客户端写入端时可能读到 EOF，不利于长期持续运行。
- 修改内容：将：

```c
fifo_fd = open(FIFO_NAME, O_RDONLY);
```

改为：

```c
fifo_fd = open(FIFO_NAME, O_RDWR);
```

修改八：增加除零和非法运算符处理。

- 修改位置：`calcserver.c`。
- 修改原因：原程序直接执行除法，若右操作数为 0 会触发错误；非法运算符也没有明确提示。
- 修改内容：

```c
case '/':
    if (info->rightarg == 0)
    {
        snprintf(buffer, size, "Error: division by zero");
        return;
    }
    result = info->leftarg / info->rightarg;
    break;
default:
    snprintf(buffer, size, "Error: unsupported operator '%c'", info->op);
    return;
```

修改九：客户端使用实验目录生成私有 FIFO。

- 修改位置：`client.c`。
- 修改原因：原程序使用 `/tmp/client<PID>_fifo`，不符合实验要求。
- 修改内容：将：

```c
sprintf(mypipename, "/tmp/client%d_fifo", getpid());
```

改为：

```c
snprintf(mypipename, sizeof(mypipename), CLIENT_FIFO_TEMPLATE, getpid());
```

修改十：修正客户端错误输出。

- 修改位置：`client.c`。
- 修改原因：原程序在 `mkfifo()` 失败时打印未初始化的 `buffer`，错误信息不可靠。
- 修改内容：将错误输出改为 `perror(mypipename)`，直接显示创建失败的 FIFO 路径和系统错误原因。

修改十一：客户端增加参数和运算符校验。

- 修改位置：`client.c`。
- 修改原因：原程序只检查参数个数，未检查运算符是否合法。
- 修改内容：增加 `parse_args()`，要求运算符只能是 `+`、`-`、`*`、`/`。

修改十二：客户端轮询读取时处理可重试错误。

- 修改位置：`client.c`。
- 修改原因：客户端以 `O_NONBLOCK` 打开私有 FIFO，暂时没有数据时 `read()` 可能返回 `EAGAIN` 或 `EWOULDBLOCK`，这不是致命错误。
- 修改内容：读取循环中忽略 `EAGAIN`、`EWOULDBLOCK`、`EINTR`，并用 `usleep(10000)` 降低空转消耗。

### 3. Server 与 Client 行为及交互分析

#### 3.1 Server 行为分析

修正后的 `calcserver` 是一个长期运行的服务器进程。启动后，它首先保证实验目录和 FIFO 目录存在，然后创建公共 FIFO：

```text
/home/szu/liwenjun2023150001/chatapplication/data/server_fifo/chat_server_fifo
```

服务器使用 `open(FIFO_NAME, O_RDWR)` 打开公共 FIFO，并进入无限循环。每次循环中，服务器从公共 FIFO 读取一个 `CLIENTINFO` 请求包。该结构体中包含客户端私有 FIFO 路径、左操作数、右操作数和运算符。服务器读取到完整请求后，根据运算符完成计算，再用 `open(info.myfifo, O_WRONLY | O_NONBLOCK)` 打开对应客户端的私有 FIFO，把结果字符串写回客户端。

服务器端在交互中承担三个职责：一是提供固定的公共 FIFO 入口；二是解析和计算客户端请求；三是根据请求包中的 `myfifo` 字段把结果定向返回给发起请求的客户端。

#### 3.2 Client 行为分析

修正后的 `client` 是一次请求、一次响应的客户端进程。客户端启动后先解析命令行参数，例如：

```bash
./client 3 + 45
```

随后客户端根据自己的进程 id 生成私有 FIFO 路径：

```text
/home/szu/liwenjun2023150001/chatapplication/data/client_fifo/chat_client<PID>_fifo
```

客户端创建并打开该私有 FIFO，用于等待服务器返回结果。然后客户端构造 `CLIENTINFO` 请求包，将自己的私有 FIFO 路径、操作数和运算符写入服务器公共 FIFO。写入完成后，客户端关闭公共 FIFO 写端，转而从私有 FIFO 中等待服务器回复。收到结果后，客户端打印结果、关闭私有 FIFO，并删除该私有 FIFO 文件。

客户端端在交互中承担三个职责：一是为本次请求创建唯一的返回通道；二是把请求写入服务器公共 FIFO；三是从自己的私有 FIFO 接收服务器返回值并清理资源。

实际输出如下：

```text

  File: /home/szu/liwenjun2023150001/chatapplication/data/server_fifo/chat_server_fifo

```

字段含义如下：

- `p`：`ls -l` 第一列第一个字符为 `p`，表示该文件类型是 FIFO 命名管道，而不是普通文件或目录。
- `rw-r--r--`：表示 FIFO 文件节点的权限。所有者可读写，同组用户和其他用户可读。实际通信还需要进程以合适方式调用 `open/read/write`。
- `1` 或 `Links: 1`：表示该 FIFO 目录项的硬链接数，通常为 1。
- `szu szu` 或 `Uid/Gid`：表示 FIFO 的所有者和所属用户组。
- `Size: 0`：FIFO 不像普通文件那样把数据保存在磁盘文件内容中，消息在内核缓冲区中临时传递，因此大小通常显示为 0。
- `Blocks: 0`：表示该 FIFO 没有占用普通文件数据块。
- `IO Block: 4096`：表示文件系统建议的 I/O 块大小，不代表 FIFO 中实际保存了 4096 字节数据。
- `fifo`：`stat` 输出的文件类型，明确说明该路径是命名管道。
- `Device` 和 `Inode`：分别表示所在设备号和 inode 编号，用于在文件系统中唯一标识该目录项。
- `Access/Modify/Change`：分别表示最近访问时间、内容修改时间和状态改变时间。FIFO 创建、权限或元数据变化会影响这些时间字段。
- `Birth: -`：表示当前文件系统或环境没有提供创建时间。

### 4. signals-hw2.c 信号实验

#### 4.1 borkfork

`borkfork()` 中宏 `#define bork fork` 使程序连续执行三次 `fork()`。每一次 `fork()` 都会让父子进程继续执行后续代码，因此最终共有 `2^3 = 8` 个进程执行 `printf("borked\n")`。

运行：

```bash
./signals-hw2 borkfork
```

预期输出 8 行 `borked`，顺序由进程调度决定。

#### 4.2 fork1

`fork1()` 创建 5 个子进程，每个子进程进入死循环。父进程随后对每个子进程发送 `SIGINT`。由于没有自定义 `SIGINT` 处理函数，子进程按默认动作异常终止，父进程使用 `wait()` 回收子进程。

运行：

```bash
./signals-hw2 1
```

预期打印 5 行 `Killing process <PID>` 和 5 行 `Child <PID> terminated abnormally`。

#### 4.3 fork2

`fork2()` 在 `fork()` 前注册 `SIGINT` 处理函数。子进程会继承该信号处理设置，因此收到 `SIGINT` 后进入 `int_handler()`，打印信号编号并调用 `exit(0)` 正常退出。

运行：

```bash
./signals-hw2 2
```

预期子进程打印 `Process <PID> received signal 2`，父进程回收时打印正常退出状态 0。

#### 4.4 fork3

`fork3()` 使用 `SIGCHLD` 处理函数回收子进程，但处理函数每次只调用一次 `wait()`。5 个子进程几乎同时退出时，多个 `SIGCHLD` 可能合并为较少的 pending signal。由于标准信号不排队，父进程可能只回收到部分子进程，导致 `ccount` 不能降到 0，程序停在 `pause()`。

运行：

```bash
./signals-hw2 3
```

预期可能只打印少于 5 行 `Received SIGCHLD signal 17 for process <PID>` 后暂停，需要按 `Ctrl+C` 结束。该现象说明普通信号不保证逐个排队。

#### 4.5 fork4

`fork4()` 使用 `child_handler2()`，在信号处理函数中通过循环 `wait()` 回收所有已经终止的子进程。因此即使多个 `SIGCHLD` 合并，处理函数仍能一次回收多个子进程，使 `ccount` 最终降为 0。

运行：

```bash
./signals-hw2 4
```

预期打印 5 行 `Received signal 17 from process <PID>` 并正常退出。

### 5. 多用户聊天系统

#### 5.1 通信模型

多用户聊天系统采用一个服务器和多个客户端进程。服务器创建 3 个公共 FIFO：

```text
/home/szu/liwenjun2023150001/chatapplication/data/server_fifo/FIFO_1
/home/szu/liwenjun2023150001/chatapplication/data/server_fifo/FIFO_2
/home/szu/liwenjun2023150001/chatapplication/data/server_fifo/FIFO_3
```

其中 `FIFO_1` 接收注册请求，`FIFO_2` 接收登录请求，`FIFO_3` 接收聊天请求。每个客户端以用户名创建自己的私有 FIFO，例如：

```text
/home/szu/liwenjun2023150001/chatapplication/data/client_fifo/alice
/home/szu/liwenjun2023150001/chatapplication/data/client_fifo/bob
```

服务器使用 `select()` 同时监听 3 个公共 FIFO。收到注册请求时检查用户名是否重复；收到登录请求时检查用户名和密码；收到聊天请求时查找接收方，并将消息写入接收方的私有 FIFO。

#### 5.2 数据结构说明

聊天系统把公共路径、长度限制和通信结构体统一放在 `chat_common.h` 中，这样服务器和客户端编译时使用同一套协议定义，避免双方对 FIFO 路径或结构体大小理解不一致。

路径宏定义如下：

```c
#define CHAT_USER_HOME "/home/szu/liwenjun2023150001"
#define CHAT_APP_DIR CHAT_USER_HOME "/chatapplication"
#define CHAT_DATA_DIR CHAT_APP_DIR "/data"
#define CHAT_SERVER_FIFO_DIR CHAT_DATA_DIR "/server_fifo"
#define CHAT_CLIENT_FIFO_DIR CHAT_DATA_DIR "/client_fifo"

#define CHAT_FIFO_REGISTER CHAT_SERVER_FIFO_DIR "/FIFO_1"
#define CHAT_FIFO_LOGIN CHAT_SERVER_FIFO_DIR "/FIFO_2"
#define CHAT_FIFO_MESSAGE CHAT_SERVER_FIFO_DIR "/FIFO_3"
```

`CHAT_FIFO_REGISTER`、`CHAT_FIFO_LOGIN`、`CHAT_FIFO_MESSAGE` 分别对应注册、登录和聊天消息 3 个公共 FIFO。客户端不共用返回 FIFO，而是在 `client_fifo` 目录下按用户名创建私有 FIFO，例如 `alice` 客户端对应 `/home/szu/liwenjun2023150001/chatapplication/data/client_fifo/alice`。这样服务器可以根据用户表中保存的 FIFO 路径，把回复或聊天消息定向写回某一个客户端。

注册和登录请求共用 `ChatAuthRequest`：

```c
typedef struct
{
    char username[CHAT_NAME_LEN];
    char password[CHAT_PASSWORD_LEN];
    char fifo[CHAT_FIFO_PATH_LEN];
} ChatAuthRequest;
```

其中 `username` 保存用户名，`password` 保存密码，`fifo` 保存该客户端私有 FIFO 路径。注册时服务器根据 `username` 判断是否重复，并保存 `password` 和 `fifo`；登录时服务器根据 `username` 找到用户，再比较 `password`，登录成功后刷新该用户的 `fifo` 并把在线状态置为 1。注册和登录能共用该结构体，是因为这两种请求都需要身份信息和回包地址。

聊天请求使用 `ChatSendRequest`：

```c
typedef struct
{
    char from[CHAT_NAME_LEN];
    char to[CHAT_NAME_LEN];
    char text[CHAT_TEXT_LEN];
} ChatSendRequest;
```

`from` 表示发送者，`to` 表示接收者，`text` 表示聊天内容。服务器收到该结构体后，先在用户表中检查 `from` 是否存在并在线，再检查 `to` 是否存在并在线，最后把消息封装成服务器到客户端的统一数据包，写入接收方私有 FIFO。

服务器写回客户端的包统一使用 `ChatPacket`：

```c
typedef enum
{
    CHAT_PACKET_REPLY = 1,
    CHAT_PACKET_MESSAGE = 2
} ChatPacketType;

typedef struct
{
    int type;
    int ok;
    char from[CHAT_NAME_LEN];
    char message[CHAT_TEXT_LEN];
} ChatPacket;
```

`type` 用来区分数据包类型。`CHAT_PACKET_REPLY` 表示服务器对注册、登录或发送消息操作的确认或错误提示，此时 `ok` 为 1 表示成功，为 0 表示失败，`message` 保存提示内容。`CHAT_PACKET_MESSAGE` 表示其他用户发来的聊天消息，此时 `from` 保存发送者用户名，`message` 保存正文。客户端收到 `ChatPacket` 后只需要根据 `type` 选择不同打印格式。

服务器内部还定义了用户表结构体：

```c
typedef struct
{
    char username[CHAT_NAME_LEN];
    char password[CHAT_PASSWORD_LEN];
    char fifo[CHAT_FIFO_PATH_LEN];
    int online;
} User;
```

`User` 不需要被客户端看到，只在服务器内维护。`username` 和 `password` 用于身份校验，`fifo` 用于记录用户当前客户端的私有 FIFO，`online` 用于判断能否接收消息。服务器用 `users[CHAT_MAX_USERS]` 保存最多 64 个用户，并用 `user_count` 记录当前已注册用户数量。服务器还使用 `read_fds[3]` 保存 3 个公共 FIFO 的读端，用 `hold_fds[3]` 保存对应写端；保留写端可以避免公共 FIFO 在没有客户端写入时反复读到 EOF，从而让 `select()` 监听更稳定。

#### 5.3 client 实现思路

客户端程序的核心职责是：创建自己的私有 FIFO，向服务器公共 FIFO 发送请求，同时监听键盘输入和服务器写回的消息。

第一步是初始化身份和目录。`main()` 要求命令行参数为 `username password`，先调用 `valid_username()` 限制用户名只能包含字母、数字、下划线和短横线，避免用户名中包含 `/` 等字符导致私有 FIFO 路径被错误拼接。随后调用 `ensure_tree()` 创建实验要求的目录树：

```c
ensure_dir(CHAT_USER_HOME);
ensure_dir(CHAT_APP_DIR);
ensure_dir(CHAT_DATA_DIR);
ensure_dir(CHAT_SERVER_FIFO_DIR);
ensure_dir(CHAT_CLIENT_FIFO_DIR);
```

第二步是创建并打开客户端私有 FIFO。`prepare_client_fifo()` 使用

```c
snprintf(myfifo, sizeof(myfifo), "%s/%s", CHAT_CLIENT_FIFO_DIR, username);
mkfifo(myfifo, 0600);
```

生成当前客户端的私有 FIFO 路径。随后客户端以 `O_RDONLY | O_NONBLOCK` 打开读端，保存到 `fifo_fd`，用于读取服务器回复；同时再以 `O_WRONLY | O_NONBLOCK` 打开一次写端，保存到 `hold_fd`。保留 `hold_fd` 的作用是让客户端自己的 FIFO 始终存在一个写端，避免服务器暂时没有写入者时客户端读端出现 EOF 并影响监听流程。退出时 `cleanup()` 会关闭两个文件描述符并 `unlink(myfifo)` 删除私有 FIFO。

第三步是根据用户命令构造请求。客户端支持 4 个交互命令：

```text
/register
/login
/send <user> <text>
/quit
```

`/register` 和 `/login` 都调用 `send_auth_request()`，只是写入的公共 FIFO 不同：注册写入 `CHAT_FIFO_REGISTER`，登录写入 `CHAT_FIFO_LOGIN`。`send_auth_request()` 会把当前 `username`、`password`、`myfifo` 填入 `ChatAuthRequest`。`/send` 由 `handle_line()` 解析出目标用户名和消息正文，再调用 `send_chat_request()` 生成 `ChatSendRequest` 并写入 `CHAT_FIFO_MESSAGE`。底层统一由 `write_request()` 打开指定公共 FIFO，并把整个结构体一次写入。

第四步是使用 `select()` 同时等待键盘和服务器回复。客户端主循环把 `STDIN_FILENO` 和 `fifo_fd` 都加入读集合：

```c
FD_SET(STDIN_FILENO, &rfds);
FD_SET(fifo_fd, &rfds);
select(maxfd + 1, &rfds, NULL, NULL, NULL);
```

如果键盘可读，说明用户输入了命令，程序读取一行后交给 `handle_line()` 解析；如果私有 FIFO 可读，说明服务器写回了 `ChatPacket`，程序调用 `drain_packets()` 循环读取所有已到达的数据包。`print_packet()` 根据 `packet->type` 判断显示格式：服务器回复打印为 `[server] OK/ERROR: ...`，聊天消息打印为 `[发送者] 消息内容`。因此客户端既能主动输入命令，也能异步收到其他用户发来的消息。

#### 5.4 server 实现思路

服务器程序的核心职责是：创建 3 个公共 FIFO，维护用户表，用 `select()` 监听注册、登录和聊天请求，并根据请求类型完成校验和转发。

第一步是创建目录和公共 FIFO。服务器启动后调用 `ensure_tree()` 确保实验目录存在，然后分别调用：

```c
open_server_fifo(CHAT_FIFO_REGISTER, 0);
open_server_fifo(CHAT_FIFO_LOGIN, 1);
open_server_fifo(CHAT_FIFO_MESSAGE, 2);
```

`open_server_fifo()` 内部先用 `ensure_fifo()` 检查路径是否已经是 FIFO，不存在时用 `mkfifo(path, 0666)` 创建。之后服务器以 `O_RDONLY | O_NONBLOCK` 打开读端保存到 `read_fds[index]`，再以 `O_WRONLY | O_NONBLOCK` 打开写端保存到 `hold_fds[index]`。这样服务器可以长期监听公共 FIFO，不会因为暂时没有客户端写入而读到 EOF 后退出。

第二步是事件分派。服务器主循环把 3 个公共 FIFO 的读端全部加入 `select()`：

```c
FD_SET(read_fds[0], &rfds);
FD_SET(read_fds[1], &rfds);
FD_SET(read_fds[2], &rfds);
select(maxfd + 1, &rfds, NULL, NULL, NULL);
```

当 `read_fds[0]` 可读时调用 `drain_auth_fifo(read_fds[0], 1)` 处理注册；当 `read_fds[1]` 可读时调用 `drain_auth_fifo(read_fds[1], 0)` 处理登录；当 `read_fds[2]` 可读时调用 `drain_chat_fifo(read_fds[2])` 处理聊天消息。`drain_auth_fifo()` 和 `drain_chat_fifo()` 都使用循环读取，直到非阻塞读返回 `EAGAIN` 或 `EWOULDBLOCK`，这样可以一次处理完当前 FIFO 中积压的多个请求。

第三步是注册处理。`handle_register()` 先检查用户名和密码是否为空，再调用 `find_user()` 查找用户名是否已存在。如果用户不存在且用户表未满，就把用户名、密码、客户端私有 FIFO 保存到 `users[user_count]`，将 `online` 初始化为 0，再递增 `user_count`。注册成功后，服务器调用 `reply_to_fifo(req->fifo, 1, "register ok")` 给客户端返回成功信息；如果用户名重复，则返回 `username already exists`。

第四步是登录处理。`handle_login()` 先通过 `find_user(req->username)` 查找用户。如果用户不存在，返回 `username does not exist`；如果密码不匹配，返回 `password is incorrect`；如果校验通过，则把用户表中的 `fifo` 更新为本次登录客户端的私有 FIFO，并把 `online` 设置为 1。这样同一个用户重新运行客户端后，服务器仍能把消息发到最新的 FIFO。

第五步是聊天转发。`handle_chat()` 先查找发送者和接收者：

```c
int from_index = find_user(req->from);
int to_index = find_user(req->to);
```

如果发送者不存在或未在线，服务器直接忽略该非法请求；如果接收者不存在，向发送者返回 `target user does not exist`；如果接收者存在但未在线，返回 `target user is not online`。当双方都在线时，服务器用 `make_packet(&packet, CHAT_PACKET_MESSAGE, 1, req->from, req->text)` 构造聊天数据包，并调用 `send_packet(users[to_index].fifo, &packet)` 写入接收者私有 FIFO。写入成功后，服务器再向发送者返回 `message sent to <user>`，表示这条消息已被服务器转发。

服务器退出时由 `cleanup()` 关闭所有公共 FIFO 的读写文件描述符，并删除 `FIFO_1`、`FIFO_2`、`FIFO_3`。因此再次运行服务器时可以重新创建干净的公共 FIFO。

## 五、实验总结与体会

本次实验首先通过 GDB 调试原始程序，体会到系统编程中路径、头文件、信号和异常处理等细节会直接影响程序能否稳定运行。GDB 不只是用来查看崩溃位置，也可以用来观察宏、全局变量和运行时生成的字符串，从而定位程序逻辑是否符合实验要求。

FIFO 计算客户端-服务器实验说明了公共 FIFO 和私有 FIFO 的职责划分：公共 FIFO 适合接收请求，私有 FIFO 适合定向返回结果。如果所有客户端共用一个返回 FIFO，多个客户端同时运行时会出现响应归属不清的问题，因此使用 PID 生成客户端私有 FIFO 是更合理的设计。

信号实验展示了异步事件处理和普通函数调用的区别。`SIGINT` 默认会终止进程，但注册处理函数后可以转换为受控退出；`SIGCHLD` 则说明标准信号不排队，如果处理函数只回收一个子进程，就可能因为信号合并而遗漏子进程。因此处理子进程退出时应尽量循环调用 `wait()` 或 `waitpid()`，避免僵尸进程和状态计数不一致。

多用户聊天系统进一步体现了服务器在并发通信中的调度作用。服务器通过 `select()` 同时监听注册、登录和聊天三个 FIFO，用用户表保存用户名、密码、私有 FIFO 和在线状态，从而完成身份校验、消息路由和错误响应。虽然该系统仍是简单的单机单服务器模型，但已经包含客户端-服务器通信的核心结构。
