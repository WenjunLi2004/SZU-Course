## 1. 从 printf 到 write

### 我的理解
系统调用是用户程序进入内核、==**请求操作系统服务**==的受控入口
它的意义有三层：  
**第一，保护**：用户态程序不能直接操作硬件、内存、进程等受保护资源，必须通过系统调用让内核检查权限并代为执行。  
**第二，管理**：内核统一管理 CPU、内存、文件、设备等资源，**系统调用是用户程序申请或使用这些资源的方式**。 
**第三，抽象**：内核把**复杂且不同的底层资源**抽象成统一接口，例如<u>文件、终端、管道</u>都可以通过文件描述符和 read/write 操作


**以最经典的printf为例子串联起 ==用户态 -> 内核态== 的完整链路**

#### **误区例子1：printf 并非直接写屏幕**
一开始啥都不懂，只知道 printf 直接把字符串发到屏幕

然后了解到抽象这个概念后，再结合操作系统的文件描述符和管道，认为printf 默认的文件描述符 1 标准输出会指向终端，而通过改变文件描述符，可以输出到不同对象中

##### 更准确理解

- **关于printf**：`printf` 默认写的是 C 标准库里的 `stdout`「用户态缓冲区」，**而 `stdout` 底层通常关联到文件描述符 `1`**

也就是：

	printf()
	  ↓
	stdout：C 库层面的标准输出流对象
	  ↓
	stdout：内部管理一个用户态缓冲区，通常关联文件描述符1
	  ↓
	write(1, ...)  
	  ↓
	fd = 1：Linux 内核层面的文件描述符
	  ↓
	终端 / 文件 / 管道

- **关于文件描述符**：不是改变"1 这个数字"，而是改变**当前进程的 fd 表**中，**文件描述符 1 指向的对象**
	- 1 确实是标准输出，只是它默认指向终端，之前固有地理解为标准输出就是终端
	- **shell** 可以在程序启动前**改变 fd 1 的指向**：普通运行时 fd 1 指向终端，重定向时 fd 1 指向文件，管道时 fd 1 指向管道写端。内核把终端、文件、管道等不同对象统一抽象成"可读写的文件描述符对象"，所以同一句 `printf` 可以输出到不同目标。

#### 误区例子2：printf 和 write 混用时，输出顺序可能变化

```c
printf("A");
write(1, "B", 1);
printf("C\n");
```

按理来说确实顺序执行，应该输出 ABC

##### **常见误区：**

> **程序语句顺序执行，不等于每一句的效果都会立刻出现在终端/文件里**


关键区别是：
1. printf()：C 标准库函数，使用 stdout 缓冲区
   ==**printf返回说明它把 `A` 交给了 `stdout` 流，不代表它已经调用了 `write()` 写到终端**==
2. write()：系统调用，直接向文件描述符 1 写数据

**这就是之前OS实验遇到的问题：为什么必须调用`fflush(stdout);`**

*当 `stdout` 连接到终端时，C 标准库通常采用行缓冲，遇到 `\n` 时可能刷新缓冲区。  
如果 `stdout` 被重定向到文件，则通常变成全缓冲，不一定遇到每个 `\n` 都立刻刷新*

如果你想强制得到 `ABC`，应该这样：

```c
printf("A");
fflush(stdout);
write(1, "B", 1);
printf("C\n");
```

**`fflush(stdout)` 的作用就是：立刻把 `stdout` 缓冲区里的内容刷出去**

##### 结论

> `printf` 是"先写到用户态缓冲区"；  
> `write` 是"直接请求内核写 fd"；  
> 混用二者时，如果不 `fflush`，输出顺序可能和代码顺序不一致
#### fork 会复制未刷新的 stdout 缓冲区
```c
printf("A");
fork();
printf("B\n");
```

乍一看fork感觉也和printf没啥关系，所以觉得输出为
AB
B

**实际运行输出：**
`AB`
`AB`

##### 为什么不是一个 A？
1. 关键还是因为没有 `\n`，所以 `A` 很可能还没有真正输出到终端，而是==**留在**== `stdout` 的用户态缓冲区里
2. `fork()` 后**输出缓冲区也会作为资源被子进程继承**，此时父子进程缓冲区都有A了
3. 最后遇到`\n` 后，各自把自己的缓冲区刷出去，都输出`AB`

完整链路：

	你的 C 程序  
	↓  
	printf()：C 标准库函数，属于 libc  
	↓  
	stdout 缓冲区：先把 hello\n 放到用户态缓冲区  
	↓  
	write(1, "hello\n", 6)：真正请求内核输出  
	↓  
	系统调用入口：CPU 从用户态切到内核态  
	↓  
	内核检查文件描述符 1 指向哪里  
	↓  
	发现 fd=1 通常指向终端 / 伪终端 / 文件 / 管道  
	↓  
	如果是终端，就交给终端驱动或伪终端设备  
	↓  
	终端程序把字符画到窗口里

## 2. 进程是什么？

### 我的理解

进程是程序运行的一个实例
- 程序：静态可执行文件
- 进程：程序的动态执行
	- **独立的进程地址空间**

之前一直overlook的一个点：**进程到底拥有什么？**

**需要回答的问题：**
1. **为什么 fork 后全局变量各自一份？** 
2. **为什么 fork 后文件描述符会被继承？**  
3. **为什么 printf 缓冲区也会被继承？**  
4. **为什么子进程退出后可能变成僵尸？**  
5. **为什么父进程可以 wait 子进程？**  
6. **为什么守护进程要 setsid？**  
7. **为什么管道可以让两个进程通信？**

#### 我的回答
fork会继承父进程的用户态地址空间，里面包含了全局变量和printf缓冲区，同时继承资源引用，包含了文件描述符

> **疑问：fork是否会继承父进程所拥有的一切资源** -> ## 3 中解答

父进程如果没有在子进程退出前回收子进程的资源，那么这个资源就会一直在待在内核中变成僵尸；相反如果父进程比子进程早退出，子进程会变成孤儿进程
- 为了防止变成僵尸进程，所以需要父进程wait

#### 纠正和解答

### 2.1 进程到底包含什么？
一个进程大致可以分成四层：

进程
├── 1. **用户态地址空间**
├── 2. **内核维护的进程控制信息**
├── 3. 打开的资源引用
└── 4. 当前执行状态

#### 1. 用户态地址空间
进程"自己能看到的**内存世界**"
- 代码段 text
- 只读数据 rodata
- 全局变量 / 静态变量 data、bss
- 堆、栈
- 共享库映射区
- stdio 缓冲区 「printf缓冲区就在这里」

`fork()` 后，==**父子进程拥有各自独立的虚拟地址空间**==

#### 2. 内核维护的进程控制信息
这部分用户程序不能直接访问，由内核维护
**核心就是 PCB**，在 Linux 里大致对应 `task_struct`

OS 课里讲的 PCB：
```
PID
PPID
进程状态
调度信息
优先级
寄存器上下文
信号处理信息
进程组 PGID
会话 SID
用户权限 UID/GID
```
#### 3. 打开的资源引用
每个进程都有自己的**文件描述符表**

比如：
```
fd 0 -> 标准输入
fd 1 -> 标准输出
fd 2 -> 标准错误
fd 3 -> 某个打开的文件
fd 4 -> 某个管道读端
fd 5 -> 某个管道写端
```

#### 4. 当前执行状态
进程还必须有"**现在执行到哪里了**"的信息

包括：
```
程序计数器 PC
CPU 寄存器
栈帧
当前处于运行、就绪、阻塞、僵尸等状态
```


## 3. fork到底做了什么？
非常有意思的一部分

**fork调用的一瞬间**：
- 父进程：从 fork 返回了，继续往下执行 「返回值是**子进程的pid**」
- 子进程：也从 fork 返回了，继续往下执行 「返回值是**0**」

> 因此，fork()其实是调用一次，但返回两次

**此时父子进程拥有几乎一模一样的资源，到底怎么理解子进程继承了多大程度的父进程拥有的资源？**

### 疑惑解答

`fork()` 会让子进程**继承**父进程的运行现场。父子进程从 `fork()` 之后分别作为两个独立进程运行，拥有**独立的虚拟地址空间**；
但某些内核资源不是完全复制，而是复制"引用"，因此父子进程之间仍可能**共享**某些底层对象

更严谨地说，fork后大致分为三类：

#### 1. 看起来独立的：用户态地址空间
```
全局变量
局部变量
堆
栈
stdio 缓冲区
```
#### 2. **继承但有共享**底层对象的：文件描述符

父子进程**各自拥有独立的文件描述符表**， fd 表项可能指向同一个内核打开文件对象，因此在都没有关闭之前，它们可能**共享文件偏移量**

```
父进程 fd=1 -> 终端
子进程 fd=1 -> 同一个终端

父进程 fd=3 -> out.txt 的打开文件对象
子进程 fd=3 -> 同一个 out.txt 的打开文件对象
```

父子进程都能继续往同一个终端、文件或管道写东西

>这就是为什么之后学习管道时，`fork()` 后父子进程都拥有管道的读端和写端，需要主动 `close()` 不用的一端

close 只是减少当前 fd 对底层打开文件对象的引用，**只有当所有引用都关闭后，内核才释放该对象**

#### 3. 不一样的：进程身份和调度实体
不同的：
```
PID
父子关系
fork 返回值
调度状态
运行顺序
退出状态
```

### 进程调度导致输出顺序不确定

**为什么我们通常不能说"父进程一定先输出"或者"子进程一定先输出"？**
#### 我的理解
谁先运行由内核调度器决定，但这是一个有趣的思考，fork之后父进程是否会多做一些工作导致轻微慢于子进程或者子进程需要多一些时间来准备从而慢于父进程呢？

#### 解答

fork 之后：
- 父进程处于可运行状态  
- 子进程也处于可运行状态

**谁先拿到 CPU，由内核调度器决定**

**关键：==内核先把子进程创建好==  然后父子进程才分别从 fork() 返回**

`fork()` 内部大致会做这些事：

```
创建子进程的 PCB / task_struct
复制或共享父进程的地址空间结构
设置写时复制 Copy-on-Write
复制文件描述符表
复制信号处理信息
分配新的 PID
设置父子关系
把子进程放入就绪队列
```

### wait 改变父子进程顺序
#### 我的理解

`fork()` 后父子进程谁先运行本来是不确定的，由内核调度器决定。  

**如果父进程调用 `wait(NULL)`，父进程会阻塞，直到某个子进程结束**。因此把父进程的输出放在 `wait(NULL)` 后面，就能保证子进程先结束，父进程后输出。

### 常见误区

误区一：`wait(NULL)` 的 `NULL` 表示不在意子进程退出方式
纠正：是**不保存**子进程退出状态

误区二：`wait(NULL)` 等待的是所有子进程。  
纠正：**一次 `wait(NULL)` 通常只回收一个已经结束的子进程**。如果有多个子进程，要多次 `wait()` 或循环等待

#### 例子：wait 只回收直接子进程
```c
fork();
fork();
printf("X\n");
wait(NULL);
```
##### 我的理解

`fork()` 后每个进程都会继续执行后面的代码，所以如果连续两次无条件 `fork()`，最终会有 4 个进程，每个进程都会执行 `printf("X\n")`，因此输出 4 次。

一次 `wait(NULL)` 通常只回收一个子进程

`wait(NULL)` 只能等待并回收当前进程的**直接子进程**，不能回收孙子进程，也不能回收兄弟进程


### 常见误区

误区一：所有进程执行 `wait(NULL)` 都能成功。  
纠正：**只有拥有子进程的进程才能成功** `wait`；没有子进程的进程会返回 `-1`

误区二：没写足够的 `wait` 就一定留下**永久僵尸** 
纠正：可能产生短暂僵尸；父进程退出后，孤儿/僵尸会被 `init` 或 `systemd` 接管并回收，但健壮程序不应该依赖这个

> **后面进一步明确僵尸进程的机制**

## 4. 进程终止与僵尸进程

**子进程结束时，不是立刻彻底消失**

因为父进程可能还需要知道它是**正常退出、异常退出，还是被某个信号杀死**。因此内核会暂时保留它的 PID、退出状态等==**最小信息**==

它更像考试结束后交卷：

```
子进程：我做完了，交卷了。
内核：我先保留你的成绩单。
父进程：我来领取成绩单。
内核：父进程领取后，才彻底清理。
```

**这个"成绩单"就是：**

```
子进程 PID
退出状态 exit status
是否被信号杀死
资源使用信息等
```

如果子进程已经结束，但父进程还没有调用 `wait()` 领取它的退出信息，那么它就会进入：

```
僵尸状态 zombie
```

注意：僵尸进程不是还在运行的进程。**它已经不执行代码了，只是内核还保留了一点退出信息，等父进程来取**

### 严谨术语
**进程终止常见方式：**

```
1. main 函数 return
2. 调用 exit(status)
3. 调用 _exit(status)
4. 被信号终止，例如 SIGKILL、SIGTERM、SIGSEGV
```

子进程终止后，，内核必须**处理**它的退出状态

如果父进程需要通过 `wait/waitpid` 获取这个状态，那么在父进程领取之前，子进程会==**以僵尸状态保留最小内核信息**==：
```
1. 内核保存子进程的退出状态
2. 子进程进入僵尸状态 Z
3. 内核向父进程发送 SIGCHLD
4. 父进程调用 wait/waitpid 回收
5. 僵尸进程彻底消失
```

如果父进程立即回收、设置自动回收，或者父进程已死由 `init/systemd` 接管，则僵尸状态可能极短或不可观察


**所以核心关系是：**

```
子进程结束
≠
子进程完全消失

子进程结束 + 父进程 wait
=
子进程资源被彻底回收

父进程先死，子进程还活着
→ 孤儿进程

子进程先死，父进程还活着但没 wait
→ 僵尸进程

```

## 5. `exit()` vs `_exit()`
**形象理解：**

```
exit()：正常收摊
    先刷新 stdio 缓冲区
    调用 atexit 注册的退出函数
    最后再调用 _exit()

_exit()：直接关门
	系统调用级别的直接退出
    不帮你刷新 stdio 缓冲区
    直接进入内核终止进程
```

严谨术语：

- `exit()` 是 C **标准库函数**
- `_exit()` 是系统调用级别的进程终止接口
- **`exit()` 最终会调用 `_exit()`**，但在此之前会做清理工作，比如刷新标准 I/O 缓冲区
- `return 0;` 从 `main()` 返回，通常等价于调用 `exit(0)`

## 6. wait 到底拿到了什么？

标准的wait写法：

```c
int status;
wait(&status);
```

`status` 不是简单的退出码

它是一个被编码过的状态值，需要用宏来解析：
1. `WIFEXITED(status)`：子进程是否**正常退出**，例如 return 或 exit()
2. `WEXITSTATUS(status)` ：如果正常退出，获取退出码
3. `WIFSIGNALED(status)`：子进程是否被信号终止
4. `WTERMSIG((status)`：如果被信号终止，获取终止它的信号编号
```c
if (WIFEXITED(status)) {
    printf("normal exit, code=%d\n", WEXITSTATUS(status));
}

if (WIFSIGNALED(status)) {
    printf("killed by signal %d\n", WTERMSIG(status));
}
```
### 为什么不直接说status=0这样？

因为status**不是单纯的退出码**，它还需要 ==**编码完整状态信息**==
- 是否正常退出
- 正常退出码
- 是否被信号杀死
- 被哪个信号杀死
- 是否产生 core dump

#### 等待具体某个子进程结束：waitpid


**waitpid(pid, &status, 0)**; ：等待指定 PID 的子进程结束，阻塞等待，并保存退出状态

```
pid：
    指定等待哪个子进程

status：
    保存退出状态
    传 NULL 表示不保存

options：
    控制等待行为
    0 表示阻塞等待
    WNOHANG 表示不阻塞，没子进程退出就立刻返回
```

## 7. 进程状态

**经典三状态模型：**
1. 就绪 Ready：进程已经拥有除 CPU 之外的所有运行条件，等待调度
2. 执行 Execute：进程正在CPU上执行指令
3. 阻塞 Block：进程正在等待某个事件，e.g. I/O完成

**经典转换关系：**
1. 就绪 → 运行：被调度器选中，获得CPU
2. 运行 → 就绪：时间片用完 or 被更高优先级进程抢占
3. 运行 → 阻塞：发起阻塞操作
4. 阻塞 → 就绪：等待的时间发生

### Linux的五种状态
R：Running 或 Runnable，正在运行或可运行  
S：Interruptible Sleep，可中断睡眠  
D：Uninterruptible Sleep，不可中断睡眠，常见于等待底层 I/O  
T：Stopped，被暂停，例如被 Ctrl+Z 暂停
Z：Zombie，僵尸进程

#### **关于可中断睡眠 S**
`sleep()` 和 `wait()` 都可能让进程暂时停止执行，进入**阻塞状态**

区别在于：

- `sleep()` 等的是时间到期
- `wait()` 等的是子进程退出

在 Linux `ps` 中，这两种等待通常都表现为 `S`，即可中断睡眠状态

### 学会用`ps` 观察进程状态

```shell
$ps -o pid,ppid,stat,cmd -p 913144

    PID    PPID STAT CMD
 913144  913143 Z+   [test] <defunct>
```
#### PPID的一个误区
子进程里的 `getppid()` 不一定等于父进程的 `getpid()` 

**前提条件：子进程比父进程先退出**

比如说如果父进程没有wait

```c
#include <stdio.h>
#include <unistd.h>

int main() {
    pid_t pid = fork();

    if (pid == 0) {
        printf("child: pid=%d, ppid=%d, fork_return=%d\n",
               getpid(), getppid(), pid);
    } else {
        printf("parent: pid=%d, ppid=%d, fork_return=%d\n",
               getpid(), getppid(), pid);
    }

    return 0;
}
```

特殊情况：父进程在子进程调用 `getppid()` 之前已经退出了

**此时子进程输出ppid为1**：

- 父进程先退出，子进程变成了孤儿进程，被 `init/systemd` 等进程接管，父进程关系被内核重新设置
```shell
parent: pid=913330, ppid=912309, fork_return=913331
child: pid=913331, ppid=1, fork_return=0
```

## 8. 程序替换：exec 函数族
`fork + exec` 才是子进程的完全体：子进程执行新程序，父进程继续执行原程序

`exec()` 不是创建新进程
它是在当前==**进程内部**==，把原来的程序替换成另一个程序
- 进程内部意味着PID不变

### exec 之后，具体哪些东西会保留？
- **会替换代码、数据、堆、栈等==用户态程序==映像**
- **通常保留进程控制信息、环境变量、打开的资源描述符**
```
原进程：  
PID = 1234  
打开了 fd 0、fd 1、fd 2  
正在运行 my_program  
  
exec("echo") 后：  
PID 还是 1234  
但运行内容变成 echo  
打开的文件描述符通常还在
```

`echo hello > out.txt` ：为什么`echo` 自己不需要知道有重定向，它只是正常写标准输出，**至于标准输出指向哪里，是 shell 在 `exec` 前安排好的**

### 常见模式：**shell 执行命令的基本模型**

```shell
pid_t pid = fork();

if (pid == 0) {
    execlp("ls", "ls", "-l", NULL);
} else {
    wait(NULL);
}
```

含义是：

```
父进程 fork 出子进程
子进程用 exec 把自己替换成 需要执行的命令
父进程 wait 等子进程结束
```

```
exec 成功：
    不返回原程序
    当前进程的代码段、数据段、堆、栈等用户态程序映像被新程序替换
    PID 不变
    进程身份不变
    只是"这个 PID 对应的进程正在运行的新程序"变了

exec 失败：
    返回 -1
    原程序继续往下执行
    所以 after exec 才可能打印
```

#### 问题：如果子进程成功 exec，父进程 wait 会一直阻塞吗？
**只会阻塞到 exec 后的新程序结束为止**

也就是说尽管子进程执行了另一个程序，但不影响原程序的父进程执行wait
#### 误区：exec的返回值
`exec` 成功后**不返回**。只有失败时才返回 `-1`

### 常用的exec族：execlp()
函数原型：`int execlp(const char *file, const char *arg, ...);`

`execlp("sleep", "sleep", "10", NULL);`

参数可以理解为：
```
我要启动哪个程序？
➡️ 第一个 "sleep" 是给操作系统看的，sleep这个可执行程序

启动后，这个程序看到自己的命令行参数是什么？
➡️ 第二个 "sleep" 是给新程序自己看的，表示argv[0]

➡️ 第三个 "10" 是真正的参数
```

file = "sleep"
    要执行的程序名
    因为用的是 execlp，带 p，所以会在 ==**PATH 环境变量**==中搜索 sleep

arg0 = "sleep"
    新程序的 argv[0]

arg1 = "10"
    新程序的 argv[1]

==**NULL==**
    **==参数列表结束标志，必须有**==
	`execlp()` 需要靠 `NULL` 知道参数列表在哪里结束。没有 `NULL`，它可能继续读错误内存，导致未定义行为

### 关键重定向函数：dup2

```c
int fd = open("out.txt", O_CREAT | O_TRUNC | O_WRONLY, 0644);  
  
dup2(fd, 1);
```

```
原来：
fd=1  -> 终端
fd=3  -> out.txt

执行 dup2(fd, 1) 后：
fd=1  -> out.txt
fd=3  -> out.txt
```

让**文件描述符 1** 指向 **fd 当前指向** 的同一个打开文件对象

### 把重定向推广到管道

**管道：**  
1. 一个进程的 fd=1 -> 管道写端  
2. 另一个进程的 fd=0 -> 管道读端

**诠释重定向：**
`ls` 并不知道后面是 `grep`，它只是正常向标准输出写数据
`grep` 也不一定知道前面是 `ls`，它只是正常从标准输入读数据  
**二者之所以能连接起来，是因为 shell 在 `exec()` 之前修改了它们的文件描述符表**

### 管道重点：引用计数

**ls | grep '\.c' 正确关闭方式：**
```
ls 进程：  
需要写管道  
所以保留写端  
关闭读端 fds[0]  
  
grep 进程：  
需要读管道  
所以保留读端  
关闭写端 fds[1]  
  
父进程：  
不负责真正读写管道  
创建完两个子进程后，应关闭自己手里的 fds[0] 和 fds[1]
```

直接关联的问题：**父进程在创建完两个子进程后，为什么也应该关闭自己手里的管道读端和写端？**

#### 严谨解释

**规则1：==读端进程==什么时候读到 EOF？**

当一个进程从**管道读数据**时：`read(fd[0],buf,size)`

如果管道里暂时没数据但 **==还有写端打开==**，那么 `read()` 会阻塞等待

—— 只有所有写端关闭 && 管道缓冲区为空，读端才读到EOF，返回0

如果父进程忘记关闭自己的写端 `fds[1]`，即使 `ls` 已经结束，`grep` 也可能认为：还有写端存在，未来可能还有数据

**于是 `grep` 可能一直等不到 EOF，程序卡住**


**规则2：==写端==什么时候发现没人读？**

当一个进程往管道写：`write(fds[1], buf, size);`

如果**所有读端都关闭**，那么写入会触发：`SIGPIPE`或者 `write()` 返回 `-1`，`errno = EPIPE`

所以如果父进程忘记关闭自己的读端 `fds[0]`，即使真正的 `grep` 退出了，写端进程也可能不会立刻发现"没人读了"


#### 我的理解
**「grep」在意的是还有没有东西要读** -> 管道写端
**「ls」知道自己写完了，所以在意的是还有没有进程要读** ->管道读端

==**易错：读端和写端是两个方向的引用，它们可以独立关闭**==

管道的阻塞与结束取决于端点引用是否关闭以及缓冲区状态

读端只有在管道为空且仍有写端打开时才会阻塞；所有写端关闭后，读端读空会得到 EOF
写端只有在缓冲区满且仍有读端时才会阻塞；如果所有读端关闭后仍然写入，就会收到 SIGPIPE 或 EPIPE

**内核正常的结束信号：**
- 写端完全关闭，但有读端想要读：read 返回 0，也就是 EOF
- 读端完全关闭，但有写端想要写：write 触发 SIGPIPE 或 EPIPE

进程眼里没有引用计数，只有**管道**是否能读/写
	而管道能否读/写对应了**引用计数是否等于0**
	**本质是内核通过引用计数在管理==管道==的读端和写端**

**有一个细节要补清楚**：

1. 进程即使 "没有手动 close 写/读端"，但它 **==进程退出时，内核会自动关闭它持有的所有文件描述==**
2. ==**如果进程没有关闭自己继承来的另一个端口，同样会阻塞**==

**总结：**
```shell
读端 read：
    管道为空 + 仍有写端打开
    → 阻塞等待数据，读不到EOF

读端 read：
    管道为空 + 所有写端关闭
    → 返回 0，也就是 EOF

写端 write：
    管道未满 + 仍有读端打开
    → 写入成功

写端 write：
    管道满 + 仍有读端打开
    → 阻塞等待空间

写端 write：
    所有读端关闭
    → SIGPIPE / EPIPE
```

上面所说的管道都是匿名管道

—— 匿名管道通常只能用于**有亲缘关系的进程**之间通信

- 因为匿名管道没有==**文件系统路径**==，它只是在内核里创建了一个管道对象，然后把两个 fd 返回给当前进程，其他无关进程拿不到这两个 fd

**匿名管道通信方式总结：**
匿名管道通过 `pipe(fds)` 创建，内核创建管道对象，并把读端和写端以==**文件描述符**==的形式返回给当前进程

如果当前进程随后 `fork()`，子进程会继承父进程的文件描述符表。因此父子进程虽然各自有独立 fd 表，但**它们的 fd 表项可以指向同一个内核管道对象，从而实现通信**

## **9. Lab 2 的核心：命名管道 FIFO**

### **1. 什么是FIFO？**

**"有名字的管道"** 
    ↓
==**特殊文件**== 

> **Linux 万物皆文件**

它有文件系统路径，比如：

```
/tmp/myfifo
```

**可以用：**

```
mkfifo("/tmp/myfifo", 0666);
```

创建

**它和普通文件的关键区别是：**

- **普通文件：**
    **数据真的存储在磁盘文件中**

- **FIFO：**
    路径存在于==**文件系统**==中；
    **但通信数据不是真的写进磁盘文件**
    数据仍主要在==**内核缓冲区**==中流动

**FIFO 的本质是：**
> 用**文件系统路径**作为“会合点”，让无亲缘关系的进程也能打开同一个内核通信对象

**严谨表述：==通过文件系统路径找到同一个 FIFO 对象，然后通过内核缓冲区通信==**
#### **匿名管道 vs 命名管道**

**匿名管道 pipe：**  
	==**没有路径**==  
	通过 fd 继承使用  
	通常用于有亲缘关系的进程  
  
**命名管道 FIFO：**  
	==**有文件系统路径**==  
	通过 **open(path, ...)** 打开  
	**让两个无亲缘关系的进程能通过同一个名字打开同一个 FIFO**

**补充**：匿名管道的数据也不是写到磁盘文件里，而是存在于**内核维护的管道缓冲区**中
- **这是两者的共同点**
- **最本质区别：有无路径**


### **2. FIFO 的 open() 为什么会阻塞？**
匿名管道通常是：

```
pipe(fds);
```

直接得到读端和写端

**但命名管道是：**

```shell
mkfifo("myfifo", 0666);

int fd = open("myfifo", O_RDONLY);  // 打开读端 -> 只读
int fd = open("myfifo", O_WRONLY);  // 打开写端 -> 只写
```

**这里的 `open()` 行为很关键**

**对于 FIFO，==默认阻塞==打开规则是：**

```shell
open(path, O_RDONLY)  
如果没有写进程打开该 FIFO，则阻塞等待写者。  
  
open(path, O_WRONLY)  
如果没有读进程打开该 FIFO，则阻塞等待读者。  
  
open(path, O_RDWR)  
读写方式打开，通常不阻塞
```

**连接的本质："==读写双方配对=="**

这和普通文件不同，普通文件打开后可以直接读写，而 FIFO 的打开行为会受到另一端是否存在的影响

**e.g. cat < myfifo**
- 在没有输入之前会阻塞，但是易错点在于是shell进程而非cat进程
- **==shell== 在执行重定向 `< myfifo` 时先尝试打开 FIFO 阻塞在 `open()`**


**如果加上 `O_NONBLOCK`，行为又会变化：**

```shell
open(path, O_RDONLY | O_NONBLOCK)
    即使没有写者，也立即返回成功。
    后续 read 时，如果没有写者且无数据，可能返回 0

open(path, O_WRONLY | O_NONBLOCK)
    如果没有读者，open 失败，返回 -1，errno = ENXIO
```

**FIFO 规范规定的非对称设计："读"没有破坏性**
- 读端可以先打开，然后等未来写者出现
	- . `read()` **可以马上得到“当前没有写者”的结果**
		1. **返回0表示读到EOF，当前没有 writer 打开 FIFO**
		2. **返回 -1**,errno = EAGAIN/EWOULDBLOCK：没有数据，但有 writer
		3. 返回 > 0：有数据
- **非阻塞写打开 FIFO 时，如果没有读者，直接失败**
	
- **==易错点：两个都不阻塞**==，**区别在于成功返回 or 失败返回**

#### **errno of read**
- `EAGAIN`：非阻塞读时“现在没有数据”，**稍后再试 Again**
- `EWOULDBLOCK`：语义同 `EAGAIN`（很多系统上两者值相同），表示操作会阻塞但你用的是非阻塞
- `EINTR`：系统调用被信号中断（例如收到 `SIGINT`），**读还没完成**

`EINTR`可恢复的“被信号打断”，一般都有
`EAGAIN`和`EWOULDBLOCK` 只在非阻塞open发生

### **3. Lab 2 为什么需要“公共 FIFO + 私有 FIFO”**

**公共 FIFO**：
    server 创建并长期监听
    client 打开它的写端，把请求写给 server

**私有 FIFO**：
    client 创建
    client 把私有 FIFO 路径写入请求结构体
    server 根据请求中的路径 open 该 FIFO
    server 把计算结果写回 client
    client 从自己的 FIFO 读取结果
    client 退出前 unlink 私有 FIFO
- **意义：因为 FIFO 是==字节流==通信通道，不天然区分“这条消息属于哪个 client”**
- 所以如果只用一个FIFO，client会抢着读，大概率接收到错误的信息

### 4. info.myfifo 的意义

`info.myfifo` 不是 FIFO 本身，而是 **client 私有 FIFO 的路径字符串**

client 构造请求时，需要把自己的私有 FIFO 路径写入 `info.myfifo`，再把整个请求结构体写入 server 的公共 FIFO
server 从公共 FIFO 读出结构体后，就可以通过 `info.myfifo` 找到 client 的私有 FIFO，并把计算结果写回去

**client 正确流程：**
```shell
1. 生成私有 FIFO 路径
   private_fifo_path = ".../chat_client<PID>_fifo"

2. mkfifo(private_fifo_path, 0666)
   先把这个回信通道创建出来

3. 填充请求结构体
   info.myfifo = private_fifo_path
   info.leftarg = ...
   info.rightarg = ...
   info.op = ...

4. open server 公共 FIFO 写端 (server_fd)
 
5. write(server_fd, &info, sizeof(info))
   把请求发给 server

6. 打开自己的私有 FIFO 读端

7. read(private_fd, ...)
   等 server 返回结果

8. close + unlink(private_fifo_path)
   关闭并删除私有 FIFO
```

**注意细节：**
1. `mkfifo()` 和填充 `info.myfifo` 的顺序可以互换，但二者必须都在 `write(server_fd, &info, sizeof(info))` 之前完成
2. 但是 **write 公有FIFO → open 私有 FIFO** 不能调换顺序：如果先**阻塞open**，client等待server write，server有等待client write，就会死等
### 5. Server
server 打开公共 FIFO 读端时，如果使用：`open(server_fifo, O_RDONLY);`

那么在没有 client 打开写端时，server 会阻塞在 `open()`, **这不一定是 bug**，可以理解为 server 正在等待 client

如果不希望 server 卡在 `open()`，可以使用：
`open(server_fifo, O_RDONLY | O_NONBLOCK);`
或：
`open(server_fifo, O_RDWR);` (**更常用**)

其中 `O_NONBLOCK` 会让后续 `read()` 逻辑变复杂，需要处理 `0`、`-1/EAGAIN` 等情况；

**`O_RDWR` 则让 server 自己持有写端，通常不会阻塞在 `open()`，也不容易因为没有 client 而读到 EOF**


## 10. 信号 signal
### 1. 什么是信号？

通俗理解：信号像是操作系统给进程发的一条“**紧急通知**”

```shell
进程正在执行第 3 行  
↓  
内核：有人按了 Ctrl+C，给你发 SIGINT  
↓  
进程暂停当前执行流  
↓  
执行信号处理动作  
↓  
然后根据处理结果继续、终止或忽略
```

所以信号最关键的特点是 **==异步==**
>随时有可能发生

**定义**：信号是Linux中一种 **异步** **事件通知机制**

**生命周期**可以分成：
1. **信号产生**：例如用户按 Ctrl + C or 内核检测到 Segment Fault
	
2. **内核记录 / 投递信号**：内核把信号送到**目标进程**
	
3. **进程处理信号**：进程可以忽略、捕获处理，或者执行默认动作
	
	**三种处理方式：**
	1. 忽略 Overlook：不做处理，但是==**SIGKILL 和 SIGSTOP 不能忽略**==
	2. 捕获：注册一个处理函数，信号到来时执行函数
		- **常用`signal()` 把某个函数注册为指定信号的处理函数**
	3. **默认动作**：e.g. 终止进程、忽略、停止进程、继续进程...
#### 常见信号

**Ctrl+C**
    终端给前台进程发送 ==**SIGINT**==
	默认情况下，进程收到 `SIGINT` 会终止

空指针解引用
    内核给进程发送 ==**SIGSEGV**==

子进程退出
    内核给父进程发送 ==**SIGCHLD**==

管道读端全部关闭后继续写
    内核给写进程发送 ==**SIGPIPE**==

**kill -9 PID**
    给目标进程发送 ==**SIGKILL**==
### 2. signal() 注册信号处理函数

signal使得进程不执行默认动作，变为执行自定义处理函数 `handle`

**所以signal的基本形式：**

```c
#include <signal.h>

void handler(int sig) {
    // 收到信号后执行的代码
}

signal(SIGINT, handler);
```
