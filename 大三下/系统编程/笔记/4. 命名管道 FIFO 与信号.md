## **1. Lab 2 的核心：命名管道 FIFO**

### **1. 什么是FIFO？**

**"有名字的管道"** 
    ↓
==**特殊文件**== 

> **Linux 万物皆文件**

它有文件系统路径，比如：

```
/tmp/myfifo
```

**可以用：**

```
mkfifo("/tmp/myfifo", 0666);
```

创建

**它和普通文件的关键区别是：**

- **普通文件：**
    **数据真的存储在磁盘文件中**

- **FIFO：**
    路径存在于==**文件系统**==中；
    **但通信数据不是真的写进磁盘文件**
    数据仍主要在==**内核缓冲区**==中流动

**FIFO 的本质是：**
> 用**文件系统路径**作为“会合点”，让无亲缘关系的进程也能打开同一个内核通信对象

**严谨表述：==通过文件系统路径找到同一个 FIFO 对象，然后通过内核缓冲区通信==**
#### **匿名管道 vs 命名管道**

**匿名管道 pipe：**  
	==**没有路径**==  
	通过 fd 继承使用  
	通常用于有亲缘关系的进程  
  
**命名管道 FIFO：**  
	==**有文件系统路径**==  
	通过 **open(path, ...)** 打开  
	**让两个无亲缘关系的进程能通过同一个名字打开同一个 FIFO**

**补充**：匿名管道的数据也不是写到磁盘文件里，而是存在于**内核维护的管道缓冲区**中
- **这是两者的共同点**
- **最本质区别：有无路径**


### **2. FIFO 的 open() 为什么会阻塞？**
匿名管道通常是：

```
pipe(fds);
```

直接得到读端和写端

**但命名管道是：**

```shell
mkfifo("myfifo", 0666);

int fd = open("myfifo", O_RDONLY);  // 打开读端 -> 只读
int fd = open("myfifo", O_WRONLY);  // 打开写端 -> 只写
```

**这里的 `open()` 行为很关键**

**对于 FIFO，==默认阻塞==打开规则是：**

```shell
open(path, O_RDONLY)  
如果没有写进程打开该 FIFO，则阻塞等待写者。  
  
open(path, O_WRONLY)  
如果没有读进程打开该 FIFO，则阻塞等待读者。  
  
open(path, O_RDWR)  
读写方式打开，通常不阻塞
```

**连接的本质："==读写双方配对=="**

这和普通文件不同，普通文件打开后可以直接读写，而 FIFO 的打开行为会受到另一端是否存在的影响

**e.g. cat < myfifo**
- 在没有输入之前会阻塞，但是易错点在于是shell进程而非cat进程
- **==shell== 在执行重定向 `< myfifo` 时先尝试打开 FIFO 阻塞在 `open()`**


**如果加上 `O_NONBLOCK`，行为又会变化：**

```shell
open(path, O_RDONLY | O_NONBLOCK)
    即使没有写者，也立即返回成功。
    后续 read 时，如果没有写者且无数据，可能返回 0

open(path, O_WRONLY | O_NONBLOCK)
    如果没有读者，open 失败，返回 -1，errno = ENXIO
```

**FIFO 规范规定的非对称设计："读"没有破坏性**
- 读端可以先打开，然后等未来写者出现
	- . `read()` **可以马上得到“当前没有写者”的结果**
		1. **返回0表示读到EOF，当前没有 writer 打开 FIFO**
		2. **返回 -1**,errno = EAGAIN/EWOULDBLOCK：没有数据，但有 writer
		3. 返回 > 0：有数据
- **非阻塞写打开 FIFO 时，如果没有读者，直接失败**
	
- **==易错点：两个都不阻塞**==，**区别在于成功返回 or 失败返回**

#### **errno of read**
- `EAGAIN`：非阻塞读时“现在没有数据”，**稍后再试 Again**
- `EWOULDBLOCK`：语义同 `EAGAIN`（很多系统上两者值相同），表示操作会阻塞但你用的是非阻塞
- `EINTR`：系统调用被信号中断（例如收到 `SIGINT`），**读还没完成**

`EINTR`可恢复的“被信号打断”，一般都有
`EAGAIN`和`EWOULDBLOCK` 只在非阻塞open发生

### **3. Lab 2 为什么需要“公共 FIFO + 私有 FIFO”**

**公共 FIFO**：
    server 创建并长期监听
    client 打开它的写端，把请求写给 server

**私有 FIFO**：
    client 创建
    client 把私有 FIFO 路径写入请求结构体
    server 根据请求中的路径 open 该 FIFO
    server 把计算结果写回 client
    client 从自己的 FIFO 读取结果
    client 退出前 unlink 私有 FIFO
- **意义：因为 FIFO 是==字节流==通信通道，不天然区分“这条消息属于哪个 client”**
- 所以如果只用一个FIFO，client会抢着读，大概率接收到错误的信息

### 4. info.myfifo 的意义

`info.myfifo` 不是 FIFO 本身，而是 **client 私有 FIFO 的路径字符串**

client 构造请求时，需要把自己的私有 FIFO 路径写入 `info.myfifo`，再把整个请求结构体写入 server 的公共 FIFO
server 从公共 FIFO 读出结构体后，就可以通过 `info.myfifo` 找到 client 的私有 FIFO，并把计算结果写回去

**client 正确流程：**
```shell
1. 生成私有 FIFO 路径
   private_fifo_path = ".../chat_client<PID>_fifo"

2. mkfifo(private_fifo_path, 0666)
   先把这个回信通道创建出来

3. 填充请求结构体
   info.myfifo = private_fifo_path
   info.leftarg = ...
   info.rightarg = ...
   info.op = ...

4. open server 公共 FIFO 写端 (server_fd)
 
5. write(server_fd, &info, sizeof(info))
   把请求发给 server

6. 打开自己的私有 FIFO 读端

7. read(private_fd, ...)
   等 server 返回结果

8. close + unlink(private_fifo_path)
   关闭并删除私有 FIFO
```

**注意细节：**
1. `mkfifo()` 和填充 `info.myfifo` 的顺序可以互换，但二者必须都在 `write(server_fd, &info, sizeof(info))` 之前完成
2. 但是 **write 公有FIFO → open 私有 FIFO** 不能调换顺序：如果先**阻塞open**，client等待server write，server有等待client write，就会死等
### 5. Server
server 打开公共 FIFO 读端时，如果使用：`open(server_fifo, O_RDONLY);`

那么在没有 client 打开写端时，server 会阻塞在 `open()`, **这不一定是 bug**，可以理解为 server 正在等待 client

如果不希望 server 卡在 `open()`，可以使用：
`open(server_fifo, O_RDONLY | O_NONBLOCK);`
或：
`open(server_fifo, O_RDWR);` (**更常用**)

其中 `O_NONBLOCK` 会让后续 `read()` 逻辑变复杂，需要处理 `0`、`-1/EAGAIN` 等情况；

**`O_RDWR` 则让 server 自己持有写端，通常不会阻塞在 `open()`，也不容易因为没有 client 而读到 EOF**


## 2. 信号 signal
### 1. 什么是信号？

通俗理解：信号像是操作系统给进程发的一条“**紧急通知**”

```shell
进程正在执行第 3 行  
↓  
内核：有人按了 Ctrl+C，给你发 SIGINT  
↓  
进程暂停当前执行流  
↓  
执行信号处理动作  
↓  
然后根据处理结果继续、终止或忽略
```

所以信号最关键的特点是 **==异步==**
>随时有可能发生

**定义**：信号是Linux中一种 **异步** **事件通知机制**

**生命周期**可以分成：
1. **信号产生**：例如用户按 Ctrl + C or 内核检测到 Segment Fault
	
2. **内核记录 / 投递信号**：内核把信号送到**目标进程**
	
3. **进程处理信号**：进程可以忽略、捕获处理，或者执行默认动作
	
	**三种处理方式：**
	1. **忽略** Overlook：不做处理，但是==**SIGKILL 和 SIGSTOP 不能忽略**==
	2. 捕获：注册一个处理函数，信号到来时执行函数
		- **常用`signal()` 把某个函数注册为指定信号的处理函数**
	3. **默认动作**：e.g. 终止进程、忽略、停止进程、继续进程...
#### 常见信号

**Ctrl+C**
    终端给前台进程发送 ==**SIGINT**==
	默认情况下，进程收到 `SIGINT` 会终止

空指针解引用
    内核给进程发送 ==**SIGSEGV**==

子进程退出
    内核给父进程发送 ==**SIGCHLD**==

管道读端全部关闭后继续写
    内核给写进程发送 ==**SIGPIPE**==

**kill -9 PID**
    给目标进程发送 ==**SIGKILL**==

#### 默认动作

```
SIGINT：
    默认动作是 Term
    所以 Ctrl+C 默认终止进程

SIGPIPE：
    默认动作是 Term
    所以往没有读者的 pipe/FIFO 写，默认可能导致进程终止

SIGCHLD：
    默认动作通常是 Ign
    子进程退出时通知父进程

SIGSTOP：
    默认动作是 Stop
    停止进程，且不能被忽略或捕获

SIGCONT：
    默认动作是 Cont
    让停止的进程继续执行

SIGSEGV：
    默认动作是 Core
    非法内存访问，终止并可能生成 core dump
```

### 2. signal() 注册信号处理函数

signal使得进程不执行默认动作，变为执行自定义处理函数 `handle`

**所以signal的基本形式：**

```c
#include <signal.h>

void handler(int sig) {
    // 收到信号后执行的代码
}

signal(SIGINT, handler);
```


**e.g. 忽略信号**：`signal(SIGINT, SIG_IGN);`

#### **signal的三种形式**

```
不调用 signal：  
使用默认动作。  
  
signal(SIGINT, SIG_IGN)：  
改成忽略，不需要再写默认动作。  
  
signal(SIGINT, handler)：  
改成捕获处理。  
  
signal(SIGINT, SIG_DFL)：  
恢复默认动作。
```

#### 困惑
**进程无法忽略的是什么情况？**
```
SIGKILL：
    强制杀死进程
    不能捕获
    不能忽略
    不能阻塞
	➟ kill -9 PID 里的 -9 

SIGSTOP：
    强制暂停进程
    不能捕获
    不能忽略
    不能阻塞
    kill(pid, SIGSTOP);
	注意和 SIGTSTP 区分
	
```

| **信号**  | **常见来源**       | **能否捕获/忽略** | **作用** |
| ------- | -------------- | ----------- | ------ |
| SIGSTOP | kill -STOP pid | 不能          | 强制暂停   |
| SIGTSTP | 终端按 Ctrl+Z     | 可以          | 请求暂停   |

**如果全都忽略会继续执行吗？**
- 对于普通可忽略的没问题
- 不可忽略的忽略了也没用
- **对于一些程序级错误，如果忽略了，可能会陷入更糟糕的情况，所以尽量不忽略**

### 3. pause：等待信号

**`pause()` 会让进程阻塞，直到捕获到一个信号**

```c
#include <unistd.h>  
int pause(void);
```

如果==**信号的处理函数返回**==了，`pause()` 会返回 `-1`，并且 `errno` **通常**是 `EINTR`，意思是
- **系统调用被信号中断**

‼️但是在这个例子里pause expired
- **直接 `_exit(1)` ， `pause()` 没机会返回**
```c
void handler(int sig) {
    unlink(mypipename);
    _exit(1);
}
```

### 4. EINTR：系统调用被信号打断「常用信号」

Interrupted system call，**EINTR是一个宏定义的常量**

如果进程正阻塞在**某些系统调用**中，例如 `pause()`、`read()`、`wait()`，信号到来后会先执行信号处理函数。如果处理函数返回，**原本阻塞的系统调用可能被中断，并返回 `-1`**，同时设置 `errno = EINTR`

> **pause 也属于系统调用**

#### 巩固：Perror 用法
`void perror(const char *s);`  里面放的是一个**常量字符串**

**作用：读取 errno，把错误码翻译成人类可读的文本**

```c
int fd = open("not_exist.txt", O_RDONLY);

if (fd == -1) {
    perror("open");
}
```

**流程：**

```
设置 errno  
↓  
perror("你写的提示词")  
↓  
输出：提示词 + errno 对应的错误说明
```

### 5. `SIGPIPE` 和 `EPIPE`

当进程对 pipe/FIFO 写入时，如果**所有读端都已经关闭**

> 所有写端关闭，读端执行读操作也是触发这个吗？
> **→ read 返回 0，表示 EOF**
> 读和写的处理方式是不对称的！

此时如果有进程执行写操作：`write(fd, buf, size);`
1. 信号层面：SIGPIPE
   > 默认动作：终止进程
2. 错误码层面：EPIPE

**==默认处理不会设置EPIPE==：**
```
默认不处理 SIGPIPE：  
进程可能直接被杀，来不及处理返回值
  
忽略/捕获 SIGPIPE：  
write 才有机会返回 -1，并设置 errno = EPIPE
```


### 6. `SIGCHLD`
当子进程结束时，内核给父进程发送的信号

> `SIGCHLD` 本身不是“回收子进程”，它只是通知父进程：你该回收了
> 真正回收的是 父进程调用 `wait`

**回顾子进程回收链路：**
```
子进程 exit
    ↓
内核保留子进程的 PID + 退出状态
    ↓
子进程进入 zombie
    ↓
内核向父进程发送 SIGCHLD
    ↓
父进程 wait / waitpid
    ↓
僵尸进程彻底消失
```

**SIGCHLD默认操作是 IGN ，为什么？**

—— 为了**让系统自动处理**子进程退出状态，减少僵尸进程出现的可能

### 7. `signal()` 和 `sigaction()` 的区别

`signal()` ：最简单、最旧的信号管理接口
sigaction()：更严谨、更可控

比如`sigaction()` 可以控制一个很关键的行为：
- 系统调用被信号中断后，是返回 EINTR，还是自动重启？
### 8. `kill()` 不是只能“杀进程”

kill 默认不是一定强杀，kill -9 才是强杀

`kill -15 1234` 发送`SIGTERM`，表示礼貌地请求进程终止，可以被捕获、忽略、处理
