
## 3.1 处理机调度的基本概念

**处理机调度**要解决的问题：多个进程竞争 CPU 时，操作系统决定
1. **哪个进程先运行**
2. **运行多久**
3. **何时切换**

### 三级调度

- **高级调度**：以==**作业**==为对象，从==**外存**==后备队列调入内存，伴随进程创建
- **中级调度**：以==**进程**==为对象，在==**内存和外存**==之间换入换出，对应挂起与激活
	- 为了提高内存利用率和系统吞吐量
- **低级调度**：以==**进程**==为对象，即==**进程调度**==，从==**就绪队列**==中选择一个进程获得 CPU
	1. **非抢占式调度**：正在执行的进程**运行完毕或发生阻塞**，才让出CPU
	2. **抢占式调度**：允许暂停当前执行的进程，重新分配**CPU**给另一进程

#### 怎么理解 "作业" 这个概念？
**作业**：用户提交给系统处理的==**一项完整任务**==，通常还在外存后备队列中等待  
**进程**：作业被接纳进入内存后，为了执行而创建出来的**运行实体**

### 我的理解
高级调度更宏观，把作业从外存放到内存，创建进程执行，变成低级调度的进程视角
低级调度处理进程的状态转换；
引入中级调度来提升内存利用率，把一些暂时不能运行的进程重新放回外存「**挂起**」，能够重新运行再放回内存「**激活**」，所以本质改变进程的状态

**高级调度管"作业进不进内存"，低级调度管"谁用 CPU"，中级调度管"进程在内存还是外存"**
### 常见误区

高级调度和低级调度不要混在一起：
- 高级调度解决的是 "**作业能不能进入内存**"
- 低级调度解决的是 **"就绪进程谁获得 CPU"**

## 3.2 调度队列模型和调度准则
进程/作业不运行时，到底排在哪些队列里？
发生事件后，又会被移动到哪里？

### 1. **仅有进程调度**的队列模型

**只有低级调度参与**

- 就绪队列：已经具备运行条件，只差 CPU
- 阻塞队列：正在等待某个事件或资源
- CPU：由进程调度从就绪队列中选择进程执行

**状态流动**：
```
就绪队列 → CPU → 完成
       ↓
    阻塞队列
```

### 2. 具有高级调度和低级调度的队列模型
**增加**了一个 **后备队列**

- **后备队列**：==**外存**==中等待进入系统的作业
- 高级调度：从后备队列中选择作业调入内存
- 就绪队列：已经进入内存、等待 CPU 的进程
- 低级调度：从就绪队列中选择进程执行

```
后备队列 --高级调度--> 就绪队列 --低级调度--> CPU
```

**根据优先权，设置多个阻塞队列**

### 3. 同时具有三级调度的队列模型
**继续增加==挂起队列**==

1. **高级调度**：后备队列 → 就绪队列
2. **低级调度**：就绪队列 → CPU
3. **中级调度**：
	1. 就绪队列 ↔ 就绪挂起队列
	2. 阻塞队列 ↔ 阻塞挂起队列

4. **事件完成**：
	1. 阻塞队列 → 就绪队列
	2. 阻塞挂起队列 → 就绪挂起队列

### 4. 面向==**用户**==

调度准则：**评价调度算法的好坏 -> 指标**

1. **==周转时间短：周转时间 = 完成时间 - 到达时间**==
	- **总共等了多久才完成**
 2. **==带权周转时间短：带权周转时间 = 周转时间 / 服务时间**==
	- **实际花的总时间是本来运行时间的几倍 -> 等待成本**
 3. 响应时间快：**从用户提交请求，到系统第一次响应的时间**

 4. 截止时间保证：尤其用于实时系统，**任务必须在规定时间前开始或完成**

 5. 优先权准则：**重要任务、紧急任务优先执行**

### 5. 面向==系统==

1. 系统**吞吐量**高：单位时间内完成的作业数量多

2. 处理机**利用率**好：CPU 尽量不要空闲

3. 各类**资源平衡**利用：不要出现 CPU 很忙但 I/O 设备闲着，或者 I/O 很忙但 CPU 闲着

### 我的理解

**首先要串起一个作业的一生**：

```shell
用户提交任务  
↓  
到达系统 / 到达时间 : 作业/进程进入系统、开始等待被调度的时刻
↓  
进入后备队列 / 就绪队列  --等待
↓  
第一次获得 CPU（响应时间结束）  
↓  
运行过程中可能阻塞/唤醒  --继续等待
↓  
最终执行完成 / 完成时间
```

**到达时间**：作业进入 "系统" ，等待被调度

**响应时间**：第一次得到CPU时刻 - 到达时间

**完成时间**：作业真正全部执行结束的时刻

==**服务时间/运行时间**==：如果 CPU 完全只给它运行，**它真正需要的 CPU 时间**
- **一般题目给出**

### 常见误区

1. 不要把服务时间和周转时间混淆
	- 服务时间是作业真正需要 CPU 运行的时间
	- **周转时间包括等待时间和运行时间**
  
2. 带权周转时间不是“等待时间 / 服务时间”，而是“周转时间 / 服务时间”
  
3. **响应时间不等于完成时间：响应时间只要求系统第一次回应，不要求任务完成**


## 3.3 调度算法  

### 1. FCFS 先来先服务 First Come First Served

**规则：**
- 按到达时间排序
- 到达早的先运行
- ==**非抢占式**==

**优点：**
- 实现简单
- 算法开销小
- 有利于长作业

**缺点：**
- 不利于短作业：长作业堵前面，短作业一直等

#### **小例子**

| 作业  | 到达时间  | 服务时间 |
| --- | ----- | ---- |
| A   | **0** | 4    |
| B   | **1** | 3    |
| C   | **2** | 1    |

**FCFS 顺序：**
	A → B → C

**时间轴：**
```
0   4   7   8  
| A | B | C |
```

**计算：**

| 作业  | 完成时间 | 周转时间 | 带权周转时间 |
| --- | ---- | ---- | ------ |
| A   | 4    | 4    | 1      |
| B   | 7    | 6    | 2      |
| C   | 8    | 6    | **6**  |

C 明明只需要 1 秒，但总共等到第 8 秒才完成，所以带权周转时间很高

### 2. Shortest Job First

**规则：**

> 每次从就绪队列里选服务时间最短的作业运行

**注意：**

- 是“==**当前已经到达**==”的作业里选最短
- ==**非抢占式调度**==

优点：为什么 SJF 很强？
- ==**平均周转时间最小**==：短任务先完成整体等待更少

缺点：
1. **长作业会饿死**：这点和FSC相反
2. **无法提前知道运行时间，只能估计**
#### **例题**

| 作业  | 到达时间 | 服务时间 |
| --- | ---- | ---- |
| A   | 0    | 6    |
| B   | 2    | 2    |
| C   | 4    | 1    |
 
 t=0
- 只有 A 到达，运行 A
- 即使 B 更短，B 还没到

**时间轴**

```
0        6    7     9
|   A    | C  |  B  |
```

 t=6
- B，C都到达，选择C
### 3. 抢占式 SJF / SRTF（拓展）  
  
SRTF，全称 Shortest Remaining Time First，最短剩余时间优先，是短作业优先 SJF 的抢占式版本  
  
#### 核心规则  
  
每次调度时，选择“剩余运行时间最短”的进程执行
  
如果一个新进程到达，并且它的服务时间小于当前运行进程的剩余时间，则当前进程被抢占，新进程获得 CPU。
  
#### 和非抢占式 SJF 的区别  
  
- 非抢占式 SJF：进程一旦开始运行，就会一直运行到完成。  
- 抢占式 SJF / SRTF：运行过程中如果来了剩余时间更短的进程，可以发生抢占。  
#### 优点  

更彻底地照顾短作业，**通常可以进一步降低平均周转时间**
  
#### 缺点  

**频繁抢占会增加上下文切换开销**，也可能使长作业长期得不到运行，产生饥饿现象

### 4. 高响应比优先调度算法 HRRN

高响应比优先算法是一种==**非抢占式**==调度算法 = **SJF + 等待补偿机制**

#### 核心思想

每次调度时，从当前已经到达的作业中，选择**响应比最高**的作业执行

#### 响应比公式

响应比 = (等待时间 + 服务时间) / 服务时间
      = 1 + 等待时间 / 服务时间

其中：

- **等待时间 = 当前时刻 - 到达时间**
- 服务时间 = 作业本身需要运行的时间

#### 特点

- 对短作业有利：服务时间越短，响应比越容易高
- 对长作业也有补偿：等待时间越长，响应比会逐渐增大
- ==**每次调度前都要重新计算响应比**==，因此系统开销比 FCFS、SJF 更大。

### **5. 时间片轮转调度 RR**

Round Robin，时间片轮转调度，是一种==**抢占式调度算法**==

#### **核心思想**

每个进程轮流使用 CPU，每次最多运行一个时间片

若时间片用完但进程尚未结束，则**立即剥夺 CPU**，并将该进程放到==**就绪队列尾部**==等待下一轮调度

**关键机制：==时钟中断==**
1. 保存当前进程现场
2. PCB 改成就绪态
3. 放回就绪队列尾部
4. 调度下一个进程
#### 特点

- **抢占式调度**
- 队列按照 **FCFS** 排队
- 依赖时钟中断实现时间片切换

#### 优点

- 响应速度快
- 调度公平
- 适合交互式系统

#### 缺点

- **时间片太小**会导致==**频繁上下文切换**==
- 时间片太大则退化为 FCFS

#### 常见误区

1. 时间片结束不代表进程结束，只是暂时被剥夺 CPU
2. RR 的队列是循环队列，运行完时间片的进程进入队尾
3. 新到达的进程进入队尾，不会立即抢占当前进程
4. RR 是由时钟中断强制抢占，而不是新进程到达触发抢占

### 6. 多级反馈队列调度算法

#### 核心思想

设置多个**就绪队列**：

- 队列 I：优先级最高，时间片最短
- 队列 II：优先级较低，时间片较长
- 队列 III：优先级更低，时间片更长

==**新进程总是先进入最高优先级队列**==

#### 调度规则

1. 新进程进入第 I 级队列
2. 如果进程在当前队列的一个时间片内完成，则退出系统
3. 如果没有完成，则降到下一级队列尾部
4. ==**只有高优先级队列为空**==，低优先级队列才可以被调度
5. ==**如果低级队列进程正在运行时，高级队列有新进程进入，则低级队列进程会被抢占**==

#### 常见误区

1. 不是所有队列都同时轮转，必须先看高级队列是否为空
2. 新进程不是进入当前队列，而是进入最高优先级队列
3. 时间片用完且未完成，才会降级
4. ==**被高级队列抢占时，通常不降级，而是回到原队列尾部，并记录剩余运行时间**==

### 7. 实时调度

实时任务必须在==**规定时间**==之前==**开始或完成**==

⬇️ 

**开始截止**时间：必须在某个时间之前开始执行

**完成截止**时间：任务必须在某个时间之前完成执行
- 需要知道**运行时间**

1. **提供必要信息**：系统必须知道任务什么时候来「**就绪时间**」、多久必须完成「**完成截止时间**」、需要运行多久「**运行时间**」、要什么资源「**资源要求**」，并且 CPU 得真的来得及处理「**处理能力**」

2. **系统处理能力足够强**：通过 **任务长期需要多少CPU时间** 来量化
	- 任务 A：每 50ms 来一次，每次需要运行 10ms  
	  A 的 CPU 占用率 = 10 / 50 = 0.2 = 20%
	- 限制：**单处理器多个任务的CPU占用率不能超过100%**

3. **采用抢占式调度**
	- 如果能预知任务的 **「开始截止时间」**，可采用非抢占调度机制，以简化调度和减少系统开销

**基于两个截止时间衍生出两种算法**
#### **7.1 最早截止时间优先 EDF**

EDF，Earliest **Deadline** First

核心规则：

- 谁的==**开始截止时间**==最早，谁优先执行

特点：

- 截止时间越早，优先级越高

#### **7.2 最低松弛度优先 LLF**

LLF，Least **Laxity** First

核心规则：

- 谁的松弛度最低，谁最紧急，谁优先执行

**松弛度** = ==**完成截止时间**== - 当前时间 - 剩余运行时间 = ==**还能拖多久**==

#### **例题（重点）**

A 每 20ms 执行一次，每次 10ms
B 每 50ms 执行一次，每次 25ms
要求用最低松弛度优先算法调度
“松弛度为 0 发生抢占”

--- 
**==易错点：必须先判断CPU能否调度！==**

A 的占用率：10 / 20 = 0.5

B 的占用率：25 / 50 = 0.5

总占用率：0.5 + 0.5 = 1
- 刚好等于 1，说明单处理器理论上刚好能调度，不能有额外开销

---

**误区1**：怎么理解任务 **每多少ms必须执行一次**？<u>划分区间内必须完成该任务</u>，还是上一个任务完成后需要等到这个时间？
- “每多少 ms 执行一次”指的是 **==周期==性释放任务实例**
- 以 A 为例：A：周期 20ms，执行时间 10ms

**意思是：**

```
A1 在 t=0 到达，通常要求 t=20 前完成
A2 在 t=20 到达，通常要求 t=40 前完成
A3 在 t=40 到达，通常要求 t=60 前完成
...
[0,20) 内完成 A1  
[20,40) 内完成 A2  
[40,60) 内完成 A3
```

--- 

**1. 任务实例**

A 每 20ms 来一次：

```
A1: 0 到达，截止 20，需要 10  
A2: 20 到达，截止 40，需要 10  
A3: 40 到达，截止 60，需要 10  
A4: 60 到达，截止 80，需要 10  
A5: 80 到达，截止 100，需要 10
```

B 每 50ms 来一次：

```
B1: 0 到达，截止 50，需要 25  
B2: 50 到达，截止 100，需要 25
```

**2. ==任务松弛度为0的时刻才抢占==**
- **A1--10**、 **A2--30**、 **A3--50**、 **A4--70**、 **A5--90**
- **B1--25**、 **B2--75**

**3. 调度过程**
t=0
- A1=10，B1=25，执行A1到10

t=10
- A1执行完毕，A2=20，B1=15,执行B1到30

**t=30**
- A2抢占，B1剩5
- **B1下一个松弛度为0时刻为50-5=45**

t=40
- A2执行完，B1更高，执行5

t=45
- A3执行10

t=55
- A4还没到达，执行B2

t=60
- A4-70，B2-80
- **松弛度没到0不抢占**

t=70
- A4抢占，B2剩10
- B2下一个松弛度为0时刻为90

t=80
- A5和B2都是90，默认FCS，B2 先执行

t=90
- A5执行10到100

### 我的理解

调度算法：
1. FCFS 先来先服务：根据到达时间排序，非抢占式则不断累加运行时间，适合长任务，会堵塞短任务
2. SJF 短作业优先：根据完成时间排序，一般非抢占，适合短作业，饥饿效应
3. 高响应比优先：改善前两种算法，响应比 = 1 + 等待时间 / 运行时间，不会让长作业等太久
4. 时间片调度：非抢占式就简单，就绪队列先来先服务，时间片结束拍到末尾
5. **多级队列**：主要是画时间轴，同时注意运行进程被抢占进入队列末尾

**实时调度做题：**
1. 先判断CPU能否调度
2. 写出任务的周期实例
3. 检测任务松弛度为0的临界时刻
- 松弛度相同通常按 FCFS 处理，即先到达者优先；如果其中一个任务已经在运行，也可以继续运行，以减少不必要的抢占
  考试做题时应在答案中写明自己的约定。

## 3.4 死锁(重点)

**知识链：**
```
死锁是什么
↓
为什么会死锁
↓
死锁四个必要条件
↓
处理死锁的四类方法
↓
预防死锁
↓
安全状态 / 不安全状态 / 安全序列
↓
银行家算法
↓
死锁检测与解除
```
### 1. 死锁是什么？
通俗来说好像就是两个进程同时等待另一个进程所拥有的资源

严谨定义：
- **死锁**：==**多个进程**==因==**竞争资源**==而造成的一种僵局，若无外力作用，**这些进程都将永远不能再向前推进**
### 2. 为什么会产生死锁

**两个根本原因：竞争资源 + 进程推进顺序非法**

**↓**

产生死锁的==**必要条件**==：
1. **互斥条件**：资源是**临界资源** → 导致进程阻塞
2. **请求和保持条件**：一个进程已经**持有**某些资源，同时又==**申请**==新的资源
3. **不剥夺条件**：进程已经获得的资源，在使用完之前，**不能被系统强制抢走**
4. **==环路等待：存在一个进程等待环**==
   **用于死锁检测**

**↓**

**四个条件必须同时发生才会触发死锁**


### 3. 死锁处理的四种方法

死锁未发生：预防和避免
**↓**
死锁可能发生：检测
**↓**
死锁已发生：解除

| 方法           | 核心思想           | 什么时候管      |
| ------------ | -------------- | ---------- |
| ==**预防**==死锁 | 直接破坏死锁必要条件     | 资源分配规则设计阶段 |
| 避免死锁         | 分配前检查会不会进入危险状态 | 每次资源请求时    |
| 检测死锁         | 允许死锁发生，然后检测    | 运行过程中      |
| 解除死锁         | 发现死锁后处理        | 死锁发生后      |

### **4. 预防死锁**
#### 破坏“请求和保持”

**要求进程一次性申请所有资源**
- e.g. **信号集**

**要么一次拿齐**，**要么一个都不给**

这样进程就不会出现“已经拿着一部分资源，又等待另一部分资源”

#### 破坏“不剥夺”

如果申请不到新资源，就**强制收回**它已经占有的资源
- 判断资源请求是否超过当前可用数量
```
你申请不到 R2？
那系统把你手里的 R1 也收回来。
```

#### 破坏“环路等待”

**给资源编号，所有进程必须按顺序申请**

```
只能 R1 → R2 → R3 
不能 R3 → R1
```

这样就不容易形成等待环

### **5. 避免死锁：动态审批**

避免死锁不是直接禁止某种申请方式，而是每次有进程申请资源时，系统问一句

> 如果我现在把资源给你，系统还能不能找到一个安全序列？

如果能找到，就分配； 
如果找不到，就暂时不分配

**→ 这就是银行家算法的思想**

**所以避免死锁的流程：**

```shell
进程申请资源
↓
系统先 “假装”分配
↓
检查分配后是否还能找到安全序列
↓
能找到：正式分配
找不到：撤销试探分配，让进程等待
```

### **6. 避免死锁的根基 - 安全序列**

#### **安全序列 -> 安全状态**

如果系统能按某种进程顺序 `<P1, P2, ..., Pn>`，依次满足每个进程的==**最大资源需求**==，使所有进程都能**顺利完成**，那么这个序列叫**安全序列**；如果找不到这样的序列，系统就是**不安全状态**

##### 形象理解：钱够不够周转

假设你是银行，现在手里有一笔现金，几个客户都**已经借走了一部分钱**，而且他们之后可能还会继续借

银行最关心的不是：

```
现在有没有人还不上钱？
```

而是：

```
如果客户继续按照最大需求来借，
我有没有一种放款顺序，
能让他们一个个完成项目、还钱，
最后所有人都能完成？
```

如果存在这样一种顺序，系统就是安全的

**↓**

把银行换成操作系统：

```shell
银行现金 = Available 当前可用资源
客户已经借的钱 = Allocation 已分配资源
客户"最多"还要借的钱 = Need 剩余最大需求
客户项目完成后还钱 = 进程完成后释放 Allocation
```

所以安全状态的核心不是“当前资源够不够所有人一起用”，而是：

> **能不能找到一个顺序，让进程一个一个完成，并释放资源**
> **这个顺序就是安全序列**

形式：**<P1, P3, P4, P2, P0>**，并且能证明：
```shell
当前资源先够 P1 完成  
P1 完成后释放资源，又够 P3 完成  
P3 完成后释放资源，又够 P4 完成  
P4 完成后释放资源，又够 P2 完成  
P2 完成后释放资源，又够 P0 完成
```
##### 安全状态 → 资源回收再分配

核心比较： `Need[i] <= Work`
- 如果成立，说明系统现在有能力满足 Pi 的剩余最大需求
- Pi 一定可以完成

Pi 完成后会释放自己已经占有的资源：`Work += Allocation[i]`

##### 数据结构实现
- `Max` ：最大需求
- `Allocation` ：已占用资源
- `Need` ：剩余最大需求
  `Max = Need + Allocation`
- `Available` ：当前可用资源
- `Work` 表示进程完成后系统可用资源数，初始等于 `Available`
- `Finish`：每个进程能否完成
##### **安全检查算法**
Step 1：Work = Available
Step 2：找一个 Finish=false 且 Need <= Work 的进程
Step 3：假设它能完成，释放资源：
        Work = Work + Allocation
        Finish = true
Step 4：重复找下一个能完成的进程
**Step 5：如果所有 Finish 都为 true，则系统安全**
        否则系统不安全

==**不安全状态不等于一定死锁**==

**易错点：==满足Need，增加Allocation==**
### **7. 银行家算法**

**场景：**
	**当前系统处于安全状态**  
	↓  
	某个进程 Pi 又**提出资源请求** Request_i  
	↓  
	系统要判断：**现在能不能把资源分给它？**

**思想**：
- ==**假装分配**==后再次检查系统是否仍然安全
	1. **==第一层：资源请求是否合法？==**
	2. **==第二层：如果分配，会不会破坏安全状态？**==
- 如果安全才正式分配
- 如果不安全，撤销分配，让进程等待

数据结构：在安全的基础上增加 **资源分配 `Request[i]`**

| 名称              | 含义                    | 你可以理解为      |
| --------------- | --------------------- | ----------- |
| `Available`     | 系统**当前**还能拿出来的资源      | 银行手里的现金     |
| `Max[i]`        | 进程 Pi 声明的**最大需求**     | 客户最多可能贷款多少  |
| `Allocation[i]` | 已经分给 Pi 的资源           | 已经借出去的钱     |
| `Need[i]`       | Pi 还可能需要多少资源          | 还可能继续借多少    |
| `Request[i]`    | Pi 这次申请多少资源           | 这次想借多少      |
| `Work`          | 安全性检查时的==**临时可用资源**== | 模拟过程中的现金    |
| `Finish[i]`     | Pi 是否能在模拟中完成          | 这个客户能不能顺利还钱 |

#### 1. 分配是否合法？ -- 合法性检查

1. 检查是否超过最大==**声明**==
	`Request[i] <= Need[i]`
	**处理：报错 / 不允许**
2. 检查**当前资源是否够分**
	`Request[i] <= Available`
	处理：Pi 等待

#### **2. 尝试分配**

1. 分配资源，**修改三个数据**
```shell
Available = Available - Request_i

Allocation[i] += Request_i

Need[i]  -= Request_i
```

2. 执行安全性算法，即寻找安全序列

**总结：**
```
① 检查 Request_i <= Need_i
若不满足，说明请求超过最大需求，出错。

② 检查 Request_i <= Available
若不满足，说明当前资源不足，Pi 等待。

③ 试探分配：
Available = Available - Request_i
Allocation_i = Allocation_i + Request_i
Need_i = Need_i - Request_i

④ 执行安全性算法：
Work = Available
寻找 Need_i <= Work 且 Finish=false 的进程
若找到，则 Work = Work + Allocation_i，Finish_i=true
重复直到不能继续

⑤ 判断：
若所有 Finish=true，则系统安全，请求可以分配。
若不是所有 Finish=true，则系统不安全，撤销试探分配，请求不能分配。
```

#### 3. 例题

三类资源 {A, B, C} 的总数量为 10、5、7

P3 good, Work = (5,3,2) + (2,1,1) = (7,4,3)
P4 good, Work += (0,0,2) = (7,4,5)
P2 good, Work += (3,0,2) = (10,4,7)
P0 good, All True, Request is safe


#### **4. 银行家算法的缺点**

1. 需要一个进程在运行前 **==提前知道Max==**，但这并不现实，进程连自己要申请多少资源都不确定
2. 算法进行时**进程数固定**，但系统内会不断有进程进入和退出
3. **不灵活**，比如可用资源可能突然故障，变为不可用
4. **算法开销大，实时性不好**

### **8. 预防 versus 避免**

> **预防和避免不是“时间先后关系”，也不是“避免更危急”**

**预防 -- ==禁止==** 
- **思想**：**==破坏==** 产生死锁的一个或多个 **==必要条件==**
- **方式**：增加限制条件
- **特点**：**简单、安全、粗暴**但是资源利用率可能低，==**限制**==也比较多，产生很多负效应

**避免 -- ==审批==**
- **思想**：**不让系统进入不安全状态**
- **方式**：动态检查、按次判断
- **特点**：更灵活

>[!help]+ 思考：满足预防+避免，是否一定能避免死锁？为什么还要检测？
> 1. 如果真的严格、完整、正确地做到预防或避免，**死锁就不会发生**
> 2. 预防太保守，代价高；避免算法要求太理想，有些资源不适合统一纳入银行家算法，因为他们很难提前声明Max
> 
> 因此有些系统选择“允许死锁，事后处理”这种成本更低的方式

### **9. 死锁检测**

死锁 = 资源分配图 + 不可简化

**对象**：
- 结点表示进程，方框表示资源
- ==**资源数量等于方框内圆圈数量**==

**关系**：
1. 进程占用资源：资源指向结点
2. 进程请求资源：结点指向资源

**简化：**
1. 找一个当前能继续执行并最终完成的进程 `Request <= Work`
	先看分配再看请求 ➡️ **请求数量 <= 方框圆圈数量 - 分配数量**
2. 假设它执行完，然后把它占有的资源全部释放
   **即从图中删掉这个进程相关的边**
3. **如果剩下进程无法继续删了，则不可完全简化**

> 不同于数据库里学到的进程等待图 + 拓扑排序，区别是这里资源会有多个实例，被多个进程占用

### **10. 死锁解除**

1. ==**剥夺资源**==：从某些死锁进程手里强行抢回资源，分给其他进程，打破等待环
	- **代价很大**：被剥夺的进程可能要回滚，已经完成的工作作废，并且资源可能无法安全剥夺，比如打印机

2. 撤掉进程：直接终止一个或者多个死锁进程，让他们释放资源
	- 损失小，但每次撤销都要重新检测是否还有死锁
