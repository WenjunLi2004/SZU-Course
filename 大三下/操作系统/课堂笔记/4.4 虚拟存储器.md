## 1. Motivation：基本分页的不足

**Relationship**：OS 真正更大的目标其实是让程序运行起来
- **分页**解决了 "连续存储" 的问题
- ==**基本**==分页其实有一个**隐含前提**：**一个进程运行前，它的==所有页==通常都要装入内存**
	> **分页的实现依然成立！**

- 所以还没解决的问题： "**没必要一次性把整个程序都放进内存**"

> 所以就如同 装入时链接 和 运行时链接
> **还是内存利用率的问题**

所以说，毫无疑问，**虚拟存储器思想**是

> **程序运行时，只把当前需要的部分装入内存；暂时不用的部分留在外存**

### 虚拟存储器和基本分页的关系

**基本分页**：**页表项记录 页号 → 物理块号**

**请求分页**：页表项不仅要记录页在哪个物理块，**还要记录这个页现在在不在内存**

**所以会在页表项增加信息：**

| 字段        | 作用              |
|-----------|-----------------|
| **物理块号**      | 如果页在内存，记录它在哪个块  |
| **状态位 / 存在位** | 记录该页是否在内存       |
| **访问字段**      | 记录访问情况，给置换算法用   |
| **修改位**       | 判断换出时是否需要写回外存   |
| **外存地址**      | 页不在内存时，记录它在外存哪里 |


## 2. 理论依据：局部性原理
**经典！**

程序在**一段时间**内，只会**集中访问** 一小部分代码和数据

1. **时间局部性**：如果某个数据或指令刚刚被访问过，那么它不久后很可能再次被访问
2. **空间局部性**：如果某个地址被访问了，那么它附近的地址不久后也很可能被访问

## 3. "虚拟" 在哪?
**同样非常经典！**

**程序以为自己拥有一个==很大的、连续==的地址空间**；
**但实际上，只有一==部分页在内存，其余页在外存==**

**虚拟存储器 = 请求调入 + 页面置换 + 外存伪装成内存的一部分**

## 4. 缺页中断 & 页面置换 ： 核心操作
> **插播：MMU = Memory Management Unit，内存管理单元**
> 主要负责把逻辑地址转换为物理地址，涉及拆分地址等一系列操作

**缺页中断 Page Fault**：**这个页不在内存**
- 操作系统介入，一系列操作把页面从外存调入内存，然后重新执行指令

**页面置换**：发生缺页并且内存满了，需要把置换一些在内存中的页
- 各种算法踢出一个页

## 5. 请求分页存储管理

需要解决的第一个问题：

> CPU 访问某个逻辑地址时，**怎么判断这个页到底在不在内存？**

所以请求页表在 **基本分页** 的 **页表** 上增加了一些新信息：

1. 这个页在不在内存？
2. 如果不在，那它在外存的哪里？ —— **缺页中断**
3. 如果要换出，它有没有被修改过？
4. 它最近有没有被访问过？

### 1. 请求分页页表 = 地址翻译 + 状态档案

| 字段         | 我的理解              |
| ---------- | ----------------- |
| **页号**     | 这是哪一页             |
| **物理块号**   | 如果在内存，它放在哪个 Frame |
| ==状态位 P==  | 这页现在是否在内存         |
| ==访问字段 A== | 最近有没有被访问，用于页面置换   |
| ==修改位 M==  | 调入内存后有没有被写过       |
| ==外存地址==   | 如果不在内存，它在磁盘哪里     |

### 2. 缺页中断会发生什么？
缺页中断不是错误，而是请求分页的**正常工作机制**

> 判断：页表状态位 P = 0

**缺页，自然而然，就要把页从外存调入内存，具体怎么调呢？**

1. 通过页表状态，OS找到这一页在外存地址
2. 找到一个空闲物理块：**前提是如果内存有空闲块**
3. 把页面从外存读入内存
4. 修改页表：`P=1` + 填写**块号**
5. **重新执行刚才的指令**

缺页中断相比普通中断的特别之处：
1. 可能发生在指令执行过程中
2. 一条指令可能多次缺页
   > copy A to B
   
### 3. 页面置换具体怎么做？

1. 算法决定换走谁—— `访问字段 A` 作为算法指标
2. 同时OS要给它擦屁股 —— **`修改位 M` 发挥作用**
	1. M = 0：未修改，换出时直接丢掉
	2. M = 1：已修改，换出时必须写回外存

**缺页中断和页面置换可以同时发生！**

## 6. 最小物理块数

请求分页需要解决的第二个问题：进程至少要几块内存才能运行？

> 那我问你：请求分页不就是需要哪块再去调哪块吗？

例子 : `Load A` 涉及的页面 
1. 1 块放指令页
2. 1 块放数据页
> 如果 间接寻址，指令跨页，源操作数跨页，那需要设计更多页
> **跨页**：指令、数据等又不是只占一个逻辑地址，所以可能前 4 个字节在第 0 页，后 2 个字节在第 1 页

如果分配的物理块极少：
1. 刚调入指令页，又缺数据页
2. 调入数据页时又把指令页换出去

所以==**问题的本质**==：**如果物理块数过少会导致进程==反复缺页==，根本无法正常推进**

**最小物理块数：保证进程至少能完成==一条指令==的==完整执行==**

> 注意这不是说永远只能给这么多块，而是至少保证有那么多块

> **满足最小后**如果需要更多，请求分页允许页 **按需调入**
> ⬇️ 分配策略
### 抖动 / 颠簸

**缺页太频繁**，称之为 **抖动** 或者 **颠簸**

**代价**：
1. 系统花大量时间换页，而不是执行用户程序
2. CPU看起来在运行，实际上大部分时间在等磁盘 I/O

更糟糕的是，如果 OS 看到 CPU 利用率下降，可能误以为：

> CPU 太闲了，应该再多调入几个进程

更多进程进入内存，会进一步减少每个进程能分到的物理块，使缺页更严重，形成恶性循环

#### 抖动的本质

不是某个置换算法的单点错误，而是：

> **进程的活跃页面集合大于它实际分到的物理块数**
> “最小物理块数”更偏底线 ，“抖动”更偏运行阶段

#### 解决方法
1. 给进程更多物理块
2. 减少并发进程数
3. 控制缺页率

## 7.  物理块分配策略
现在系统有很多进程，每个进程也只装入部分页面了，但是**整个物理内存块还是有限的**

**第三个问题：应该怎么分给不同进程？**

1. 固定分配 + 局部置换：稳定但不灵活，物理块负载不均衡
	> B用不完也不能借给 A
2. 可变分配 + 全局置换：灵活但互相影响
	> A 可能把 B 的页挤出去，导致 B 之后缺页
3. 可变分配 + 局部置换：折中方案
	> A 缺页率很高，B 可以多给 A 几块，但是又不相互影响

## 8. 置换算法

无论怎么换，都会遇到同一个问题：应该换出哪页？

OS必须回答：换出哪一页，才能让 **==未来缺页次数==尽量少**？

### 1. OPT：最佳置换算法

换出==**未来**== **最长时间不会被访问**的页面

> **谁能预测未来🤣**，理论最优但不可能实现

**唯一作用：做题的时候计算 理论最少缺页次数**
### 2. FIFO：先进先出算法

**谁最早进入内存，就先换出谁**
- **简单，但性能一般**

所以问题是：进入内存最早，**完全不代表现在最没用**，可能一直被频繁访问

⬇️ 进一步考虑**访问频率**
### 3. LRU：最近 最久 未使用
如果一个页面很久没有被访问，那么它接下来大概率也暂时不会被访问

> 这就是在反向利用 **局部性原理**

LRU，**Least Recently Used** , 最近最久未使用
-  ==**谁距离最近一次访问「上一次访问」的时间最久**==
#### 为什么LRU不容易实现？

每次访问内存时，都要更新页面的“最近使用记录”

1. **计数器**：每个页表项里加一个时间戳
	- 页面被访问时，记录当前时间
	- 置换时，找时间戳最旧的页面

> **每次访问都要更新时间戳，开销大**

2. **栈 / 链表**：每次访问某页，就把它移到栈顶或链表头

> **每次访问都要调整链表/栈结构，硬件实现复杂**

### 4. CLOCK：时钟置换算法

CLOCK 的思想是：

> LRU 很合理，但精确实现太贵；
> 那我们用**一个简单的访问位**来近似判断页面==最近==有没有被访问过

#### 核心结构

CLOCK 会把内存中的页面组织成一个==**环形队列**==

每个页面有一个访问位 `A`：

```
A = 1：最近被访问过
A = 0：最近没被访问过
```

**再用一个指针像钟表指针一样转**

所以叫：**时钟算法**

#### **置换规则**

1. 从当前指针指向的页面开始检查
2. 如果访问位 `A = 0`，说明最近没用过，换出它
3. **如果访问位 `A = 1`，说明最近用过，给它第二次机会，把 `A` 改成 0，指针后移**
4. 继续检查下一个页面

所以 CLOCK 也叫：

> **Second Chance Algorithm，二次机会算法**
> 最近用过的页面**先放过一次**；
> 如果下一轮还没被访问，就可以换出

#### 例子理解

假设内存里有 4 个页面：[1, 2, 3, 4]

访问位：
	1:A=1  
	2:A=0  
	3:A=1  
	4:A=0

**指针现在指向页面 1**

假设发生缺页，要换出一个页面

判断1：
- A = 1，说明最近用过
- 不给它换出，但把 A 改成 0
- 指针后移

判断2：
- A = 0，说明最近没用过
- 换出 2

**==最坏情况下 最多扫描两轮==**
#### CLOCK 和 LRU 的关系

可以理解为：**CLOCK 是 LRU 的低成本近似实现**

> CLOCK 只在意 ==最近一段== 时间有没有被访问过
> LRU 在意 ==谁最久== 没被访问

如果继续深究，简单CLOCK没考虑另一个重要问题：

> 这个页如果换出去，代价大不大？
> **代价：写回成本** ，磁盘 I/O 成本很高
### 5. 改进型 CLOCK：访问位 + 修改位

**先考虑是否访问，再考虑是否修改**

**所以优先级：**
1. `A=0 & M=0` : 最近没访问，也没修改 —— 最适合淘汰
2. `A=0 & M=1` : 最近没访问，但被修改过 —— 可以淘汰，但成本比 **1.** 高
3. `A=1 & M=0` : 最近访问过，也没修改 —— 不太应该马上淘汰；但如果真的要淘汰，代价不大
4. `A=1 & M=1` : 最近没访问，也没修改 —— 最不该淘汰

#### 特殊的两轮扫描过程
##### 第一轮：找 A=0, M=0
先找最理想的页面，如果找到，直接淘汰
- **扫描过程中不修改 A**
##### 第二轮：找 A=0, M=1
**这一轮扫描时，会把==扫描过的页面访问位 A 置为 0==**
- 给最近访问过的页面一次机会；如果下一轮还没被访问，就可能被淘汰
- 如果再来一轮，就必定能找到

> 重复前两轮，所以**最坏情况扫描四轮**
## 9. Belady 异常
FIFO 有一个很反直觉的问题：

> 分配的物理块数增加，缺页次数反而可能增加

这叫 **Belady 异常**

直觉上你会觉得：

```
给进程更多内存块 → 应该缺页更少
```

==**但 FIFO 不一定**==，原因是 **FIFO 只看进入顺序**

物理块变多后，页面在队列里的进入/淘汰节奏会变，反而可能在某些访问序列下做出更差的淘汰选择

注意：

> Belady 异常主要出现在 FIFO 这类算法中；OPT 和 LRU 一般不会出现这种异常

**为什么 LRU 不容易出现？** 因为 LRU 具有“栈性质”：

```
给更多物理块时，小内存中的页面集合通常包含在大内存的页面集合中
```

所以内存变多不会让它更差
