**进程**是操作系统最核心的概念
## 0. 为什么要引入进程
要理解进程，首先要理解**程序是如何运行的**
### （1）顺序执行
早期，程序是严格**按顺序一步步执行**的，**前一操作完成才能执行后继操作**
**三个特征：**
1. **顺序性**：下一操作要等待前一操作结束
2. **封闭性**：执行时独占资源，不受外界影响
3. **可再现性**：只要重复执行，就会获得相同结果


程序：Input -- Compute -- Print
每条语句也可以看做一个程序 
![[Pasted image 20260318224607.png#pic_center|575]]
### （2）前趋图：描述执行的先后关系
有向无环图：箭头“→”表示偏序或前趋关系
- Pi→Pj，称Pi是Pj的直接前趋，而称Pj是Pi的直接后继

![[Pasted image 20260318223402.png#pic_center|600]]
### （3）并发执行
现代操作系统为了提高效率，会让多个程序同时运行，导致程序
1. **间断性**：在并发环境下，多个程序共享系统的资源，所以当另一个程序占用需要的资源时，必须暂停等待，等待空闲再执行
2. 失去封闭性
3. ==**不可再现性**==：即使是**同样的程序、同样的输入，每次运行的结果都可能不一样**
——使得纯粹的 **“程序”在并发环境下无法正确运行**

为了保证程序能在**多程序环境**下**安全、正确地并发执行**，操作系统必须引入 **进程** 这个概念，给每个运行的实例分配一个独立的进程控制块（PCB）来记录它的现场和状态

## 1. 进程的基本概念
### 1. 什么是进程？(核心定义与结构)
- **官方定义**：**进程是==程序的一次执行==**，**是系统进行==资源分配和调度的基本单位==**

- **进程的结构由三部分组成：**
	1. **程序**：代码段，描述进程要完成的功能
	2. **数据**：数据段，进程执行时所需要的数据区
	3. **进程控制块 PCB**：**最重要的部分**！
		- PCB 是一种**数据结构**，用于**标识进程的存在**，并记录进程执行过程**各个时刻的状态特征** 
		  哪怕两个进程共享同一段代码程序，它们也必须拥有各自独立的 PCB 和数据集合
![[Pasted image 20260318225318.png#pic_center]]
**所以进程有四个特性**：
1. **动态性**：创建——执行——消亡
2. **并发性**：多个进程共存于内存中，并同时执行
3. **独立性**：资源独立，互不干扰
4. **异步性**：速度不可预测

#### **简单理解 进程 & 并发**
核心在于 ==**PCB + 独立数据区 → 完美重启**==
- PCB存储能够重启的状态特征：PC，寄存器状态...
- 数据独立：不被污染
所以说 **并发是宏观上同时，微观上交替**
#### **进程 vs. 程序 (经典对比)**

- **进程是动态**的执行实体，而**程序是静态**的数据与指令的集合 
    
- **进程有生命周期**（会创建、消亡），而**程序是永存的**（只要不删就一直存在硬盘里）
    
- **进程执行**需要竞争 CPU 等资源，**程序存储**只需要存储器
    
- ==**一个程序运行时可以衍生出多个进程**==

### 2. 进程分类
1. **系统进程 （VIP 玩家）**：运行在管态（核心态、系统态）
	它们被分配了初始资源，可以直接独占使用，并且拥有最高优先权，可以为所欲为，比如执行一切指令、直接做 I/O 操作、访问受保护的寄存器
2. **用户进程（普通玩家）**：运行在目态（用户态）
	它们没有特权，必须通过“**服务请求**”的方式来竞争资源
	不能直接操作 I/O 设备，只能执行指定的指令和访问指定的内存

### **3. 进程的“生命周期”：三大基本状态**
1. **创建状态  Created**：进程刚刚开始初始化，**已经分配了 PCB，但还没有获得所需的物理资源**（比如程序数据还没读入内存），也没有进入调度队列
    
2. **==就绪状态== Ready**：万事俱备，只欠东风
	进程已经获得了除 CPU 以外的所有资源，正**乖乖待在就绪队列里排队等候分配 CPU**
	
3. **==执行状态== Running**：成功获得 CPU，正在执行指令 
    
4. **==阻塞状态== Blocked**：进程在运行中**遇到了需要等待的事件**（比如请求 I/O 读取文件、请求缓冲空间等），导致暂时无法继续，于是 **==主动放弃== CPU** 处于暂停状态，进入阻塞队列
    
5. **终止状态 Terminated**：进程执行完毕或被外力异常终止
  此时系统正在回收它的全部资源，它永远不能再获得 CPU 执行

![[Pasted image 20260318232331.png#pic_center|425]]
```
New → Ready → Running → Terminated
                ↓
             Blocked
                ↓
              Ready
```

### **4. 进阶大 Boss：挂起状态 (Suspend) 与 七状态转换**
**挂起状态** 是一种 **更深度的静止状态**，被挂起的进程不能马上投入运行
- **为什么挂起？** 常见原因：终端用户想要暂停程序进行调试 、父进程请求同步 、操作系统的负荷太重需要==**减轻内存压力**== ，或者是操作系统需要检查资源使用情况
- **四个派生状态与转换原语**：因为有了**挂起 (suspend)** 和**激活 (active)** 这两个操作 ，原本的**就绪和阻塞**裂变成了四个状态：
	- **活动就绪 (Readya)** 被挂起 $\rightarrow$ **==静止就绪== (Readys)**
	- **活动阻塞 (Blockeda)** 被挂起 $\rightarrow$ **==静止阻塞== (Blockeds)**
	- 反之，使用“激活”原语可以从静止状态恢复到活动状态
![[Pasted image 20260318233702.png#pic_center|550]]
### **5. PCB(Process Contrl Block) 进程控制块**
PCB是==**进程存在的唯一标志**==，OS是根据PCB来对并发执行的进程进行控制和管理的

#### **1. PCB 里到底装了什么？**
可以把 PCB 想象成进程的 **“个人档案”和“工作日志”**，里面记载了**四个核心信息** ：
- **进程标识符 PID**：进程的身份证号，用来**唯一标示这个进程**
	
- **处理机状态**：==**核心！**== 里面保存了 CPU 内部**各种寄存器的内容**
	当进程被暂停时，当前的计算进度就会“截图”保存在这里，等下次恢复运行拿出来接着算
    
- **进程调度信息**：记录了**进程的优先级、等待了多久**等，帮助操作系统决定下一个让谁上 CPU 运行
    
- **进程控制信息**：记录了这个进程**拥有哪些资源**（比如分配了哪些内存、打开了哪些文件）

#### 2. 操作系统怎么收纳这堆 PCB？
两种主流的组织方式 ：
1. **链接方式**：操作系统把具有相同状态的 PCB 用**指针链接成一个队列**
	比如所有的就绪状态 PCB 串成一个“就绪队列”，阻塞状态的串成“阻塞队列” 
![[Pasted image 20260319000046.png#pic_center|525]]
2. **索引方式**：像查字典的目录，系统建立几张“==**索引表**==”（比如就绪索引表、阻塞索引表），表里记录着指向各个 PCB 的地址
	要找哪个状态的进程，直接查表就行
![[Pasted image 20260319000140.png#pic_center|650]]
## 2. 进程控制
进程控制，就是操作系统对“进程一生”的管理：**创建**、运行、等人、被叫醒、暂停、恢复、死亡

本质：**操作系统不断==移动==进程的 PCB，让它在不同==队列和状态==之间变化**
### 2.1 重点：父进程和子进程的关系

- 父进程：**系统**或**用户**首先创建的进程
- **子进程：父进程创建的进程**

1. **子进程由父进程创建或撤销**：父进程有权管理子进程，但子进程不能反过来控制父进程
2. **子进程可以继承父进程资源**：比如父进程打开了某些文件，子进程可能继承文件句柄；父进程有某些权限，子进程可能部分继承
3. **父子进程可以同时运行，也可以有先后关系**：比如父进程创建子进程后，可以继续干自己的；也可以等子进程结束后再继续
4. ==**这种关系记录在 PCB 里**==：PCB 不只是记录“我是谁”，还记录“父进程是谁，孙子进程是谁”

---
### 2.2 原语
**原语 = 操作系统中==不可分割==的基本操作**
- 要么成功，要么完全不发生

比如“把进程从执行态改成阻塞态”时，至少要做几件事：
1. 保存 CPU 状态  
2. 修改 PCB 状态  
3. 插入阻塞队列  
4. 重新调度 CPU
**这些事情必须作为一个整体完成**
不能只改了状态，还没插入队列；也不能插入队列了，但 CPU 状态没保存

所以：
```
原语 = 操作系统内核中不可中断的动作  
特点 = 要么全做，要么全不做  
作用 = 保证进程状态转换不会乱
```

后面的**创建、终止、阻塞、唤醒、挂起、激活**，本质上都靠原语完成
- create
- exit/terminate
- block
- wakeup
- suspend
- active

---
### 2.3 进程创建 create

什么时候会创建进程？
- 用户登录
- 系统调度作业
- 程序请求服务
- 主动创建

**Linux 里常见的是 `fork()`**

底层做了些什么？
1. **申请空白PCB**：PCB 是进程存在的标志
2. **分配资源**：分配内存、文件、I/O 资源等
3. **初始化PCB**：
	- 进程标识符 PID
	- 父进程是谁
	- 当前状态
	- 程序入口地址
	- CPU 寄存器初始状态
	- 资源信息
	- 优先级
4. **==插入就绪队列==**：排队等 CPU 调度

---
### 2.4 进程终止 exit / terminate

**进程为什么会终止？**

主要三类：

#### 第一类：正常结束

程序自己跑完了，例如：return 0;

或者用户正常注销、程序正常退出。

#### 第二类：异常结束

程序出错了，被系统终止

比如：
- 数组越界  
- 非法指令  
- 权限错误  
- 除零错误  
- 运行超时  
- I/O 故障

你写 C 程序段错误 `Segmentation fault`，就是典型异常终止

#### 第三类：外界干预

别人把它杀了

比如：

- 用户在任务管理器结束任务  
- 父进程要求子进程结束  
- 操作系统强制终止  
- 父进程终止导致子进程也被处理

**==终止过程==像“退学手续”：**

1. 找到它的 PCB  
2. 查看它当前状态  
3. 如果正在执行，立刻停掉  
4. 终止它的子孙进程  
5. 回收资源  
6. 把 PCB 从队列中移出

**这里有一个重点：**

> 进程死了，不只是“程序不跑了”，还要释放它占用的一切资源

比如内存、打开的文件、I/O 设备、PCB 等等

否则会出现资源泄漏

---
### 2.4 进程阻塞 block ：进程主动说“我先等一下”
**阻塞不是进程坏了，而是它暂时等条件**
- 比如一个进程正在执行，突然它要读硬盘文件：CPU很快但硬盘很慢，如果一直占着CPU等硬盘，那就是浪费
- 不如**主动进入阻塞队列**等 I/O 完成

**引起阻塞的事件：**
- 请求系统服务
- 启动某种 **I/O** 操作
- **等待**新数据到达：read(fd, buffer, size) ，如果数据没准备好，进程可能被阻塞
- 暂时无工作可做

**重点：**
> 阻塞是进程自身的==**主动行为**==

**==阻塞底层在做什么？==**

1. 保存现场信息：能继续在停下的位置往下执行
2. 状态从执行态改为阻塞态
3. 把 PCB 插入阻塞队列
4. 重新调度CPU
5. CPU切换给另一个就绪进程
---
### 2.7 进程唤醒 wakeup：条件到了，把它从等待区叫回来
阻塞之后，进程不是自己回来，而是要被唤醒

例如：

	I/O 完成了  
	数据到了  
	资源可用了  
	等待的事件发生了

这时某个相关进程或操作系统**调用 `wakeup` 原语**

**==唤醒过程==：**
1. **从阻塞队列中移出 PCB**  
2. **把状态从阻塞改为就绪**  
3. **插入就绪队列**  
4. **等待 CPU 调度**

注意：**==唤醒之后不是马上执行，而是进入就绪队列==**

回忆经典关系图：阻塞 → 唤醒 → 就绪

### 2.8 挂起 suspend：把进程从内存“搬到外存”
#### 区分阻塞和挂起

**阻塞：进程在等事件**  
**挂起：进程被暂时移出内存**

可以这样理解：
- **阻塞 = 人在等材料**  
- **挂起 = 人被请出教室，档案和东西暂时放仓库**

#### **为什么要挂起？**

**常见原因：**
- 内存不够  
- 系统负载太高  
- 用户或父进程要求暂停  
- 操作系统需要腾出资源

挂起时，进程可能原来是：
- **活动**就绪  
- **活动**阻塞

挂起后变成：
- 活动就绪 → 静止就绪  
- 活动阻塞 → 静止阻塞

**这里的“活动”和“静止”主要看它是否在内存里**

==**活动 = 在内存中**==
==**静止 = 被换出到外存**==

所以状态可以这样理解：

- 活动就绪：人在教室里，准备上台  
- 静止就绪：人不在教室，在外面仓库/宿舍，但事情已经准备好  
- 活动阻塞：人在教室里，但在等材料  
- 静止阻塞：人不在教室，而且还在等材料

**挂起过程大致是：**

1. 检查**进程状态**  
2. 活动就绪改为静止就绪  
3. 活动阻塞改为静止阻塞  
4. 复制 PCB 到指定内存区域  
5. 把数据复制到外存  
6. 释放内存  
7. 如果它正在执行，则重新调度

**本质**：==**挂起 = 为了节省内存，把进程暂时换出**==

---

### 2.9 激活 active：把挂起的进程重新搬回内存

激活就是挂起的反向过程

#### 什么时候激活？
- 用户请求恢复  
- 父进程请求恢复  
- 内存空间足够了  
- 系统决定让它回来

#### 激活过程

1. 把进程从外存调入内存  
2. 检查当前状态  
3. 静止就绪改为活动就绪  
4. 静止阻塞改为活动阻塞  
5. 如果进入就绪队列，可能重新调度

#### 重点

**激活不是一定立刻运行**，而是回到==**“活动状态”**==

1. 如果它本来是静止就绪：**静止就绪 → 活动就绪**
   它回来后可以竞争 CPU
2. 如果它本来是静止阻塞：**静止阻塞 → 活动阻塞**
   它虽然回到内存了，但还在等事件，所以不能运行
### 阻塞 vs 挂起

| 概念  | 原因            | 是否缺 CPU | 是否缺事件/资源 | 是否在内存  |
| --- | ------------- | ------- | -------- | ------ |
| 阻塞  | 等 I/O、等数据、等事件 | 是       | 是        | 通常还在内存 |
| 挂起  | 被换出内存         | 是       | **不一定**  | 不在内存   |
| 就绪  | 只差 CPU        | 是       | 不缺       | 在内存    |
| 执行  | 正在用 CPU       | 不缺      | 不缺       | 在内存    |
### 唤醒 vs 激活
**唤醒**：阻塞 → 就绪，**等的事件完成了**
**激活**：静止 → 活动，**重新调入内存了**

### **总结**

| 操作  | 原语               | 状态变化    | 核心动作                  |
| --- | ---------------- | ------- | --------------------- |
| 创建  | create           | 无 → 就绪  | 申请 PCB、分配资源、初始化、入就绪队列 |
| 终止  | terminate / exit | 任意 → 终止 | 停止执行、终止子孙、回收资源、移出 PCB |
| 阻塞  | block            | 执行 → 阻塞 | 保存现场、入阻塞队列、重新调度       |
| 唤醒  | wakeup           | 阻塞 → 就绪 | 出阻塞队列、改为就绪、入就绪队列      |
| 挂起  | suspend          | 活动 → 静止 | 换出到外存、释放内存            |
| 激活  | active           | 静止 → 活动 | 调入内存、恢复为活动状态          |
## 3. 进程同步
**进程同步，就是让多个并发进程在==共享资源、互相合作==时，不乱、不抢、不出错，并且==结果可重复==**

### 3.1 为什么需要进程同步？
多个进程可以并发执行，所以不可避免就有并发面临的麻烦：**资源共享**

	进程 A 执行一半，CPU 可能切给进程 B
	进程 B 执行一半，CPU 又可能切回来

如果它们都在操作同一个东西，就可能出错

**不是算法错了，而是执行顺序乱了**

### 3.2 进程同步到底在同步什么？

❌ 同步 = 所有进程同时运行

✅ 同步 = 让多个进程按照**某种==正确的配合关系==** 运行

	菜没做好，服务员不能端
	菜做好了，厨师不能无限往桌上堆
	桌子满了，厨师要等
	桌子空了，服务员要等

因此进程同步包含两类关系：

#### **1. 间接相互制约关系**
常见的例子就是 **申请I/O、CPU**

- 多个进程本身没有直接合作关系，但要 **争同一个资源**
- 而同一个资源一次只能给一个进程用

#### **2. 直接相互制约关系**
常见的例子是 **输入与运算**

	进程 A：负责输入数据
	进程 B：负责计算数据
	B 必须等 A 输入完才能算

**进程之间有明确的合作顺序**

### 3.3 临界资源：大家都想用，但一次只能一个人用

**临界资源**：一次仅允许一个进程访问的共享资源
- 可以是硬件：打印机
- 也可以是软件：共享变量、共享缓冲区、共享文件

**共享 + 修改 + 同时访问会出错 ≈ 临界资源**

### 3.4 生产者=消费者问题：进程同步的经典例子

**这个例子非常重要，后面信号量经常用它讲**

想象一个奶茶店：

	生产者：做奶茶的人  
	消费者：取奶茶的人  
	缓冲池：放奶茶的取餐架，取餐架有 n 个位置

**规则是：**

1. 生产者每次放入**一个**产品，占用一个缓冲区 
2. 消费者每次取走**一个**产品，释放一个缓冲区  
3. 生产者不能往满的缓冲池里放
4. 消费者不能从空的缓冲池里取
5. **同一时刻只能有一个进程操作缓冲池**

**所以这里有两个问题**

#### **1. 顺序同步**
- **缓冲池空时，消费者要等**
- **缓冲池满时，生产者要等**
—— 同步关系

#### **2. 互斥访问**
**生产者和消费者不能同时修改缓冲池**
—— 互斥关系

### 3.5 经典变量定义：缓冲池、in、out、counter
#### 1. Buffer 缓冲区
==**数据结构是一个环形队列**==
![[Pasted image 20260425221952.png]]
#### 2. in指针
**in：指向下一个可以==放==产品的空缓冲区**
e.g. write_in

生产者每放入一个产品：
`buffer[in] = 产品`
`in = (in + 1) mod n`

#### 3. out指针
out：指向下一个**可以==取==产品**的满缓冲区

消费者每取一个产品：
`产品 = buffer[out]`
`out = (out + 1) mod n`

#### 4. counter变量
counter：当前缓冲池里产品数量

**初始时：**

	in = 0  
	out = 0  
	counter = 0

`counter = 0` 表示缓冲区为空，`counter = n` 表示缓冲区满

**并发==乱序执行==会导致 counter 错误**

> 环形队列另一种不使用counter的判断方式：`in = out` 表示缓冲区为空，`(in+1) mod n = out` 表示缓冲区满

### 3.6 为什么乱序交叉共享变量 counter 会出错？
表面上：

	生产者：counter = counter + 1
	消费者：counter = counter - 1

**问题在于**： `counter = counter + 1` 不是一条**真正不可分割的操作**

**它在机器内部通常会拆成多条指令**

#### 1. counter + 1 的底层过程
**先存到寄存器，+1后再写回counter**
1. register1 = counter
2. register1 = register1 + 1
3. counter = register1

counter - 1 的底层过程同理：
1. register2 = counter
2. register2 = register2 - 1
3. counter = register2
#### 2. 乱序交叉执行

生产者：register1 = counter        // register1 = 5
生产者：register1 = register1 + 1  // register1 = 6

消费者：register2 = counter        // register2 = 5
消费者：register2 = register2 - 1  // register2 = 4

生产者：counter = register1        // counter = 6
消费者：counter = register2        // counter = 4

最后 counter 变成了 4，但正确结果应该是 5

这种问题叫做：==**竞争条件**==
- 多个进程并发访问和操作同一共享数据，最终结果取决于进程执行的**相对时序**

### 3.7 临界区 **critical** section

**临界区**：进程中访问临界资源的那段代码
比如生产者代码中：

	buffer[in] = nextp  
	in = (in + 1) mod n  
	counter = counter + 1

这段在操作共享缓冲池和共享变量 counter，所以它属于临界区

消费者代码中：
	
	nextc = buffer[out]  
	out = (out + 1) mod n  
	counter = counter - 1

这段也属于临界区

>[!help]+ **只读不写算临界区吗？**
> **只读共享数据，不算临界区！必须修改**
> Critical 危急的
#### 1. 临界区程序结构
```txt
repeat
    entry section;
    critical section;
    exit section;
    remainder section;
until false;
```

**entry section 进入区**：进入临界区之前，检查自己能不能进去
- 有没有别的进程正在使用临界资源，如果有则等待

**同一时刻最多只能有一个进程在临界区内**

**exit section 退出区**：离开临界区后，释放使用权

**remainder section 剩余区**：和临界资源无关的代码
### 3.8 同步机制必须遵循的四条规则
**空闲让进、忙则等待、有限等待、让权等待**

1. 空闲让进 ：当临界资源空闲时，应允许**一个**请求进入临界区的进程立即进入

2. 忙则等待：当已有进程进入临界区时，其他试图进入临界区的进程必须等待 **【互斥】**

3. **有限等待**：对请求进入临界区的进程，应保证它能在有限时间内进入，不能无限期等待

4. **让权等待**：当进程不能进入临界区时，应阻塞释放 CPU，避免**忙等待**

### 3.9 信号量机制：解决同步和互斥的核心工具 **（重点）**

**信号量本质**：一个带规则的资源==**计数器**==
- S=1 表示某种资源只有一个

**⚠️：它==不是普通整数==，因为不能随便访问它**

⬇️

信号量只能通过两个原子操作访问
- wait(S) ： P 操作，申请资源 / 进入前检查
- signal(S)：V 操作，释放资源 / 离开后归还

#### **1. 整型信号量：简单但会忙等**

**wait(S)**：如果 S > 0，说明有资源，于是 S = S - 1，拿走一个资源；如果S <= 0，没资源就一直循环等

	wait(S):
	    while S <= 0 do no-op;
	    S = S - 1;

**signal(S)**：S = S + 1表示释放一个资源

	signal(S):
	    S = S + 1;

整型信号量的问题在于**忙等**，没有拿到资源时一直占着CPU，所以它不满足 **让权等待**

#### 2. 记录型信号量：真正体现 block / wakeup
为了解决忙等问题，记录型信号量多了一个==**等待队列**==

结构是：

	type semaphore = record  
	    value: integer;        // 资源可用数量  
	    L: list of process;    // 等待进程队列  
	end

也就是说，它不只是一个整数，而是：
==**可用资源数量(S.value) + 等待队列**==

形象理解 -- 叫号系统：  

- **value** = 当前还能服务几个顾客  
- **L** = 没轮到的人坐在等待区

#### 3. 重点：记录型信号量的PV操作

	wait(S):
    S.value = S.value - 1;
    if S.value < 0 then block(S.L);

进程==**先申请一个资源（S.value - 1）**==，如果真的有（S.value >= 0）则继续执行，否则进程要**阻塞**，进入等待队列 S.L

> block：wait 失败 → block → 释放 CPU → 进入等待队列


>[!check]+ Value 精妙之处
>**先申请资源， S.value < 0表示阻塞进程的个数**，比如S.value = -2表示有 2 个进程正在等待这个资源
>这样signal直接根据value来判断是否有进程在等，不用额外检查等待队列S.L是否为空

同理：**signal(S)先释放一个资源，再判断是否有人在等待**

	signal(S):
    S.value = S.value + 1;
    if S.value <= 0 then wakeup(S.L);

> wakeup：signal 释放资源 → wakeup 一个等待进程 → 进入就绪队列


#### 4. 互斥信号量：S 初值为 1
S.value 初值为 1，表示只允许一个进程访问临界资源，此时信号量转化为互斥信号量

**常见的互斥**：`mutex = 1` 
### 3.10 经典互斥例子：银行存取款

共享变量 counter：银行余额

两个进程：P1存款300，P2取款200

如果没有信号量，两个操作交叉执行，最后结果取决于谁最后写回

解决方案：**加入mutex信号量** 将共享变量读 → 改 → 写变成原语

	P1:  
		wait(mutex);  
		count += 300;  
		signal(mutex);  
	  
	P2:  
		wait(mutex);  
		count -= 200;  
		signal(mutex);

### 3.11 AND型信号量

#### **为什么需要？**

假设有两个资源：Dmutex和Emutex，初值都是 1（两把锁）

有两个进程：

- process A:  
    wait(**Dmutex**);  
    wait(Emutex);  
  
- process B:  
    wait(**Emutex**);  
    wait(Dmutex);

一种执行顺序是：

A 拿到 Dmutex  
B 拿到 Emutex  
A 想拿 Emutex，但被 B 占着，于是 A 阻塞  
B 想拿 Dmutex，但被 A 占着，于是 B 阻塞

结果：

A 等 B  
B 等 A

==**谁都不释放，死锁**==

**这就是典型死锁：两个人都拿着一部分资源，都在等对方释放另一部分资源，最后都被阻塞**

#### **基本思想**

将进程整个运行过程中需要的==**所有资源，一次性全部分配给进程**==；只要有一个资源不能分配，其它资源也不分配

#### Swait 和 Ssignal
**Swait(S1,S2,...,Sn)** = wait(S1) ==**AND**== wait(S2) 表示同时申请多个资源
 
	if Si≥1 and … and Sn≥1 then //每种资源数量都大于1才分配
		for i ∶ = 1 to n do
		Si ∶= Si-1;
		endfor

Ssignal(S1, S2, ..., Sn)  把占用的多个资源一起释放，并唤醒相关等待进程重新判断

### 3.12 信号量集：一次申请多种资源，每种还可以要多个

前面几种可以这样对比：

- **记录型**信号量：**申请 1 种资源，数量 1 个**  
- AND 型信号量：**申请 n 种资源**，**每种数量 1 个**  
- **信号量集：申请 n 种资源，每种数量可以是多个**

比如一个进程运行需要：

	打印机 1 台  
	磁带机 2 台  
	内存块 5 块

**这就不是简单的一个信号量能表达的**

信号量集可以表达：

**资源 S**：资源当前数量
**下限值 t**：判断是否允许分配的下限，`if Si≥t1 and … and Sn≥tn ` 所有资源种类大于下限值才分配时，才允许申请
>下限确保资源存在，最直观存在 Swait(S,d,d)

**需求值 d** ：真正要拿走的资源数量


形式是：`Swait(S1, t1, d1, ..., Sn, tn, dn)`

	如果每种资源都达到对应下限 t：  
	    分配对应需求数量 d  
	否则：  
	    阻塞

Swait(S, 3, 3)：一个任务一次需要 3 台设备
Swait(S, 1, 1)：普通记录型信号量
**Swait(S, 1, 0)：相当于一个可控开关**，S >= 1：门开着，大家可以进；S = 0：门关了，谁都不能进
### 3.13 逻辑梳理
**并发**进程会**共享资源**
        ↓
共享资源可能被**同时访问**
        ↓
同时访问会造成**竞态条件**
        ↓
把访问共享资源的代码称为**临界区**
        ↓
临界区必须**互斥**进入
        ↓
**同步机制**要满足空闲让进、忙则等待、有限等待、让权等待
        ↓
**信号量**提供 P/V 操作
        ↓
P 负责申请资源，失败则阻塞
        ↓
V 负责释放资源，并唤醒等待进程
        ↓
多个资源同时申请时，用 AND 型信号量或信号量集

## 4. 经典线程同步

### 4.1 进程同步问题的三类矛盾

1. **互斥**：**同一个资源**，**同一时刻只能一个进程** 访问
	- 共享变量，缓冲区
	- 一般用 互斥锁：wait(S) -> critical -> signal(S)

2. **同步**：某个动作必须等另一个动作完成之后才能做
	- 公交车：关门后才能开车，停车后才能下车
	- 通常是：
		1. A 做完某事：signal(S)「完成条件」
		2. B 做某事前：wait(S)「等待条件」

3. **死锁避免**：通常来自进程先拿了一部分资源，然后等待另一部分资源

### 4.2 信号量应用
#### **经典例子：信号量实现互斥锁**
```
semaphore mutex = 1;

process:
    wait(mutex);
    critical section;
    signal(mutex);
    remainder section;
```

==**信号量的重要规则**==：`wait` 和`signal`必须成对出现，==**不等于必须在同一个进程中**==

#### **例子：生产者消费者模型**
三个信号量：
1. mutex：互斥锁
2. empty：还能生产多少
3. full：剩余多少产品


**生产者：**
```
wait(empty)
wait(mutex)

buffer[in]=product
in=(in+1)%count

signal(mutex)
signal(full)

```

**消费者：**
```
wait(full)
wait(mutex)

product = buffer[out]
out = (out+1)%count

signal(mutex)
signal(empty)
```

- `P(empty)` 在生产者里
- `V(empty)` 在消费者里
**它们是“成对”的，但不在同一个执行单元里**

**关键口诀：先私后公**
- 先执行对资源信号量的 wait，再执行对互斥信号量的 wait

进一步区分：
1. 互斥/公用信号量：必须在单个进程中成对出现
2. 资源/公有信号量：必须成对出现，但可不同进程

#### 被唤醒进程应该插队头还是排队尾？
规则1：阻塞进程被唤醒后，立即插入队列头，作为下一个执行对象
规则2：阻塞进程被唤醒后，放入队列末尾

**结论：阻塞进程被唤醒后优先执行，可以减少后续阻塞次数**

**形象理解：**

```
一个人因为没座位在等。刚好有人让出座位
如果立刻让等待的人坐下，效率高
如果让他重新排到队尾
这个座位可能又引发一堆新的混乱
```

#### AND信号量实现 生产者消费者

刚好mutex和 full/empty 都是需要同时获得才进入 critical section

生产者：

```
Swait(empty, mutex);
buffer[in] = nextp;
in = (in + 1) mod n;
Ssignal(mutex, full);
```

消费者：

```
Swait(full, mutex);
nextc = buffer[out];
out = (out + 1) mod n;
Ssignal(mutex, empty);
```

### 4.3 管程：把信号量封装起来
把共享数据 + 操作共享数据的方法 + 同步控制
==**封装**==成一个“受保护的对象”

比如生产者—消费者封装为：
```
producer:
    PC.put(item);

consumer:
    PC.get(item);
```
把复杂同步细节藏进 `PC.put()` 和 `PC.get()` 里面

### 4.6 哲学家进餐问题

5 个哲学家+圆桌
**5 ==根==筷子**
每个哲学家需要左、右两根筷子才能吃饭  
每根筷子同一时刻只能被一个哲学家拿
![[ChatGPT Image 2026年4月29日 20_26_20 1.png]]
**筷子是临界资源，需要互斥**
- **设置chopstick[0..4] = 1**

**问题：怎么避免死锁，让至少一个哲学家能吃饭**

最朴素做法：等待左筷子 -> 等待右筷子
- 保证不会有两个相邻哲学家同时吃饭
- 如果都拿左筷子，那也会陷入死锁
#### 方法一：最多允许 4 个哲学家同时拿筷子

设置一个信号量：

```
room = 4
```

每个哲学家：

```
wait(room);
wait(left);
wait(right);
eat;
signal(right);
signal(left);
signal(room);
```

为什么能避免死锁？
- 因为最多 4 个人拿左筷子时，**至少有 1 根筷子是空的**
这样总能让<u>某个人</u>拿到两根筷子并吃饭，吃完释放资源，系统继续推进

---

#### 方法二：左右筷子都可用时才允许拿

这就是 AND 信号量思想：

```
Swait(left, right);
eat;
Ssignal(left, right);
```

要么两根都拿到，要么一根都不拿。

这样不会出现：

```
每个人拿着一根，等另一根
```

因为不允许部分占有。

---

#### **方法三：奇偶哲学家拿筷子顺序不同**

比如：

```
奇数号：先拿左，再拿右
偶数号：先拿右，再拿左
```

这样破坏了所有人按同一方向等待的环形结构

奇数号和偶数号竞争不同筷子，最后总会有一位哲学家能获得两只筷子而进餐

这背后的思想是：==**打破循环等待条件**==

死锁的一个重要原因是循环等待：

```
P0 等 P1
P1 等 P2
P2 等 P3
P3 等 P4
P4 等 P0
```

只要破坏这个环，就能避免死锁

### 4.7 读写锁

**共享数据文件**
1. 多个读者「Reader」可以同时读
2. 同时只能有一个进程写「Writer」
3. 写的时候其他进程不能读
4. 读的时候其他进程不能写
	**读-写/ 写-写：互斥**

#### 怎么用信号量解决？

wmutex = 1：读和写进程互斥
rmutex = 1 // 保护 **readcount**
**readcount** = 0 // 当前正在读的读者数量
##### readcount 为什么需要？
因为多个读者可以同时读
第一个读者进入时，需要阻止写者：

```
if readcount == 0:    wait(wmutex);
```

意思是：

```
我是第一个读者，我要把写者挡在外面
```

后续读者进入时：

```
readcount > 0
```

**说明已经有读者在读，写者已经被挡住了，所以后续读者不用再 wait(wmutex)，可以直接加入读**

最后一个读者离开时：

```
if readcount == 0:    signal(wmutex);
```

意思是：

```
现在没有读者了，可以让写者进来了
```

所以：

```
第一个读者负责关门，最后一个读者负责开门
```

所以为了保护readcount，增加rmutex保护共享变量

#### 代码逻辑

```
READER:
    repeat
        wait(rmutex);
        if readcount == 0:
            wait(wmutex);
        readcount = readcount + 1;
        signal(rmutex);

        perform read operation;

        wait(rmutex);
        readcount = readcount - 1;
        if readcount == 0:
            signal(wmutex);
        signal(rmutex);
    forever
    
WRITER:
    repeat
        wait(wmutex);
        perform write operation;
        signal(wmutex);
    forever
```

## 5. 进程通信

进程通信就是**进程之间交换信息**

前面学的信号量其实也算通信，但它交换的信息很少，称为「**低级通信**」 —— 效率低，数据量太少，需要自行控制进程
真正的 **「高级进程通信」**，是用户直接使用**操作系统提供的通信指令**，高效传送大量数据

### 5.1 三种高级进程通信方式
**共享存储器 Share Memory**
**消息传递 Message Passing**
**管道通信 Pipe**

##### 1. 共享存储器：Pthreads
多个进程共享一块内存区域

- **优点：速度快，简单直接**
- 缺点：要自己处理**互斥和同步**
	- 常常需要搭配 **互斥锁、信号量、条件变量**
	- **防止并发访问出错**
##### 2. 消息传递：报文
进程之间以**格式化**的消息为单位交换数据
- 消息里面有发送者、长度、内容等==**字段**==
- **应用最广泛的一种进程间通信机制**

- 优点：程序员友好，只需要send / receive，由操作系统管理细节

#### 3. 管道通信： Linux的 ｜

**管道 Pipe**可以理解为一根连接两个进程的“水管”
	**一个进程写，一个进程读，像文件一样传输字符流**

**本质**：连接一个读进程和一个写进程的==**共享文件**==，也叫 pipe 文件；写进程把字符流送入管道，读进程从管道接收数据

**协调机制：**
1. 读写互斥
2. 同步：写 -> 读
3. 确实存在：三方握手

经典例子：`ls | grep txt`
- ls 的输出 → 管道 → grep 的输入

### 5.2 直接通信 vs 间接通信

#### 1. 直接通信：点名发送
发送者明确指定接收者
接收者也可以明确指定发送者
⬇️
以前用信号量时，要自己写 wait / signal
用消息传递时，send / receive 内部帮你处理等待

#### 2. 间接通信：通过信箱转发
**发送者 → 信箱 mailbox → 接收者**
间接通信需要某种 **==共享数据结构==** 作为中介，这个中介一般称为**信箱 mailbox**，所以间接通信又叫**信箱通信**

对应原语有：

```
Create(mailbox)
Delete(mailbox)
Send(mailbox, message)
Receive(mailbox, message)
```

**区分了三种信箱**：
1. 私用信箱：某个进程自己的邮箱
2. 公用信箱：操作系统建的公共邮箱
3. 共享信箱：一组进程共享的邮箱
