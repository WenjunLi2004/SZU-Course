## 1. 请求分段存储管理方式

### 1.1 本质

**请求分段 = 基本分段 + 虚拟存储器思想**

也就是：

- 基本分段：程序按逻辑意义划分为多个段
- 请求机制：不是所有段一次性装入内存
- 缺段中断：访问合法段但该段不在内存时触发
- 分段置换：内存不够时，把暂时不用的段换出

可以和请求分页对应记忆：

| 对比 | 请求分页 | 请求分段 |
|---|---|---|
| 基础 | 基本分页 | 基本分段 |
| 调入单位 | 页 | 段 |
| 中断 | 缺页中断 | 缺段中断 |
| 置换 | 页面置换 | 分段置换 |
| 单位大小 | 固定 | 不固定 |
| 更适合 | 内存离散管理 | 共享、保护、动态链接 |
### 1.2 请求分段的**段表扩展**

基本分段的段表主要记录：

- 段长
- 段基址

请求分段还需要增加：

- **状态位**：该段是否已经在内存
- **访问字段**：该段最近是否被访问，用于置换
- **修改位**：该段调入后是否被修改
- **外存地址**：该段在外存中的位置
  
- **==存取控制字段==**：读、写、执行等权限

所以请求分段的段表项可以理解为：

| 字段   | 作用          |
| ---- | ----------- |
| 段长   | 越界检查        |
| 段基址  | 段在内存中的起始地址  |
| 状态位  | 判断是否缺段      |
| 访问字段 | 辅助分段置换      |
| 修改位  | 判断换出时是否写回外存 |
| 外存地址 | 缺段时从哪里调入    |
| **权限字段** | **控制读、写、执行**    |

---

### 1.3 地址变换过程

逻辑地址：

```text
(段号 S, 段内地址 W)
```

**地址变换过程也大差不差：**

1. 检查段号 `S` 是否越界
2. 查段表，得到该段的段长、状态位、基址等信息
3. 检查段内地址 `W` 是否越界
   - 合法条件：`W < 段长`
   - 越界条件：`W >= 段长`
4. 检查状态位：
   - 若段已在内存：`物理地址 = 段基址 + W`
   - 若段不在内存：产生缺段中断，OS 将该段调入内存
5. 调段完成后修改段表，再重新执行被中断的指令

### 1.4 共享段管理

分段天然适合共享，因为段是有逻辑意义的单位，例如：

- 共享库代码段
- 公共子程序段
- 只读常量段

多个进程可以让自己的段表指向同一个共享段

共享段表中常见字段：

| 字段 | 含义 |
|---|---|
| 共享段名 | 标识共享段 |
| 段长 | 共享段大小 |
| 内存基址 | 当前在内存中的位置 |
| 外存地址 | 不在内存时的位置 |
| 权限 | 读、写、执行限制 |
| count | 当前共享该段的进程数 |

`count` 是共享段回收的关键

共享段回收规则：

1. 某进程不再使用共享段时，只删除该进程段表中的对应表项
2. 共享段表中的 `count - 1`
3. **如果 `count > 0`，说明仍有其他进程在使用，不能回收**
4. **如果 `count = 0`，说明无人使用，才真正回收该共享段**

重点：

> 共享段是否回收，不看某一个进程是否不用了，而看 `count` 是否为 0

---

### 1.6 请求分段的核心优缺点

优点：

- 更符合程序逻辑结构
- 适合共享代码段、共享库段
- 适合按段设置保护权限
- 不必一次性装入所有段，节省内存

缺点：

- 段大小不固定，调入和置换更复杂
- 调入一个大段可能需要较大的连续内存空间
- 仍可能产生外部碎片
- 置换时需要考虑共享段、修改位、段大小等因素

一句话总结：

> 请求分段的重点不是"怎么算地址"，而是：**把虚拟存储器的按需调入思想用在逻辑段上，并强化共享和保护**
