存储器管理，就是操作系统想办法把多个程序 **安全**、**高效**、**方便** 地 **放进内存**，并让 CPU 能正确找到它们的数据和指令

## 1. 为什么需要存储管理？

把==**内存**==想象成宿舍楼：房间有限、住户很多、不能乱住、位置不固定、程序员也不想关心房间号

所以 OS 要做"宿管系统"：分配、记录、保护、提高利用率，并让程序以为自己拥有一片连续、完整、很大的空间

**关键概念**：
1. **逻辑地址**：程序看到的地址
2. **物理地址**：真实内存中的地址

OS 的核心工作之一就是：**逻辑地址 → 物理地址**

## 2. 存储器架构

抽象层次：寄存器 → 主存 → 外存

OS 主要管理主存（内存），但必须结合外存——因为对换、虚拟存储器、页面置换都离不开外存

## 3. 程序如何进入内存

源代码 → **编译** → 目标模块 → **链接** → 装入模块 → **装入** → 内存

![[Pasted image 20260520165559.png]]

> **概念边界（容易混）**：
> - **装入**：把装入模块放入内存，并建立**逻辑地址 → 物理地址**的关系
> - **链接**：解决多个目标模块和库模块之间**符号引用和地址连接**的问题

### 1. 三种装入方式

核心问题：**程序里的地址，怎么对应到真实内存地址？**

| 装入方式    | 地址确定时机    | 核心特点               | 灵活性 |
| ------- | --------- | ------------------ | --- |
| 绝对装入    | 编译/装入前    | 逻辑地址 = 物理地址        | 最差  |
| 可重定位装入  | 装入时一次性修改  | 装入时把逻辑地址都加一个基址     | 中等  |
| 动态运行时装入 | 运行时由硬件做转换 | 装入后仍保留相对地址，靠重定位寄存器 | 最强  |

- **绝对装入**：地址写死，程序只能放固定位置
- **可重定位装入**：装入后地址被改死，搬动作业就麻烦
- **动态运行时装入**：装入后地址还是相对的，运行时才翻译——这是后面"动态分区分配能搬动作业"以及"分页/分段"的前提

### 2. 程序的链接

链接 = 把目标模块和**库模块**拼接起来，解决符号引用和地址连接

> - **静态库**：通常是多个 `.o` 的归档，静态链接时**只抽取需要的目标模块**
> - **动态库**：已经链接好的共享对象，运行时由装入器/OS 映射到进程地址空间

#### 1. 静态链接

装入内存前，已经把目标模块和库模块链接成完整装入模块

- 库代码**复制进可执行文件**
- 多个程序用同一个库 → 内存中重复
- 库更新 → exe 必须重新链接（因为里面是旧版库代码副本）

![[Pasted image 20260520171819.png]]

#### 2. 装入时动态链接

程序装入内存时，**边装入边链接**：可执行文件里只记录"需要哪个库"，由装入器去找

- 多个程序可**共享同一份库代码**
- 库更新一般不用重新链接 exe

![[Pasted image 20260520180415.png]]

#### 3. 运行时动态链接

程序先跑起来，等真正调用某个模块时，OS 才把它调入内存并链接

- 加快装入、节省内存
- 没用到的模块根本不进内存

![[Pasted image 20260520184134.png]]

> **动态库的本质**：库代码不提前复制进可执行文件，而是运行时由装入器/OS **映射到进程地址空间**代码页可按需调入，只读代码页可被多个进程共享

#### 4. 对比

| 链接方式     | 链接时机       | 库代码在哪      | 库更新是否需重链 |
| -------- | ---------- | ---------- | -------- |
| 静态链接     | 装入内存前      | 复制进 exe    | 需要       |
| 装入时动态链接  | 装入内存时      | 外存动态库，运行映射 | 一般不需要    |
| 运行时动态链接  | 程序运行中真正调用时 | 外存动态库，按需映射 | 一般不需要    |

> **装入时动态链接 vs 运行时动态链接**（不要错写成"装入 vs 运行"）
> - **装入时**：装入这道程序时，把它依赖的库一起链接进来
> - **运行时**：只有运行中某模块真正被调用且尚未装入时，才调入并链接

## 4. 连续分配方式

### 1. 核心理解

> 给程序分配**一整块连续的内存空间**

`| OS | 空闲区 | 作业 A | 空闲区 | 作业 B | 空闲区 |`

连续分配的**根本矛盾**：

> **内存空闲总量可能足够，但由于不连续，作业仍然无法装入**

这是后面要引出分页/分段的根本动机

### 2. 演化逻辑

**单一连续分配** → **固定分区** → **动态分区** → **动态重定位** → 引出 **分页**

| 方式      | 解决的旧问题          | 核心思想       | 新问题       |
| ------- | --------------- | ---------- | --------- |
| 单一连续分配  | 程序怎么放进内存        | 用户区只给一个程序  | 一次只能跑一个程序 |
| 固定分区    | 想跑多个程序          | 内存预先切固定大小区 | 内部碎片，分区数死 |
| 动态分区    | 固定分区不灵活、内部浪费    | 按作业大小现切    | 外部碎片      |
| 动态重定位分区 | 外部碎片导致大作业装不下    | 紧凑 + 动态地址转换 | 移动作业有时间代价 |
| 分页（后续）  | 连续分配的根本矛盾——必须连续 | 干脆放弃连续要求   |           |

### 3. 四种方式

#### 3.1 单一连续分配

`| 操作系统区 | 用户程序区 |`

整个用户区只给一个程序简单，但只能跑一个用户程序、内存利用率低

#### 3.2 固定分区分配

内存预先切成多个==**固定大小**==的分区，每个分区最多住一个作业

`| OS | 16K | 32K | 64K | 128K |`

**内部碎片**：分区已分配但作业没用完，剩余部分无法再分给别人

| 32K 分区              |
| ------------------- |
| 20K 作业 + **12K 浪费** |

#### 3.3 动态分区分配

按作业大小**现场切**：

```
初始：   | OS | 200K 空闲 |
来 A50: | OS | A 50K | 150K 空闲 |
来 B80: | OS | A 50K | B 80K | 70K 空闲 |
```

需要维护**空闲分区表**或**空闲分区链**

==**外部碎片**==：

> **空闲总量够，但不连续**，大作业无法装入

`| OS | A | 10K空 | B | 15K空 | C | 20K空 |` 总空闲 45K，但放不下一个 30K 的连续作业

#### 3.4 动态重定位分区分配

> **它不是一个独立的新分配算法**，而是 = **动态分区分配 + 紧凑 + 动态地址转换支持**

分配流程：

1. 找到足够大的单个空闲区 → 按动态分区算法分配
2. 找不到，但空间总量够 → **紧凑**（移动已分配作业，合并碎片），再分配
3. 总量也不够 → 动态重定位也无能为力

紧凑示例：

```
前：| OS | 作业1 | 10K空 | 作业3 | 30K空 | 作业6 | 14K空 |
后：| OS | 作业1 | 作业3 | 作业6 | 大空闲区 |
```

**前提**：必须有**动态运行时装入**支持，否则作业一搬动地址就错了

### 4. 数据结构

- **空闲分区表**：每行记录起址、大小、状态
- **空闲分区链**：用指针把空闲分区串成链表，便于动态插入、删除、合并

### 5. 动态分区分配算法

核心问题：新作业来了，**选哪一块空闲分区**？

| 算法         | 核心规则          | 主要问题         |
| ---------- | ------------- | ------------ |
| FF 首次适应    | 从头找第一个够用的     | 低地址区碎片多      |
| CF/NF 循环首次 | 接着上次位置继续找     | 大空闲区容易被破坏    |
| BF 最佳适应    | 找最接近需求的       | 容易留下极小、难用的碎片 |
| WF 最坏适应    | 找最大的          | 大空闲区被快速消耗    |
| 快速适应       | 为常见大小维护多个空闲链表 | 回收和合并复杂      |

**记忆口诀**：
- FF：从头找，够用就拿
- NF：接着上次继续找
- BF：找最贴身的房间（剩边角料）
- WF：专挑最大的切（大房间消耗快）

### 6. 内存回收

**回收作业占用区，并与相邻空闲区合并，更新空闲分区表/链**

### 7. 伙伴系统

特殊的连续分配：**分割和回收都按 2 的 k 次幂**需要 20K → 给 32K

- 分割合并规则清晰，回收时容易找"伙伴块"
- 仍可能产生**内部浪费**

### 8. 两类碎片

| 类型   | 出现位置    | 典型来源      | 本质        |
| ---- | ------- | --------- | --------- |
| 内部碎片 | 已分配分区内部 | 固定分区、伙伴系统 | 分给你了，但没用完 |
| 外部碎片 | 已分配分区之间 | 动态分区      | 总量够，但拼不起来 |

> 内部碎片：房间里空着
> 外部碎片：走廊上零散空房拼不起来

## 5. 我的理解

连续分配的本质：**OS 把内存看作一条连续走廊，每个作业必须找一段连续区域**

知识链条：

> 单一连续 → 固定分区（多道、但分区死） → 动态分区（按需切、但外部碎片） → 动态重定位（紧凑救场、但需要运行时地址转换） → **连续这个约束本身才是根源** → 引出分页/分段

每次演化都解决上一步的问题，又带出新的问题；最终发现"必须连续"才是矛盾根源，所以后面会彻底放弃连续要求

## 6. 常见误区

#### 误区 1：动态重定位 = 修改地址

不对它至少包含三件事：
1. **移动作业**位置
2. **合并空闲碎片**（紧凑）
3. 靠**动态地址转换**（重定位寄存器）保证作业移动后仍能正确访问内存

#### 误区 2："装入时动态链接 vs 运行时动态链接" ≠ "装入 vs 运行"

两者都属于**动态链接**，差别只是链接发生的时机：
- 装入时：装入这道程序时连带把库链接进来
- 运行时：运行中真正调用到时才链接

#### 误区 3：动态库 = 整个搬进内存

不准确动态库长期在外存，**运行时由装入器/OS 映射到进程地址空间**，代码页按需调入，只读代码页可被多个进程**共享**

#### 误区 4：静态库 = 一个大文件全塞进 exe

不准确静态库是多个 `.o` 的归档，静态链接时**只抽取需要的目标模块**复制进 exe

#### 误区 5：动态重定位是一种新的分配算法

不是它依附于动态分区分配，只是在"找不到足够大的单个空闲区"时通过**紧凑**继续救场
